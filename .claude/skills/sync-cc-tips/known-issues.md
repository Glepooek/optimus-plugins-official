## 2026-09-09 降级链实测记录（2.1.2）

judge-D 的 (c) 指出上一轮重建的三跳降级链根本不工作，两条实测全部复现：

### ① 第二跳没有真换主机

```
curl -s -o /dev/null -w 'code=%{http_code} redirect=%{redirect_url}
'   https://github.com/anthropics/claude-code/raw/main/CHANGELOG.md
→ code=302 redirect=https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md

curl -sL … 同一 URL
→ final=https://raw.githubusercontent.com/… redirects=1 code=200
```

`-L` 跟随后的落点**恰是第一跳刚宣告不可达的那台主机**。上一轮我验证了「字节等价」（638939 字节、`cmp` 无差异，成立），就断言「同时换掉工具、网络栈、主机名三个变量」——**字节等价对内容成立、对可达性不成立，而降级链关心的恰是后者**。

`--max-redirs 0` / `-f` 都不能用来检测回落：

```
curl -sf --max-redirs 0 -o /dev/null https://github.com/…/raw/… → exit 0（code=302）
```

`-f` 只管 4xx/5xx，302 不算错误；`--max-redirs 0` 单独也不报错。两个「安全」选项叠加后仍静默通过。

**可用的真独立通道**（已验证）：

```
curl -sf -H 'Accept: application/vnd.github.raw'   https://api.github.com/repos/anthropics/claude-code/contents/CHANGELOG.md
→ code=200 redirects=0，638939 字节，与 raw 域 cmp 无差异
```

### ② 第一跳失败信号被管道吞掉

```
out=$(curl -s --max-time 5 https://<不可达>/CHANGELOG.md | awk '/^## /{exit} {print}')
→ exit=0  len=0
set -o pipefail 后同一条命令 → exit=6（CURLE_COULDNT_RESOLVE_HOST）
```

管道退出码取 awk 的。执行者唯一能观察到的现象是「空输出」，而当时的兜底表把「内容为空」路由到「停止流程，报告解析失败」——**降级指令与兜底表冲突，且后者会赢**，因为它匹配的是唯一可观测的现象。

**根因是兜底表把一个现象对应到了单一原因。** 空输出可以来自取数失败（该降级）或解析失败（该停止）。修复方式是引入能区分二者的第二个观测点（curl 退出码 + 文件是否非空），拆成两行。**兜底表的条目必须是「可观测现象 → 唯一处置」的映射**；当一个现象对应两种处置时，先找到区分它们的观测点，否则表会给出看起来完全合理的错误路由。

### 方法论教训

三个缺陷（(a) 分类校验、(c)① 假换主机、(c)② 管道吞码）**同一形态**：都是「验证了容易验证的那一半，把结论推广到没验证的那一半」。(a) 验了命令能跑、数字属实，没验输出能否支撑判断；(c)① 验了内容等价，没验可达性；(c)② 验了成功路径，没验失败路径。

**写死具体断言是好事**——SKILL.md 里那句「同时换掉工具、网络栈、主机名三个变量」正因为具体，judge 才能实跑反驳。若当初写的是「提升了鲁棒性」，这个缺陷永远不会被发现。

## 2026-09-09 脚本化重构实测记录（2.2.0）

把正文内嵌命令抽成 `scripts/` 下脚本时，暴露出三类**只在换实现后才可见**的问题。记录在此供后续同类重构参照。

### ① 判据里混着旧实现的视角

`needs_confirm` 原条件「锚点未找到 **且** > 30 个版本」中，前半个条件是 awk 实现的产物：awk 跑到文件末尾都没 `exit` 才会输出全部内容，所以「输出了全部」等价于「没找到锚点」。改用 Python 显式查找后，「找到锚点」与「范围过大」成了两个独立事实——锚点 `1.0.0` 真实存在且截断后仍有 351 个版本，旧判据在此完全失效。

**这类问题的特征**：判据在原实现下是对的，抽出来后仍然「能跑」，只是静默地漏掉一类场景。发现它靠的是**构造边界输入实跑**，不是读代码。

### ② 小数据上永不出现的分块 bug

`check_slash_name.py` 分块扫描 209MB 二进制（CHUNK 8MB，26 块），块间重叠 400 字符防止跨界匹配被切断。首版按上下文文本去重（`if ctx not in hits`），单测在小文件上全绿——因为小文件只有一块，没有重叠区。

实际缺陷：重叠区里同一命中在两个块中的**窗口长度不同**（块尾被截断），字符串比较必然不等，去重失效，`hit_counts` 虚高。修法是按全局字节偏移去重。

**发现它靠的是 `mock.patch(CHUNK, 1024)` 把边界拉进测试可控范围**，而不是构造 8MB 假文件。凡是分块/分页/流式处理，单测必须显式压小块大小造出边界。

### ③ 参数语法冲突

原文用 `grep -nE '标识符A|标识符B'` 传被删标识符，grep 的模式串不与 flag 语法冲突。改成 `argparse` 后，`--removed-ids --add-dir` 里的值本身长得像 flag（tips 中大量 id 以 `--` 开头），被解析成另一个选项。

选了「文档化 `--removed-ids=--foo` 等号形式」而非改用 `nargs='+'`——后者会引入「吃掉后续参数」的新歧义。约束写进 `--help`，调用方读得到。

### 顺带修正的历史记载

`init` 此前被记为「v2.1.266 已移除」（2026-09-04 全量核对的结论之一）。用新脚本实测发现它是带 `get description()` 与 `CLAUDE_CODE_NEW_INIT` 引用的活注册体。**这印证了「脚本只取证不下结论」的设计选择**：若脚本直接输出存在性判定，为迎合旧记载就得在代码里塞 `init` 特例；输出证据原文则让错误记载自己暴露。

### 脚本化引入的新维护负担：文档—脚本契约漂移

正文现在描述的是**脚本的输出契约**（`ok`/`verdict`/`next`/`needs_confirm` 等 30 个字段名）。脚本改了字段名而正文没跟，会产生一类新的失效引用——比「命令写错」更隐蔽，因为正文读起来仍然自洽。

改动脚本输出结构后跑一次交叉验证（2.2.0 首次执行，结果：30/30 全部命中，零漂移）：

```bash
python - <<'PY'
import re, pathlib, subprocess, json
skill = pathlib.Path('.claude/skills/sync-cc-tips/SKILL.md').read_text(encoding='utf-8')
# 把 names 换成当前正文实际引用的字段名清单
names = 'ok|hop|verdict|next|needs_confirm|advance_anchor|entries|failed|checks'
mentioned = set(re.findall(rf'`({names})`', skill))
def keys_of(cmd):
    r = subprocess.run(cmd, shell=True, capture_output=True, text=True, encoding='utf-8')
    try: d = json.loads(r.stdout)
    except Exception: return set()
    out = set(d)
    for v in d.values():
        if isinstance(v, dict):
            out |= set(v)
            for vv in v.values():
                if isinstance(vv, dict): out |= set(vv)
        if isinstance(v, list) and v and isinstance(v[0], dict): out |= set(v[0])
    return out
S = '.claude/skills/sync-cc-tips/scripts'
actual = set()
for c in [f'python {S}/fetch_changelog.py --limit 2', f'python {S}/validate_tips.py',
          f'python {S}/check_slash_name.py doctor', f'python {S}/build_alias_index.py',
          f'python {S}/detect_residue.py']:
    actual |= keys_of(c)
print('正文提到但脚本未输出:', sorted(mentioned - actual) or '无')
PY
```

⚠️ **只在成功路径跑一遍会漏掉失败分支字段。** `next`/`head`/`hint`/`warning`/`delta` 五个只在特定失败分支出现，正常调用永不输出——2.2.0 验证时它们初次被报为「未输出」，须分别 mock 出对应分支才能确认存在。**「字段没出现」有两种原因：不存在，或这条路径下本就不该出现。**

### 反向漂移：脚本输出了但正文不消费

上面那个交叉验证只查「正文提到 → 脚本是否输出」，**反方向查不到**。2.2.0 门禁评分时 judge 实跑发现 `shared_main` 被脚本输出、在正文第 75 行的注释里出现过一次，之后再无消费方——实跑 `shared_main_groups: 5`，其中 3 组（`agent`/`memory`/`vscode`）按当时的流程永远不会呈现给用户，而 `test-prompts.json` id 14 早就断言了「同组 ≥ 2 条时列出供人工判断」。修法是在第四步补一栏 📚 同主标识符聚集，并写明它与残影栏的区别（阈值内 vs 阈值外、参考 vs 可裁决）。

把上面脚本的最后两行换成下面这段可查双向：

```python
print('正文提到但脚本未输出:', sorted(mentioned - actual) or '无')
# 反向：脚本输出但正文一次都没提；提到 1 次的要人工确认是「声明」还是「消费」
print('脚本输出但正文未提:', sorted(k for k in actual - mentioned if not k.startswith('_')) or '无')
```

**「出现 1 次」是最危险的计数**——它足以骗过 `mentioned - actual` 这类存在性检查，却往往只是个声明，没有任何一步真的用它。

### 同类缺陷：改了实现忘了回头核对引用方

2.2.0 门禁一并查出的两处，成因相同——都是**同一事实在正文里写了两遍，只改了一遍**：

| 位置 | 写的 | 实际 | 后果 |
|---|---|---|---|
| 开篇检查点索引表 | 「锚点找不到**且** > 30 个」 | 实现只看版本数 | 与本文 ① 修过的判据自相矛盾，索引表成了旧判据的化石 |
| 第四步合并选项条件 | 「有残影候选时」 | 应为 `pending_review > 0` | 全部候选已豁免时（现网即是）会错误弹出合并选项，与 id 17 断言相反 |

第二处**是既有 bug 被重写时照抄**，不是重构引入的：`pending_review` 从 `detect_residue.py` 有它那天起就存在，正文却一直写「有候选」。**重写一段文字时，照抄的部分不会因为「我只是搬运」而免于审查。**

新增或改名字段后，检查项应是「正文里凡提到这个概念的地方」，而非「我这次编辑过的段落」——`grep -n '<字段名>\|<该字段的中文说法>'` 全文扫一遍成本极低。

### 判重索引对 camelCase 设置项零覆盖（2.2.0 门禁查出，已修）

`build_alias_index.py` 的 `PATTERNS` 原有四条：斜杠命令、长 flag、短 flag、**带前缀白名单**的大写环境变量。没有任何一条能匹配 camelCase——全库 45 个 settings 键（`defaultMode`/`statusLine`/`respondToBashCommands`…）全部 MISS，而 SKILL.md 的新增判定明写要检查「**设置项名**」是否命中。

更直接的证据：docstring 自陈收录「反引号内的 settings 键」，实测 `extract('`defaultMode`')` 返回 `set()`——**描述了一个不存在的能力**。全库 268 条里 settings 键一个都没加反引号，这个分支从写下那天起就没生效过。

环境变量前缀白名单 `(CLAUDE|CLAUDE_CODE|OTEL|ANTHROPIC|AWS|GOOGLE|DISABLE|MAX)_` 同样漏收 3 个：`BASH_DEFAULT_TIMEOUT_MS`、`FORCE_HYPERLINK`、`API_KEY`。

**失效方向是最危险的一侧**：漏收 → 判重报「未命中」→ 判为新增 → 静默产出重复条目，正是本 skill 自己认定「比不同步更糟」的那类失效。这四条现有条目的 `id` 恰好含该标识符（`defaultMode-权限模式`）而被 `ids` 兜住，但兜住是巧合——新条目的 id 不含设置项名时就漏了。

修法（两条模式各带形态约束，不是放宽成裸词）：

| 模式 | 约束 | 挡住了什么 |
|---|---|---|
| `[a-z]{2,}[a-z0-9]*(?:[A-Z][a-z][a-zA-Z0-9]*)+` | 首段 ≥2 个小写、大写后紧跟小写、前置排除 `/.-` | `macOS`（尾部全大写）、`iTerm2`（单字母头）、`hooks/monitors/headersHelper`（路径分量） |
| `[A-Z][A-Z0-9]*(?:_[A-Z0-9]+)+` | 至少一个下划线 | `MCP`/`JSON`/`CLI`/`API` 等无下划线缩写 |

aliases 从 1448 增至 1536（+6%），精确增长，未出现裸词方案那种数千词膨胀。`TestCamelCaseSettingsKeys` 与 `TestEnvVarPrefixWhitelistRemoved` 共 6 个测试锁住两侧（该收的收到、该挡的挡住）。

**教训**：`TestExtractRejectsNoise` 一直存在，它只测「不该收的没收」。**只测拒绝面不测覆盖面，漏收就是测试的盲区**——精确率被锁死，召回率无人看管。这类提取器的单测必须两侧都有。

### 「用户选继续」的分支要能真的继续（2.2.0 门禁查出，已修）

第二步基线体检失败时给用户「先修 / 继续」两个选项，续跑分支写的是「第五步比对时排除这些已知项」。但第五步的门是 `ok: true` 才放行，而 `validate_tips.py` 的 `ok = not failed` 由全部 checks 聚合、**argparse 里没有任何忽略项参数**——存量缺陷会让它恒为 `ok: false`，选「继续」的用户每一轮都会卡死在第五步。

**这类缺陷读单个步骤看不出来**，两处分别都自洽：第二步说「后面会排除」，第五步说「不过就停」。要跨步骤追一条具体路径才暴露。修法是把排除机制写实——留存第二步的基线 JSON，第五步逐项对比（`failed` 项在基线中已存在且 errors 未扩大 → 放行），并明确 `count_match` / `orphan_ref` 永不豁免（两者算的都是本轮增删，与存量无关）。

**给用户一个选项，就要保证那条路走得通。**「先修 / 继续」里的「继续」若无实现，等于把选择权做成了摆设。

### 「同一事实写多份」是本文档自己没套用的原则（2.2.0 门禁提出）

SKILL.md 对 **tips.jsonl 的条目总数**执行得很彻底——2026-09-07 删掉 6 处冗余数字、同步点归零，黑名单还专门立了一条禁令。但对**自身文档里的散文事实**从没套用同一原则：

| 同一事实 | 写在几处 | 后果 |
|---|---|---|
| 校验项数 | 3 处（正文 ×2、脚本 docstring） | 全部写「八项」，实际 9 项，三处同错 |
| `/tmp` 跨文件系统坑 | 4 处（回滚基线、失败表、黑名单、compatibility） | 未失准，但每处都在重复同一段论证 |
| `needs_confirm` 判据 | 2 处（开篇索引表、字段表） | 改实现时只改了一处，索引表成了旧判据的化石 |

三评查出的 8 条缺陷里，4 条集中在**派生计数与序号**上（八项 vs 九项、悬空的「第 4 项」、索引表判据、失败表行序与脚本键序不一致）。

**处理方式分两类，不要一刀切：**

- **派生计数与序号**——不写。项数改为「见下表」，序号改为写实调用方式（如「把 id 传入 `--removed-ids=`」而非「执行第 4 项」）。凡是能从脚本输出即时读出的，正文一律不复述数值
- **论证性散文**——留一处完整版，其余指向它。本轮把 `/tmp` 与「裸英文词」的重复论证压成「（失效原理见文末黑名单）」，保留黑名单里的完整版

⚠️ **不要为了消冗余把警告本身删掉**——警告出现在触发点附近是有价值的，冗余的是**论证**不是**提醒**。压缩的目标是「一句提醒 + 一个指向」，不是「删到只剩黑名单里那一条」。

### 分组召回的边界要写进正文（2.2.0 门禁查出，已修）

`main_identifier()` 取 id 的 **ASCII 前缀**分组。库里三条 code-review 条目（`/code-review-审查当前改动`、`requesting-code-review-…`、`receiving-code-review-…`）因共同概念在**后缀**而分属三个 main，永远聚不到一起——test-prompts id 14 原本就是拿这个场景做断言的，两侧都达不成。

前缀分组是有意取舍（无歧义、零误报），不是缺陷。但**边界不写进正文，用户会把「聚集栏为空」读成「库里没有主题冗余」**。已在聚集栏那节加一段说明，并把 id 14 的场景换成真实可达成的 `agent` 组（3 条，重叠度未达阈值故只进聚集栏不进 candidates），同时在 expected 里记下这条边界。

**教训**：召回类功能的文档必须写清「查不到 ≠ 不存在」。这与 `check_slash_name.py` 那条「正则写窄会把『存在』误判成『不存在』」同源——**都是把工具的能力边界误当成世界的边界**。

## 取证方法备注

判定某个斜杠名是否真实存在时，一手证据源是本机原生二进制而非官方文档（文档滞后于发布）：

```bash
B=~/AppData/Roaming/npm/node_modules/@anthropic-ai/claude-code/bin/claude.exe
grep -ao 'name:"<名字>"[^}]\{0,200\}' "$B" | head -3   # 命中注册体 → 斜杠名存在
grep -ao '{agentType:"<名字>"[^}]\{0,80\}' "$B"        # 命中 → 内置 subagent，无斜杠命令
```

### ⚠️ 2026-09-09：三次判据推翻记录

同一天对「怎么判定内置 skill」迭代了四轮，前三轮都能在抽样上跑通、都有反例，**这个过程本身是最重要的结论**：

| 轮次 | 判据 | 为什么错 |
|---|---|---|
| 1 | `no({name:"` 提取清单 | 混淆函数名随版本变，v2.1.266 已改名 `po(`，返回 **0 项**。0 项是最危险的输出——看起来像「没有内置 skill」而非「命令坏了」 |
| 2 | `[A-Za-z_$]{1,4}\(\{name:"` 泛匹配 | 命令跑通、36 项数字属实、抽样交叉验证也过，但按前缀分组后是 **12 个互不相干的函数**：`po(`、`Tee(`、`wmr(`，还有 `property(`/`create(` 被吃掉词尾的纯噪音。**「命令跑通且数字属实」≠「输出能支撑那个判断」** |
| 3 | 否定式：命中 `aliases`/`menuDescription`/`isEnabled` → 是命令不是 skill | `menuDescription` 不是命令专属，内置 skill 同样有。`claude-api`/`keybindings-help`/`design-sync` 全带 `files:()=>...SKILL_FILES`、`getPromptForCommand`、`userInvocable`——它们是 **skill**，被判成了命令 |
| 4（当前） | 只判**存在性**，不判 skill/命令 | ✅ 11 个样本全部可实跑复现 |

**根因：这个区分在 v2.1.266 已经不存在。** `claude --help` 明写 "Skills still resolve via `/skill-name`"，`--disable-slash-commands` 的说明是 "Disable all skills"——斜杠命令与 skill 是同一套注册（`po(` 是统一入口，`files:`/`getPromptForCommand` 的有无只是「正文来自文件」还是「写在代码里」的实现差异，用户不可见）。第 1–3 轮都是在为一个**问错了的问题**找精确答案。

**方法论教训：校验类步骤给错答案比给不出答案危害大得多**，因为它会让人停止怀疑。新判据比旧版少答一个问题，但每条判定都能实跑复现。已有 `[Skill]`/`[交互]` 标签的历史划分**不回溯改动**。

### 两个仍然有效的坑

1. **常量表不能作为存在性证据。** 二进制里有形如 `fJe="simplify",pJe="commit",MM="code-review"` 的常量表，用途是「需特殊处理的名字」，内置项与官方插件项混在一起——`code-review` 已证实来自插件的 `commands/code-review.md`。
2. **正则写窄会把「存在」误判成「不存在」**，方向恰好是最危险的一侧。首次提取用 `name:"x",menuDescription`（要求紧邻），漏掉中间插字段的 `name:"fewer-permission-prompts",requires:{workspace:!0},menuDescription:...`，该名字差点被当作不存在而删除。窗口取 200 字符正是为此。另外 `name:"init"` 这类短名会命中 JS 解析器里的无关字符串（`e.kind!=="init"`），**必须看上下文是不是注册体**，不能只看命中数。

删除类改动收尾必查**悬挂引用**：被删标识符是否仍被其他条目正文提及。2026-09-04 删 29 条后，`/simplify`、`/code-review`、`/commit`、`Bedrock/Vertex/Foundry`、`Remote Control` 在 5 条保留条目里留下悬挂引用，其中包括那条专讲「skill 与命令区别」的条目——它举的两个例子恰好都被删掉了。

### ⚠️ 2026-09-11：随附 skill 是惰性解包的内嵌资源，grep 不到 ≠ 不存在

第四轮判据（只判存在性）仍不足以覆盖**随附 skill**。二进制里：

```
bundledSkillsRoot = Ie(rp(), "bundled-skills", {ISSUES_EXPLAINER: ...})
```

随附 skill 的正文是**内嵌资源，首次使用时才解包**到 `<临时目录>/bundled-skills/`。未触发过就不在磁盘上（本机 `AppData/Local/Temp/claude-1000/` 下当时没有该目录），名字也不以 `name:"x"` 字面量形式存在于可执行段。**于是 `grep 'name:"simplify"'` 返回 0，而 `/simplify` 实际可用。**

当轮据此把 `/simplify`、`/dataviz` 判为「斜杠名本机不存在」并提请删除，被用户实跑推翻。同时暴露上文第 1 条坑的记载偏差：`code-review` 不只来自插件——CLI 自带的提示语写着「a fast, cheap code review, try `/code-review low`. **It runs the built-in skill** at its lightest effort level」，内置与插件同名并存。

**判定顺序改为：**

| 优先级 | 手段 | 结论强度 |
|---|---|---|
| 1 | 在真实会话里敲一次 | 决定性，直接采信 |
| 2 | `ls <临时目录>/bundled-skills/` | 有 → 存在；**空或不存在 → 无结论**（惰性解包） |
| 3 | 二进制 grep `name:"x"` | 命中 → 存在；**未命中 → 无结论** |

**教训**：这是同型错误的第三、四次了（前两次记在上文「两个仍然有效的坑」与「查不到 ≠ 不存在」；第四次是 `/deep-research`，见台账 2026-09-12 那行）。共同形状是**把「我的工具没看到」当成「它不存在」**——而由此派生的两个动作都不可逆：

| 派生动作 | 形态 | 为什么第二种更危险 |
|---|---|---|
| 提请删除条目 | `/simplify`、`/dataviz` | 会经 CHECKPOINT 被用户拦一次 |
| 在正文里写「没有此命令」 | `/deep-research` | **没有任何拦截点**，假陈述直接投放；tips 载体的固有约束正是「读者读完既无法追问也无法查证」，他照着这句话就不会去试 |

因此规矩是：存在性未命中一律降级为「无结论」并交回用户实跑确认，**既不得据此删除，也不得据此写下任何否定断言**——写「没有 X」与删掉 X 是同等强度的动作。允许写的只有「本机未取证到，未确认」。

### ⚠️ 2026-09-11：Git Bash 路径转换让 `orphan_ref` 静默漏检（已在脚本里堵住）

`--removed-ids` 的值以 `/` 开头时，MSYS 会把它当 POSIX 路径重写成 `<MSYS 安装根>/...`：
