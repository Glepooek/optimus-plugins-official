## 一、什么是提示词工程？

[提示词工程](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)是通过组织指令的结构，从 AI 模型获得更好输出的技艺。它关乎你如何措辞查询、指定风格、提供背景，以及引导模型行为来达成你的目标。

模糊指令和精心设计的提示词之间的差距，可能就是笼统输出与你真正需要的结果之间的差距。结构不佳的提示词可能需要多轮来回才能澄清意图，而一个精心设计的提示词能让你一次就得到想要的结果。

提示词工程也是[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)的基础构件——上下文工程已成为使用 LLM 时日益重要的一部分。不过，对于 Claude 5 系列模型而言，提示词工程正在与[上下文工程](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)趋同——趋势是更少的脚手架，更多的信息筛选（curation）。

为帮助你入门，我们整理了团队的一些最佳实践，包括能立即改善结果的实用方法。我们将从今天就能用上的简单习惯开始，逐步扩展到适用于复杂项目的高级方法。

## 二、如何使用提示词工程

最基本层面上，提示词工程就是修改你传给 LLM 的查询内容。通常只是在实际请求之前，为查询添加信息——但知道*哪些*信息才是*正确*的信息，才是设计出优秀且有效提示词的秘诀。

### 核心技巧

这些提示词工程技巧构成了有效 AI 交互的基础。持续使用它们，你会立刻看到响应质量的提升。

#### 明确清晰

现代 AI 模型对清晰、明确的指令反应格外好。不要假设模型会推断出你想要什么——直接说出来。用简单的语言明确说出你想要什么，不留歧义。

**关键原则**：明确告诉模型你想看到什么。如果你想要全面的输出，就直接要求。如果你想要特定功能，就把它们列出来。像 Claude 这样的现代模型尤其能从明确的指示中获益。

**示例：创建分析仪表盘**

**模糊**："创建一个分析仪表盘"

**明确**："创建一个分析仪表盘。尽可能包含相关的功能和交互。不要止步于基础功能，做一个功能完整的实现。"

第二个版本明确要求了全面的功能，并传达出你希望模型超越最低限度完成任务。

**最佳实践**：

* 用直接的动作动词开头："写""分析""生成""创建"
* 跳过开场白，直接进入请求本身
* 说明你希望输出包含什么，而不仅仅是要处理什么
* 明确质量与深度方面的期望

#### 提供背景与动机

解释某件事*为什么*重要，能帮助 AI 模型更好地理解你的目标，并给出更有针对性的响应。这对能够推理你潜在目标的新模型尤其有效。

**示例：格式偏好**

**效果较差**："永远不要使用项目符号"

**效果更好**："我更喜欢用自然段落的形式回答，而不是项目符号，因为我觉得流畅的行文更容易阅读、更有对话感。项目符号对我这种偏随性的学习风格来说太正式、太像清单了。"

第二个版本帮助模型理解规则背后的理由，从而能在相关的格式选择上做出更好的判断。

**何时提供背景**：

* 说明输出的目的或受众
* 澄清某些限制存在的原因
* 描述输出将如何被使用
* 指出你想解决的问题

#### 保持具体

提示词工程中的具体性，意味着用明确的指导原则和要求来组织你的指令。你对想要什么表达得越具体，效果就越好。

**示例：制定膳食计划**

**模糊**："为地中海饮食制定一份膳食计划"

**具体**："为糖尿病前期管理设计一份地中海饮食膳食计划。每日 1800 卡路里，侧重低血糖指数食物。列出早餐、午餐、晚餐和一份加餐，附完整的营养分析。"

**怎样才算足够具体？**

包含：

* 明确的约束条件（字数、格式、时间线）
* 相关背景（受众是谁、目标是什么）
* 期望的输出结构（表格、列表、段落）
* 任何要求或限制（饮食需求、预算限制、技术约束）

#### 使用示例

示例并非总是必需的，但在解释概念或演示特定格式时会大放异彩。这种做法也被称为 one-shot 或 few-shot 提示——用示例来"展示"而非"描述"，澄清那些仅靠文字描述难以表达的细微要求。

**给现代模型的重要提示**：Claude 4.x 及同类先进模型会非常仔细地关注示例中的细节。请确保你的示例与你想鼓励的行为一致，并尽量减少你想避免的模式。

**示例：文章摘要**

**没有示例**："总结这篇文章"

```
这是我想要的摘要风格示例：

文章：[关于 AI 监管的文章链接]
摘要：欧盟通过针对高风险系统的全面 AI 法案。关键条款包括透明度要求和人工监督规定。2026 年生效。

现在用同样的风格总结这篇文章：[你的新文章链接]
```

**何时使用示例**：

* 期望的格式更容易展示而非描述
* 你需要特定的语气或风格
* 任务涉及微妙的模式或惯例
* 简单指令未能产生一致的结果

**小贴士**：先从一个示例开始（one-shot）。只有当输出仍不符合你的需求时，才添加更多示例（few-shot）。

#### 允许 Claude 表达不确定性

明确允许 AI 表达不确定性，而不是去猜测。这能降低幻觉，提高可靠性。

**示例**："分析这份财务数据并识别趋势。如果数据不足以得出结论，请如实说明，而不要去揣测。"

这个简单的补充能让响应更值得信赖，因为它允许模型承认自身的局限。

## 三、高级提示词工程技巧

上面这些核心习惯已经能带你走得很远，但你可能仍会遇到需要更精细方法的场景。当你在构建智能体方案、处理复杂数据结构、或需要拆解多阶段问题时，高级提示词工程技巧会大放异彩。

### 预填充模型回复

预填充让你替 AI 的回复先起个头，从而引导格式、语气或结构。这个技巧在强制输出格式或跳过开场白时特别有效。

**何时使用预填充**：

* 你需要 AI 输出 JSON、XML 或其他结构化格式
* 你想跳过对话式的开场白，直接进入内容
* 你需要维持特定的语音或角色
* 你想控制 AI 回复的开头方式

**示例：强制 JSON 输出**

没有预填充时，Claude 可能会说："这是你要的 JSON：{...}"

使用预填充（API 用法）：

```
messages=[
    {"role": "user", "content": "从这段产品描述中提取名称和价格，转成 JSON。"},
    {"role": "assistant", "content": "{"}
]
```

AI 会从这个左花括号继续输出，只产出合法的 JSON。

**注意**：在聊天界面中，你可以通过非常明确的指令来近似实现这一点："只输出合法的 JSON，不要有任何开场白。以左花括号开始你的回复。"

### 思维链提示

思维链（Chain of Thought，CoT）提示要求模型在回答前进行逐步推理。这个技巧有助于那些能从结构化思考中受益的复杂分析任务。

**现代做法**：Claude 提供了[扩展思考（extended thinking）](https://www.anthropic.com/news/visible-extended-thinking)功能，能自动完成结构化推理。在可用的情况下，扩展思考通常优于手动构造思维链提示。不过，理解手动 CoT 仍然有其价值——适用于扩展思考不可用，或你需要可审查的透明推理过程的场景。

**何时使用思维链**：

* 扩展思考不可用（例如免费版 [Claude.ai](http://claude.ai) 方案）
* 你需要可供审查的透明推理过程
* 任务需要多个分析步骤
* 你想确保 AI 考虑了特定因素

思维链有三种常见的实现方式：

**基础版思维链**

只需在指令中加一句"逐步思考"。

```
为今年的"关爱儿童"募捐项目，给捐赠人写一封个性化的求捐邮件。

项目信息：
<program>
{{PROGRAM_DETAILS}}
</program>

捐赠人信息：
<donor>
{{DONOR_DETAILS}}
</donor>

在写邮件之前，请逐步思考。
```

**引导版思维链**

组织你的提示词，提供具体的推理阶段。

```
在写邮件之前先思考。首先，根据这位捐赠人的捐赠历史，思考什么样的措辞可能会吸引他们。然后，考虑"关爱儿童"项目的哪些方面会引起他们的共鸣。最后，运用你的分析，写出这封个性化的捐赠人邮件。
```

**结构化思维链**

用标签将推理过程与最终答案分隔开。

```
在 <thinking> 标签中思考后再写邮件。首先，分析什么样的措辞会吸引这位捐赠人。然后，识别项目中相关的方面。最后，在 <email> 标签中运用你的分析，写出这封个性化的捐赠人邮件。
```

**注意**：即使扩展思考可用，明确的 CoT 提示对复杂任务仍然有益。这两种方法是互补的，而非互斥的。

### 控制输出格式

对于现代 AI 模型，有几种有效的方式可以控制响应格式：

**1. 告诉 AI 应该做什么，而不是不应该做什么**

不要写："回复中不要使用 markdown" 试着写："你的回复应该由流畅的段落式行文组成"

**2. 让提示词的风格匹配期望的输出**

提示词中使用的格式风格可能会影响 AI 的响应风格。如果你想要极简的 markdown，就在提示词中减少 markdown 的使用。

**3. 明确说明格式偏好**

要对格式进行细致的控制：

```
在写报告或分析时，用清晰、流畅的行文，采用完整的段落。用标准的分段来组织内容。markdown 主要保留给行内代码、代码块和简单的标题使用。

除非你在呈现真正离散的条目、且列表格式确实是最佳选择，或用户明确要求列表，否则不要使用有序或无序列表。

不要用项目符号列出条目，而是把它们自然地融入句子中。你的目标是可读、流畅的文本，自然地引导读者理解思路。
```

### 提示词链（Prompt chaining）

与前面的技巧不同，提示词链无法在单个提示词中实现。链式提示把复杂任务拆解成更小的、按顺序执行的步骤，每个提示词处理一个阶段，其输出会作为下一条指令的输入。

这种方式用延迟换取更高的准确率，因为它让每个单独的任务变得更简单。通常这个技巧会通过工作流或编程方式来实现，但你也可以在收到响应后手动依次提供提示词。

**示例：研究摘要**

1. **第一个提示词**："总结这篇医学论文，涵盖方法论、研究发现和临床意义。"

2. **第二个提示词**："审查上面的摘要，评估其准确性、清晰度和完整性。给出分级反馈。"

3. **第三个提示词**："根据这条反馈改进摘要：[第 2 步的反馈]"

每个阶段都通过聚焦的指令增加一层打磨。

**何时使用提示词链**：

* 你有一个需要拆解成多个步骤的复杂请求
* 你需要迭代式打磨
* 你在做多阶段分析
* 中间验证能带来价值
* 单个提示词产生的结果不一致

**权衡**：链式提示会增加延迟（多次 API 调用），但通常能显著提升复杂任务的准确率与可靠性。

## 四、较旧或不太必要的技巧

一些在早期 AI 模型上流行的提示词工程技巧，对于像 Claude 这样的模型而言已不那么必要。不过，你可能仍会在较旧的文档中遇到它们，或在特定场景下发现它们仍然有用。

### 用 XML 标签组织结构

XML 标签曾是为提示词增加结构与清晰度的推荐做法，尤其是在纳入大量数据时。虽然现代模型即使没有 XML 标签也能更好地理解结构，但在特定场景下它们仍然有用。

**示例**：

```
<athlete_information>
- 身高：6'2"
- 体重：180 lbs
- 目标：增肌
- 饮食限制：素食
</athlete_information>

根据上面的运动员信息生成一份膳食计划。
```

**XML 标签仍可能有帮助的场景**：

* 你在处理混合多种内容类型的极其复杂的提示词
* 你需要绝对确定内容的边界
* 你在使用较旧的模型版本

**现代替代方案**：对大多数场景而言，清晰的标题、空白排版和明确的语言（"使用下面的运动员信息……"）效果同样好，且开销更小。

### 角色提示（Role prompting）

角色提示是在你措辞查询的方式中，定义专家人设与视角。虽然这可能有效，但现代模型已经足够成熟，过度设定角色人设往往没有必要。

**示例**："你是一名财务顾问。分析这份投资组合……"

**重要警示**：不要过度限定角色。"你是一个乐于助人的助手"往往比"你是一位举世闻名的专家，只讲技术术语，从不犯错"效果更好。过于具体的角色设定会限制 AI 的帮助能力。

**角色提示可能有帮助的场景**：

* 你需要在大量输出中保持一致的语气
* 你在构建需要特定人设的应用
* 你想为复杂主题增加领域专家的框架感

**现代替代方案**：通常，明确说出你想要的视角会更有效："分析这份投资组合，重点关注风险承受能力和长期增长潜力"，而不是分配一个角色。

## 五、综合运用示例

你已经分别见过了这些技巧，但它们真正的威力在于策略性地组合使用。提示词工程的艺术不在于用上所有可用的技巧，而在于为你的具体需求挑选正确的组合。

**综合运用多种技巧的示例**：

```
从这份季度报告中提取关键财务指标，并以 JSON 格式呈现。

我需要这些数据用于自动化处理，所以你的回复必须只包含合法的 JSON，不能有开场白或解释——这一点非常重要。

使用这个结构：
{
  "revenue": "带单位的数值",
  "profit_margin": "百分比",
  "growth_rate": "百分比"
}

如果报告中没有清楚说明某项指标，使用 null，不要去猜测。

以左花括号开始你的回复：{
```

这个提示词组合了：

* 明确指令（确切说明要提取什么）
* 背景说明（为什么格式很重要）
* 示例结构（展示格式）
* 允许表达不确定性（不确定时使用 null）
* 格式控制（以左花括号开头）

## 六、如何选择技巧

不是每个提示词都需要用上每一种技巧。这里有一套决策框架：

**从这里开始：**

1. 你的请求是否清晰明确？如果不是，先解决清晰度问题
2. 任务是否简单？只用核心技巧（保持具体、清晰、提供背景）
3. 任务是否需要特定格式？使用示例或预填充
4. 任务是否复杂？考虑拆解任务（链式提示）
5. 是否需要推理？使用扩展思考（如果可用）或思维链

**技巧选择指南**：

| 如果你需要…… | 使用…… |
| --- | --- |
| 特定的输出格式 | 示例、预填充，或明确的格式说明 |
| 逐步推理 | 扩展思考（Claude 4.x）或思维链 |
| 复杂的多阶段任务 | 提示词链 |
| 透明的推理过程 | 带结构化输出的思维链 |
| 防止幻觉 | 允许模型说"我不知道" |

## 七、排查问题与常见错误

### 排查常见提示词问题

即使是善意设计的提示词也可能产生意外结果。以下是常见问题及对应修复方法：

* **问题：响应过于笼统** → 解决方法：增加具体性、示例，或明确要求全面的输出。要求 AI"不要止步于基础"。
* **问题：响应偏离主题或没抓住重点** → 解决方法：更明确地说明你真正的目标。提供你为什么这样问的背景。
* **问题：响应格式不一致** → 解决方法：添加示例（few-shot），或用预填充控制响应的开头。
* **问题：任务过于复杂，结果不可靠** → 解决方法：拆解成多个提示词（链式提示）。每个提示词只做好一件事。
* **问题：AI 包含不必要的开场白** → 解决方法：使用预填充，或明确要求："跳过开场白，直接给出答案。"
* **问题：AI 编造信息** → 解决方法：明确允许它在不确定时说"我不知道"。
* **问题：你想要实现，AI 却建议修改方案** → 解决方法：明确表达行动意图："修改这个函数"，而不是"你能建议一些修改吗？"

**小贴士**：从简单开始，只在需要时增加复杂度。每加一项改动就测试一下它是否真的改善了结果。

### 常见误区

从以下常见陷阱中吸取经验，节省时间并改进你的提示词：

* **不要过度工程化**：更长、更复杂的提示词并不总是更好。
* **不要忽视基本功**：如果你的核心提示词本身不清晰或含糊，高级技巧也帮不上忙。
* **不要假设 AI 会读心**：明确说出你想要什么。留有歧义会给 AI 留下误解的空间。
* **不要同时用上所有技巧**：只选择针对你具体挑战的技巧。
* **不要忘记迭代**：第一版提示词很少能完美运行。要测试并打磨。
* **不要依赖过时的技巧**：对现代模型而言，XML 标签和过度的角色提示已不那么必要。从明确、清晰的指令开始。

## 八、其他考量

### 处理长内容

实施高级提示词工程的一大挑战是，它会通过额外的 token 使用增加上下文开销。示例、多个提示词、详细的指令——它们都会消耗 token，而上下文管理本身就是一项技能。

请记住，只有在提示词工程技巧确实有意义、其使用能够被证明合理时才使用它们。关于如何有效管理上下文的全面指导，请参阅我们关于[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)的博客文章。

**上下文感知能力的提升**：包括 Claude 4.x 在内的现代 AI 模型，其上下文感知能力已显著改善，有助于解决历史上"迷失在中间"（lost-in-the-middle）的问题——即模型难以对长上下文的所有部分给予同等关注。

**为什么任务拆分仍然有帮助**：即便有了这些改进，把大任务拆分成更小、离散的任务块仍然是一项有价值的技巧——不是因为上下文的限制，而是因为它能帮助模型在一组非常具体的要求和范围内专注地做好工作。相比在单个提示词中尝试完成多个目标，边界清晰、聚焦的任务始终能产生更高质量的结果。

**策略**：在处理长上下文时，把最关键的细节放在信息的开头或结尾，清晰地组织你的信息结构。在处理复杂任务时，考虑将其拆解为聚焦的子任务是否能提高每个组成部分的质量与可靠性。

### 提示词工程示例：好的提示词是什么样的

提示词工程是一项技能，你需要多次尝试才能掌握它。判断自己做得对不对，唯一的方法就是测试并观察结果。第一步就是亲自尝试。你会立刻看到使用了本文技巧和没使用技巧的查询之间的差异。

## 九、结语建议

提示词工程归根到底是一种沟通：用能让 AI 最清晰理解你意图的语言来表达。从本文早先介绍的核心技巧入手，持续使用直到它们成为你的第二天性。只有在高级技巧能解决特定问题时，才叠加使用它们。

请记住：最好的提示词不是最长或最复杂的那一个，而是能用最简的必要结构可靠达成你目标的那一个。随着实践的积累，你会培养出判断哪种技巧适合哪种场景的直觉。

对于你希望应用到每一次会话、而不仅仅是每一条提示词的指令，把它们迁移到 [CLAUDE.md 文件、Skill 或其他引导（steering）方法](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)中管理。不过，向上下文工程的转变并不会削弱提示词工程的重要性。

事实上，提示词工程是上下文工程中的一块基础构件。每一个精心设计的提示词都会成为塑造 AI 行为的更大上下文的一部分，与对话历史、附加文件和系统指令共同作用，产生更好的结果。
