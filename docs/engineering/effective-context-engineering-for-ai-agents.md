# 面向 AI 智能体的高效上下文工程

上下文是 AI 智能体一种至关重要但有限的资源。本文探讨了如何有效地筛选和管理为智能体提供动力的上下文。

> **来源：** [Anthropic Engineering - Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
> **发布日期：** 2025 年 9 月 29 日
> **作者：** Anthropic 应用 AI 团队

---

经过几年应用 AI 领域对提示词工程的持续关注，一个新术语开始崭露头角：**上下文工程（context engineering）**。用语言模型构建应用，正变得越来越不是关于为你的提示词找到恰当的措辞和句式，而是要回答一个更宏观的问题："什么样的上下文配置最有可能激发出我们模型想要的行为？"

**上下文（Context）**指的是从大语言模型（LLM）中采样时所包含的那组 token。而**工程（engineering）**要解决的问题，则是在 LLM 固有的各种约束条件下，优化这些 token 的效用，从而稳定地达成预期结果。要有效驾驭 LLM，往往需要*用上下文思考*——换句话说：要考虑在任意给定时刻 LLM 可用的整体状态，以及这种状态可能催生出的潜在行为。

在本文中，我们将探讨上下文工程这门正在兴起的技艺，并提供一套用于构建可引导、高效能智能体的精炼思维模型。

## 一、上下文工程与提示词工程的区别

在 Anthropic，我们把上下文工程看作提示词工程的自然演进。提示词工程指的是为获得最佳结果而撰写和组织 LLM 指令的方法（参见[我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)，了解概述及实用的提示词工程策略）。**上下文工程**则指的是在 LLM 推理过程中筛选并维护最优 token（信息）集合的一整套策略，涵盖除提示词之外可能进入上下文的所有其他信息。

在 LLM 工程实践的早期，提示词编写是 AI 工程工作中最大的组成部分，因为除了日常的对话交互之外，绝大多数使用场景都需要针对一次性分类或文本生成任务进行优化的提示词。顾名思义，提示词工程的核心关注点在于如何撰写有效的提示词，尤其是系统提示词。然而，随着我们朝着构建能够跨越多轮推理、更长时间跨度运作的更强大智能体迈进，我们需要一整套策略来管理完整的上下文状态（系统指令、工具、[模型上下文协议](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）、外部数据、消息历史等）。

一个在循环中运行的智能体会不断生成越来越多*可能*与下一轮推理相关的数据，而这些信息必须被周期性地提炼。上下文工程正是这样一门[技艺与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)：从这个持续演变的、信息量庞大的可能性宇宙中，筛选出真正应该进入这个有限上下文窗口的内容。

![提示词工程与上下文工程的对比：提示词工程只需一次性剪裁上下文窗口内容，上下文工程则需要在每一轮推理前对海量候选上下文进行筛选、剪裁后再送入模型](../assets/prompt-engineering-vs-context-engineering.png)

*与撰写提示词这种一次性、离散的任务不同，上下文工程是迭代式的，每一次我们决定要向模型传递什么内容时，都要经历一次筛选阶段。*

## 二、为什么上下文工程对构建强大的智能体至关重要

尽管 LLM 具备很快的速度和处理越来越大数据量的能力，但我们观察到，LLM 就像人类一样，到了某个临界点就会失去专注或产生混乱。针对"大海捞针"式（needle-in-a-haystack）基准测试的研究揭示了[上下文腐化（context rot）](https://research.trychroma.com/context-rot)这一概念：随着上下文窗口中 token 数量的增加，模型准确回忆该上下文中信息的能力会随之下降。

尽管一些模型表现出的性能衰减比其他模型更为平缓，但这一特性会在所有模型中出现。因此，上下文必须被当作一种边际收益递减的有限资源来对待。就像人类拥有[有限的工作记忆容量](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277)一样，LLM 在解析大量上下文时，也依赖一个会被消耗的"注意力预算"。每引入一个新 token，都会消耗一定量的这个预算，这也增加了对提供给 LLM 的 token 进行精心筛选的必要性。

这种注意力稀缺性源于 LLM 的架构限制。LLM 基于[Transformer 架构](https://arxiv.org/abs/1706.03762)构建，该架构使得每个 token 都能[关注（attend to）整个上下文中的其他每一个 token](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)。这就导致 n 个 token 之间会产生 n² 个两两配对关系。

随着上下文长度的增加，模型捕捉这些两两配对关系的能力会被拉得越来越薄，这就在上下文规模与注意力聚焦程度之间形成了一种天然的张力。此外，模型的注意力模式是从训练数据的分布中习得的，而在训练数据中，较短的序列通常比较长的序列更为常见。这意味着模型对于跨越整个上下文的依赖关系，积累的经验更少，专门用于处理这类依赖关系的参数也更少。

诸如[位置编码插值（position encoding interpolation）](https://arxiv.org/pdf/2306.15595)之类的技术，能让模型通过适配其最初训练时使用的较短上下文，来处理更长的序列，不过这种做法会在一定程度上损失模型对 token 位置的理解能力。这些因素共同造就的是一种性能上的渐变梯度，而非断崖式下跌：模型在更长的上下文中依然保持相当强的能力，但相比在较短上下文下的表现，在信息检索和长距离推理方面的精确度可能会有所下降。

这些现实情况意味着，深思熟虑的上下文工程对于构建强大的智能体而言是必不可少的。

## 三、高效上下文的构成要素

既然 LLM 受限于有限的注意力预算，那么*好*的上下文工程，意味着要找到能够最大化实现预期结果可能性的*最小*高信号 token 集合。落实这一原则说起来容易，做起来难，但在接下来的内容中，我们将概述这一指导原则在上下文的各个不同组成部分中，具体意味着什么。

**系统提示词**应当极其清晰，使用简单、直接的语言，把想法呈现在适合智能体的*恰当高度*上。这个恰当的高度，正是处于两种常见失败模式之间的"金发姑娘区间"（Goldilocks zone）。一个极端是，工程师在提示词中硬编码复杂而脆弱的逻辑，试图引出精确的智能体行为。这种做法会造成脆弱性，并随着时间推移增加维护的复杂度。另一个极端是，工程师有时会提供模糊、高层次的指引，既没有给 LLM 提供关于预期输出的具体信号，又错误地假设了双方共享的上下文。最优的高度需要在两者间取得平衡：足够具体以有效引导行为，又足够灵活，能为模型提供强有力的启发式引导。

![校准系统提示词的过程：过于具体的一端是脆弱的 if-else 硬编码提示词，过于宽泛的一端是过度笼统或错误假设共享上下文的提示词，恰到好处的提示词则介于两者之间](../assets/calibrating-the-system-prompt.png)

*在这个谱系的一端，我们看到的是脆弱的、硬编码 if-else 逻辑的提示词；而在另一端，我们看到的是过于笼统、或错误地假设了共享上下文的提示词。*

我们建议将提示词组织成若干独立的小节（例如 `<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description` 等），并使用 XML 标签或 Markdown 标题这类技巧来划分这些小节，不过随着模型能力的增强，提示词的具体格式可能正变得越来越不那么重要。

无论你决定如何组织你的系统提示词，你都应该追求那个能完整勾勒出预期行为的最小信息集合。（请注意，"最小"并不一定意味着"简短"；你仍然需要事先给智能体提供足够的信息，以确保它遵循预期的行为。）最好的做法是先用市面上能力最强的模型，测试一份最简版本的提示词，看看它在你的任务上表现如何，然后根据初始测试中发现的失败模式，逐步添加明确的指令和示例来提升表现。

**工具**让智能体能够与其所处的环境交互，并在工作过程中拉取新的、额外的上下文。由于工具定义了智能体与其信息/行动空间之间的契约，因此工具必须能促进效率，这一点极其重要——既要通过返回具有 token 效率的信息，也要通过鼓励高效的智能体行为来实现。

在[《为 AI 智能体编写工具——借助 AI 智能体本身》](https://www.anthropic.com/engineering/writing-tools-for-agents)一文中，我们讨论了如何构建那些能被 LLM 充分理解、且功能重叠极小的工具。与一个设计良好的代码库中的函数类似，工具应该是自成一体的、对错误具有鲁棒性的，并且在其预期用途上表述得极其清晰。输入参数同样应该具备描述性、无歧义，并能充分发挥模型的固有优势。

我们观察到最常见的一种失败模式，是工具集过于臃肿，覆盖了过多的功能，或者导致在"该用哪个工具"这个决策点上出现歧义。如果一名人类工程师都无法明确说出在某种情况下应该使用哪个工具，那就不能指望一个 AI 智能体能做得更好。正如我们稍后会讨论的，为智能体精心筛选出一套最小可行的工具集，也有助于在长时间的交互中更可靠地维护和裁剪上下文。

提供示例，也就是所谓的少样本提示（few-shot prompting），是一项众所周知的最佳实践，我们依然强烈建议采用。然而，团队常常会把一长串边缘情况塞进提示词里，试图把 LLM 在某项特定任务中应遵循的每一条可能规则都表述清楚。我们不建议这样做。相反，我们建议致力于筛选出一组多样化、具有代表性的典范示例，以有效地呈现智能体的预期行为。对 LLM 而言，示例就是"一图胜千言"的那张图。

我们对上下文各个不同组成部分（系统提示词、工具、示例、消息历史等）的整体建议是：审慎思考，让你的上下文既内容丰富，又保持精简紧凑。接下来，让我们深入探讨在运行时动态检索上下文的问题。

## 四、上下文检索与智能体式搜索

在[《构建高效的 AI 智能体》](https://www.anthropic.com/research/building-effective-agents)一文中，我们强调了基于 LLM 的工作流与智能体之间的区别。自那篇文章发表以来，我们已经逐渐倾向于采用一个针对智能体的[简洁定义](https://simonwillison.net/2025/Sep/18/agents/)：LLM 在循环中自主地使用工具。

在与客户共同工作的过程中，我们看到整个领域正在向这个简洁的范式收敛。随着底层模型能力的增强，智能体的自主程度也能相应扩展：更聪明的模型能让智能体独立地在复杂微妙的问题空间中导航，并从错误中恢复。

我们现在正看到工程师们在设计智能体上下文时的一种思路转变。如今，许多 AI 原生应用都采用某种基于嵌入的、推理前的检索方式，为智能体呈现需要推理的重要上下文。随着这个领域向更具智能体特质的方式转变，我们越来越多地看到团队用"即时（just in time）"上下文策略来增强这些检索系统。

与预先处理好全部相关数据不同，采用"即时"方式构建的智能体维护着一些轻量级的标识符（文件路径、存储的查询、网页链接等），并借助这些引用在运行时通过工具动态地将数据加载进上下文。Anthropic 的智能体式编程解决方案 [Claude Code](https://www.anthropic.com/claude-code) 就采用这种方式对大型数据库进行复杂的数据分析。模型可以编写有针对性的查询、存储结果，并借助像 head、tail 这样的 Bash 命令来分析海量数据，而完全不需要把整个数据对象加载进上下文。这种方式与人类的认知方式如出一辙：我们通常不会去记住整个信息语料库，而是引入外部的组织和索引系统——比如文件系统、收件箱、书签——按需检索相关信息。

除了存储效率之外，这些引用的元数据还提供了一种能高效地细化行为的机制，无论这种细化是显式提供的，还是靠直觉体会到的。对于一个在文件系统中操作的智能体而言，一个名为 `test_utils.py` 的文件出现在 `tests` 文件夹中，与同名文件出现在 `src/core_logic/` 文件夹中，所暗示的用途是不同的。文件夹层级、命名惯例和时间戳，都提供了重要的信号，帮助人类和智能体理解应该如何、以及何时利用这些信息。

让智能体能够自主地导航和检索数据，也带来了渐进式披露（progressive disclosure）——换句话说，让智能体能够通过探索逐步发现相关的上下文。每一次交互都会产生能为下一步决策提供依据的上下文：文件大小暗示了复杂程度；命名惯例暗示了用途；时间戳可以作为相关性的代理指标。智能体可以逐层构建自己的理解，只在工作记忆中保留必要的内容，并借助笔记记录策略来实现额外的持久化。这种由智能体自主管理的上下文窗口，能让智能体专注于相关的信息子集，而不至于淹没在详尽但可能无关的信息海洋中。

当然，这里存在一个权衡：运行时探索比检索预先计算好的数据要慢。不仅如此，要确保 LLM 拥有正确的工具和启发式方法，以有效地在其信息版图中导航，还需要有明确主张、深思熟虑的工程投入。如果没有恰当的引导，智能体可能会因误用工具、追逐死胡同，或未能识别出关键信息而白白浪费上下文。

在某些场景下，最有效的智能体可能会采用一种混合策略：预先检索一部分数据以求速度，同时在其认为必要时自主进行进一步探索。何为"恰当"的自主程度，这个决策边界取决于具体任务。Claude Code 正是采用这种混合模型的智能体：[CLAUDE.md](http://claude.md) 文件会被直接、不加处理地放入上下文，而像 glob 和 grep 这样的基础工具则让它能够在环境中导航，即时检索文件，从而有效避开了索引过时和语法树过于复杂这两个问题。

这种混合策略可能更适合动态性较低的场景，比如法律或金融工作。随着模型能力的提升，智能体的设计趋势将朝着让智能的模型自主、智能地行动，而人工筛选的介入会逐步减少这个方向发展。鉴于该领域的进步速度如此之快，"做最简单可行的事"很可能仍将是我们给那些在 Claude 之上构建智能体的团队所能提出的最好建议。

### 长时程任务的上下文工程

长时程任务要求智能体在一系列动作中保持连贯性、上下文和目标导向的行为，而这些动作所涉及的 token 数量会超出 LLM 的上下文窗口。对于像大型代码库迁移或综合性研究项目这类跨越数十分钟到数小时持续工作的任务，智能体需要一些专门的技巧来绕开上下文窗口大小的限制。

等待更大的上下文窗口似乎是个显而易见的策略。但可以预见，在未来一段相当长的时间里，无论上下文窗口有多大，都会受到上下文污染和信息相关性问题的困扰——至少在追求最强智能体表现的场景下是这样。为了让智能体能在延长的时间跨度内有效工作，我们开发了几种直接应对这些上下文污染约束的技巧：压缩（compaction）、结构化笔记记录，以及多智能体架构。

**压缩**

压缩，指的是把一段接近上下文窗口上限的对话进行摘要总结，然后用这份摘要重新初始化一个新的上下文窗口的做法。压缩通常是上下文工程中用来提升长期连贯性的第一个杠杆。从本质上讲，压缩以高保真的方式提炼出一个上下文窗口的内容，让智能体能够以最小的性能损耗继续推进。

以 Claude Code 为例，我们通过把消息历史传给模型，让它对最关键的细节进行摘要和压缩来实现这一点。模型会保留架构决策、未解决的 bug 和实现细节，同时丢弃冗余的工具输出或消息。此后，智能体就可以带着这份压缩后的上下文，加上最近访问过的五个文件，继续工作。用户能够获得连续性，而不必担心上下文窗口的限制。

压缩的技艺在于取舍：哪些该保留，哪些该舍弃，因为过度激进的压缩可能导致丢失一些细微但关键的上下文，而这些上下文的重要性往往要到后来才会显现出来。对于正在构建压缩系统的工程师，我们建议在复杂的智能体轨迹上仔细调优你的提示词。先从最大化召回率开始，确保你的压缩提示词能捕捉到轨迹中每一条相关的信息，然后再通过剔除多余内容来迭代提升精确率。

一个容易识别的多余内容的例子，就是清除工具调用及其结果——一旦某个工具在消息历史中被调用过、且时间已经比较久远，智能体又为什么需要再次看到那次调用的原始结果呢？其中一种最安全、最轻量的压缩形式，就是清除工具调用结果，这项功能最近作为 [Claude 开发者平台的一项功能](https://www.anthropic.com/news/context-management)正式发布。

**结构化笔记记录**

结构化笔记记录，也称为智能体式记忆（agentic memory），是一种让智能体定期把笔记写入上下文窗口之外的持久化存储的技巧。这些笔记会在之后的时间点被重新拉回上下文窗口。

这种策略以极低的开销提供了持久化的记忆能力。就像 Claude Code 会创建一份待办事项清单，或者你自定义的智能体维护一份 NOTES.md 文件那样，这种简单的模式能让智能体在处理复杂任务时跟踪进展，保留那些原本会在数十次工具调用中丢失的关键上下文和依赖关系。

[Claude 打宝可梦](https://www.twitch.tv/claudeplayspokemon)这个项目展示了记忆能力如何在非编程领域改变智能体的能力。这个智能体能在成千上万个游戏步骤中维护精确的计数——追踪像"在过去 1,234 步里，我一直在 1 号道路训练我的宝可梦，皮卡丘已经朝着 10 级的目标提升了 8 级"这样的目标。在完全没有关于记忆结构的提示的情况下，它自主构建出了已探索区域的地图，记住了自己已经解锁的关键成就，并维护着战斗策略方面的战术笔记，帮助它了解哪些招式对不同的对手最有效。

在上下文重置之后，智能体会读取自己之前写下的笔记，继续进行长达数小时的训练序列或地下城探索。这种跨越摘要步骤的连贯性，使得那些如果只依靠 LLM 自身上下文窗口来保存全部信息就根本无法实现的长时程策略变为可能。

作为我们[发布 Sonnet 4.5](https://www.anthropic.com/effective-context-engineering-for-ai-agents) 的一部分，我们在 Claude 开发者平台上发布了公开测试版的[记忆工具](http://anthropic.com/news/context-management)，它通过一套基于文件的系统，让在上下文窗口之外存储和查阅信息变得更加容易。这使得智能体能够随着时间推移建立起知识库，在多个会话之间维护项目状态，并在不需要把所有内容都保留在上下文中的情况下，引用此前的工作成果。

**子智能体架构**

子智能体架构提供了另一种绕开上下文限制的方式。与由单个智能体试图在整个项目范围内维护状态不同，专职的子智能体可以用干净的上下文窗口来处理聚焦的任务。主智能体负责协调一份高层次的计划，而子智能体则执行深入的技术性工作，或使用工具查找相关信息。每个子智能体都可能进行大量的探索，消耗数万甚至更多的 token，但最终只返回一份经过浓缩、提炼的工作总结（通常只有 1,000 到 2,000 个 token）。

这种方式实现了清晰的关注点分离——详细的搜索上下文始终被隔离在子智能体内部，而主智能体则专注于综合分析这些结果。这种模式在[《我们如何构建多智能体研究系统》](https://www.anthropic.com/engineering/multi-agent-research-system)一文中有过讨论，事实证明它在复杂研究任务上相比单智能体系统有着显著的提升。

在这几种方式之间做选择，取决于任务本身的特性。例如：

* 压缩适合维持需要大量来回交互任务的对话流；
* 笔记记录在具有明确里程碑的迭代式开发中表现出色；
* 多智能体架构则适合处理复杂的研究与分析工作，这类工作中并行探索能带来切实的收益。

即使模型能力持续提升，如何在延长的交互过程中保持连贯性，这一挑战仍将是构建更高效智能体的核心所在。

## 五、结语

上下文工程代表着我们构建 LLM 应用方式的一次根本性转变。随着模型能力的增强，真正的挑战已不再仅仅是打造完美的提示词——而是审慎地筛选，在每一步该让哪些信息进入模型有限的注意力预算。无论你是在为长时程任务实现压缩，设计具备 token 效率的工具，还是让智能体能够即时探索其所处的环境，其指导原则始终如一：找到能够最大化实现预期结果可能性的那个最小高信号 token 集合。

我们在本文中概述的这些技巧，将随着模型的改进而持续演变。我们已经观察到，更聪明的模型需要的规定性工程投入更少，这让智能体能够以更高的自主性运作。但即便能力持续扩展，把上下文当作一种珍贵而有限的资源来对待，仍将是构建可靠、高效智能体的核心所在。
