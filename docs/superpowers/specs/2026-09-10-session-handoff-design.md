## 背景

Claude Code / Codex 的每个新会话对之前发生的一切一无所知。context 压缩能延续单次会话的连贯性，但**关不掉的窗口边界依然存在**：换一天、换一台机器、换 harness，上下文一律归零。

任务跨多个会话时（本仓的知识库三领域扩建跨五个阶段、门禁迁移跨两个会话，都是实例），现有载体各有缺口：

| 现有载体 | 记录什么 | 缺什么 |
|---|---|---|
| `git log` | 做了什么（已落盘的结果） | 为什么这么选、放弃过什么、下一步打算做什么 |
| 待办清单（`docs/todo-list/`） | 待办条目 | 无上下文，"session-handoff" 五个字看不出要做成什么样 |
| harness 的 memory 机制 | 跨会话恒真的事实 | 单条一事，不承载「某个任务当前进行到哪一步」 |
| CHANGELOG / known-issues | 已完成的变更、已发现的缺陷 | 只覆盖产物自身，不覆盖会话级的进行状态 |

本 skill 补的正是中间那层：**任务级的会话交接**——下一个会话（或下一个人、下一个 harness）读完就能接着干。

这是跨领域的通用需求，与具体技术栈无关，因此作为独立插件对外发布。

## 参照实现与本 skill 的取舍

`fltrp-session-handoff` v2.1.0 是本 skill 的直接参照，逐项对照如下。**✅ 采纳 / 🔄 改造 / ❌ 不采纳**三档，每档都给出理由——不采纳的部分同样重要，它标出了两个仓库环境的真实差异。

| # | fltrp 机制 | 处置 | 理由 |
|---|---|---|---|
| 1 | 三层分职责交接物（progress / summaries / conversations） | ✅ 采纳结构 | 「做了什么 / 为什么 / 别处装不下的」三层职责划分是参照实现最有价值的部分，压成单文件会让恢复时无法按需只读一层 |
| 2 | 第三层记「逐轮对话记录」 | 🔄 改造为「习得与踩坑」 | 逐轮记录依赖静默追写才成立，见「决策 2」 |
| 3 | 按 `git config user.name` 隔离 | ✅ 采纳，但运行时判定 | 见「决策 3」 |
| 4 | 按 git 分支粒度建目录 | ✅ 采纳 | 分支是任务的天然边界，参照实现在这点上是对的 |
| 5 | 待办队列四档优先级（🔴🟡🔵⏸️） | ✅ 采纳 | 符号在终端视觉区分度高，阻塞项单列能避免下轮反复尝试做不了的事 |
| 6 | ⏸️ 阻塞项附原因 | ✅ 采纳并升为硬约束 | 不写原因等于没写，下轮还要重新排查 |
| 7 | 待办队列 7 种写入场景检查清单 | ✅ 采纳 | 这是参照实现里最容易被忽略的好东西：把「有没有漏记待办」变成可逐项核对的清单，而非凭感觉 |
| 8 | HARD-GATE 前置校验 | ✅ 采纳 | 与本仓 skill 的「执行前置校验」惯例一致 |
| 9 | 目录完整性静默修复 | ✅ 采纳 | 缺什么建什么、不中断，兼容老版本目录结构 |
| 10 | 每轮静默追写 | ❌ 不采纳 | 见「决策 2」 |
| 11 | 上下文告急自动保存 | ❌ 不采纳 | 判定标准（"处理超过 10 个文件"）是代理指标，与真实剩余上下文无关；且本 skill 无法读取 harness 的上下文余量 |
| 12 | 交接物自动 `git commit` | ❌ 不采纳 | 本仓有专属提交流程（`commit-cc-plugin`），代为提交会绕过它。见「决策 4」 |
| 13 | `init.sh` 环境启动脚本 | ❌ 不采纳 | 参照实现的四平台检测（Flutter/Android/iOS/HarmonyOS）绑定其客户端技术栈。本仓与通用用户的环境启动方式无法枚举，猜错比不做更糟 |
| 14 | `feature_list.json` 功能清单 | ❌ 不采纳 | 参照实现自己已在 v2.0.0 删除它（"对单人 main 分支场景无用，由 progress 待办队列替代"）——直接采纳其结论，不重走一遍 |
| 15 | `artifacts.json` 产物注册 | ❌ 不采纳 | 消费方是 fltrp 的 `tech-spec-generator` / `client-dev-pipeline` 流水线，本仓无此流水线 |
| 16 | `pitfalls.md` → code-linter 闭环 | ❌ 不采纳 | 本仓对等物是 `knowledge-base/` 与各 skill 的 `known-issues.md`，已有归属。踩坑改为落在第三层交接物内 |
| 17 | stop hook（session-guard） | ❌ 不采纳 | 见「决策 5」 |
| 18 | 恢复后按待办队列直接开工 | 🔄 改为复述后停下 | 见「决策 6」 |
| 19 | 独立 `agents/*.md` 双 agent | ❌ 不采纳 | 两个 agent 的 prompt 内容与 SKILL.md 的两模式高度重复。本仓 agent 的定位是「需与主对话上下文隔离的判定类任务」，交接恰恰需要主对话的上下文 |

**一句话概括取舍**：**结构照搬（三层分职责 + 分支 × 用户名 + 待办队列四档），联动机制全不采纳（init.sh / feature_list / artifacts / pitfalls / hook），写入时机与恢复后行为按本仓风格改造。**

## 设计决策

### 决策 1：三层分职责，不压缩为单文件

采纳参照实现的三层结构，每层回答一个不同的问题：

| 层 | 回答什么问题 | 恢复时的用途 |
|---|---|---|
| `progress` | **做了什么 + 接下来做什么** | 恢复的主入口，读它就能开工 |
| `summaries` | **为什么这么选** | 要改动上轮的决定时读，避免推翻已论证过的选择 |
| `insights` | **别处装不下的：习得、踩坑、已核验的事实** | 避免重蹈覆辙、避免重做已验证过的事 |

**为什么不压成单文件**：恢复时三层的读取必要性不同。日常恢复只需 `progress`；只有当要改动上轮决定时才需 `summaries`。压成单文件后每次恢复都得读全部内容，而这恰恰是交接物要解决的问题（上下文有限）的反向操作。

**为什么第三层叫 `insights` 而不是 fltrp 的 `conversations`**：见决策 2。

### 决策 2：仅显式触发，第三层随之改为「习得」而非「逐轮对话」

参照实现 v2.0.0 的核心改动是「静默保存」——每轮有实质产出就自动追加 `conversations`，其 CHANGELOG 明确写了动机：*"解决 conversations 记录丢失问题（根因：保存策略过于被动）"*。

**本 skill 仍不采纳**，两个理由：

1. **判定不可靠**——"有实质产出"由 LLM 自评。参照实现给的判据是"创建/修改文件、技术决策、分析代码、修复 Bug"，但"分析代码并给出建议"与"纯问答"的边界完全依赖当次判断，标准必然漂移
2. **产生碎改动**——每轮写盘会让 `git status` 长期不干净，与本仓 `commit-cc-plugin` 第二步的原子性自查直接冲突（那一步要求确认"是否混入无关变更"，而每轮追写的交接物永远是"无关变更"）

**连带后果（这是本次重写的关键推论）**：`conversations` 层的定位是逐轮记录「用户意图 → AI 行动 → 产出 → 本轮总结」，**它依赖静默追写才成立**——那是逐轮增量累积的产物。仅显式触发时，到会话末尾一次性回溯补写全部轮次有两个问题：

- **不可靠**：早期轮次多已被 context 压缩，凭残留印象重编等于编造
- **无价值**：即使写出来也是压缩后的二手信息，不如直接看 `git log` + `summaries`

因此第三层改为 **`insights`——本轮习得、踩坑、已核验通过的事实**。它同样是 `progress`/`summaries` 装不下的内容，但**会话末尾能一次性可靠写出**（它是结论而非过程）。

> 📌 该改造有实践依据：本仓已有的两份手写交接物（`2026-08-29-*`，已被本次重写删除，可从 `d945234` 回溯）中就有「本轮新习得的教训」与「已机械核验通过的事实（下轮不必重做）」两段，且后者直接省下一整轮重复劳动。手写实践先于 spec 验证了这个维度的价值。

⚠️ **不可兼得**：若将来要严格的逐轮对话记录，必须同时改回静默追写。两者是一对，不能只取其一。

### 决策 3：分支 × 用户名做成运行时**推导规则**，而非固定层级

采纳参照实现的「分支 × 用户名」隔离维度，但**每次运行实测、按需退化**，不写死目录层级。

参照实现固定为 `docs/sessions/{分支}/{层}/{user}.ext`，因为它的原生场景是多人 feature 分支的业务仓库。本 skill 对外发布，落地环境差异极大：

| 环境 | 分支 | 协作者 | 合适的路径 |
|---|---|---|---|
| 业务仓库（fltrp 原生场景） | 多 feature 分支 | 多人 | `docs/sessions/feat-x/progress/anyu.md` |
| 单人插件仓（如本仓） | 长期 master | 1 人 | `docs/sessions/<date>-<slug>/progress.md` |

固定写死 `{branch}/{user}` 会让后者得到 `docs/sessions/master/progress/anyu.md`——两段各只有一个取值，纯噪音。反过来只按日期又会让前者的多人交接物互相覆盖。

**规则表达维度，运行时决定是否展开**。详见「三、交接物路径」。

### 决策 4：不自动提交

参照实现的 Initializer 第 6 步直接 `git commit` 交接物。**本 skill 只写文件，报告路径，不提交。**

理由是本仓有专属提交流程（`commit-cc-plugin`，AGENTS.md 明确"禁止手动执行 git 工作流"），代为提交会绕过它。对外部用户同理——很多仓库有自己的提交规范、pre-commit 门禁、commit message 格式，代为提交等于替用户做了一个他没授权的决定。

交接物是否入库、何时入库、用什么 message，全部交给用户。

### 决策 5：不做 stop hook

参照实现有 `session-guard.sh`：检测到回复中含 git commit 相关字样时，检查该 commit 是否包含交接物文件，缺失则 stderr 提醒。

**不采纳**，三个理由：

1. **本仓 hook 的对等位置是 `.githooks/pre-commit`**，而交接物是否更新**不适合做阻断**——它不是仓库一致性问题，漏写只影响下次接手效率
2. **检测手段是正则匹配 assistant 回复文本**（`grep -qiE "(git commit|已提交|committed)"`），这类基于自然语言输出的触发极易误报与漏报
3. **Codex 侧无对应机制**（AGENTS.md 已列明"Claude 侧 hooks 在 Codex 中不生效"），做了就是单 harness 特性，违反"单一真源，两个 harness 共用"

### 决策 6：恢复后复述并停下，不直接开工

参照实现的 Coder 模式 Step 5 是「读 progress 末尾待办队列，按 🔴>🟡>🔵 顺序执行，⏸️ 跳过」——**读完直接开工**。

**本 skill 改为复述三件事后停下等指令。** 理由是交接物里的「下一步」是上个会话的判断，而两个会话之间可能发生了任何事：需求变了、优先级调了、别人已经把那件事做了。直接开工的期望收益（省一轮确认）远小于跑错方向的成本（做完才发现不该做）。

参照实现能这么设计，是因为它的上游是 `client-dev-pipeline` 自动化流水线，交接物的消费者是流程而非人。本 skill 的消费者是人，人会改主意。

## 一、定位与产物形态

**层级**：`plugins/optimus-session-plugin/skills/session-handoff/`——**对外发布的插件产物**，不是本仓自用 skill。

### 为什么新建独立插件而非并入 optimus-devops-plugin

`optimus-devops-plugin` 装的是 Jenkins 构建、项目分析、周报、符号链接同步、.NET 取证——都绑定「某条具体的运维/交付动作」。会话交接是**跨领域的基础能力**：写 WPF 的人要交接，写 PRD 的人也要交接。挂在 DevOps 下会让另外八个领域的用户找不到它。

代价明确并接受：marketplace 顶层版本需升 Minor，且要独立维护两份 `plugin.json`。

### 无本仓自用副本

本仓开发时直接用发布版 `/optimus-session-plugin:session-handoff` 调用，**不在 `.claude/skills/` 另存副本**。两份内容必然逐渐分叉，违反 `AGENTS.md`「单一真源」原则。

因此**不需要** `.kiro/skills/` 与 `.agents/skills/` 符号链接——那两处只镜像 `.claude/skills/` 下的自用 skill，`plugins/` 下的产物由各 harness 的插件安装机制分发。

### 文件构成

```
plugins/optimus-session-plugin/
├── .claude-plugin/plugin.json     # Claude 侧清单
├── .codex-plugin/plugin.json      # Codex 侧清单（含 interface 段）
└── skills/session-handoff/
    ├── SKILL.md                   # 主流程，目标 ≤ 180 行
    ├── references/templates.md     # 三层交接物的完整模板
    ├── README.md                   # skill 级 README，六章节
    ├── CHANGELOG.md
    └── test-prompts.json           # 触发与边界测试用例
```

**设 `references/templates.md`**——这是与旧版设计的一处改动。三层交接物各有独立模板（含 frontmatter、段落结构、示例），全部内联会把 SKILL.md 推到 300 行以上，超出本仓 skill 的合理体量。参照实现正是因同样原因在 v2.0.0 把模板外移（SKILL.md 662 → 342 行）。

**不设插件根 README**——9 个现有插件中 8 个没有（唯一有的 `optimus-mcp-servers` 不含 skill），那一层无此惯例。`doc-conventions.md` 的六章节规范是对 skill 级 README 的要求。

**不设 `known-issues.md`**——那是本仓自用 skill 的惯例（`.claude/skills/*/`），发布产物用 CHANGELOG 记录演进。

### 版本号

按 `AGENTS.md` 触发矩阵，本次改动同时落在四处：

| 层级 | 动作 |
|---|---|
| `plugins/optimus-session-plugin/.claude-plugin/plugin.json` | 新插件起 `1.0.0` |
| `plugins/optimus-session-plugin/.codex-plugin/plugin.json` | 同上，同值 |
| `SKILL.md` 的 `metadata.version` | 起 `1.0.0` |
| `.claude-plugin/marketplace.json` 顶层 | 升 Minor（新增插件） |

⚠️ marketplace 顶层的具体新值**实施时读实际文件确定**，不在 spec 里写死——spec 到实施之间可能有其他插件增删。

⚠️ marketplace 的**插件条目内不写 `version`**——会被 `plugin.json` 静默覆盖，且本仓条目 `source` 为本地路径时官方还会报不一致警告。

## 二、Frontmatter

遵循 `.claude/rules/skill-conventions.md` 的六字段规范：

```yaml
---
name: session-handoff
description: 跨会话交接工作时使用。会话结束前保存交接物（进度与待办、关键决策、习得与踩坑三层），或新会话开始时恢复上次进度。触发场景：用户说"交接"、"保存进度"、"handoff"、"要下班了"、"继续上次的工作"、"接着干"、"上次做到哪了"、"恢复进度"。
metadata:
  version: "1.0.0"
  author: optimus
  category: workflow
compatibility: 需要 Git 仓库环境；无 MCP 或第三方 CLI 依赖。
allowed-tools: Bash Read Write Edit Glob Grep
---
```

**调用方式**：Claude 侧 `/optimus-session-plugin:session-handoff`，Codex 侧按 description 自然语言匹配或 `@optimus-session-plugin:session-handoff`。`name` 字段本身不带插件前缀——前缀由 harness 按所属插件自动加。

**`allowed-tools` 说明**：`Write`/`Edit` 写三层交接物，`Read`/`Glob`/`Grep` 读回历史交接物与相关代码，`Bash` 取 git 状态。**不含** `Task`/`Agent`——本 skill 不拉起子 agent（对照表 #19）。

⚠️ **不采纳参照实现的 frontmatter 格式**。它用的是 `name`/`version`/`description`/`author`/`tags`/`category` 平铺结构，而本仓规范要求 `metadata` 嵌套 + `compatibility` + `allowed-tools`。两个harness 都会原样读取缓存 frontmatter，格式必须按本仓规范，不能照抄参照实现。

## 三、交接物路径

### 推导规则

```
docs/sessions/[<branch>/]<YYYY-MM-DD>-<slug>/<层>[.<user>].md
```

三层文件固定为 `progress.md` / `summaries.md` / `insights.md`，两个可选段按实测退化：

| 段 | 何时出现 | 何时省略 | 判定命令 |
|---|---|---|---|
| `<branch>/` | 当前分支 ≠ 远端默认分支 | 在默认分支上工作时 | `git symbolic-ref refs/remotes/origin/HEAD` |
| `.<user>` | 提交者去重后 > 1 人 | 单人仓库 | `git log --format=%an \| sort -u \| wc -l` |

**默认分支的判定**：取 `git symbolic-ref refs/remotes/origin/HEAD` 的输出，取不到（如无 origin）则回退为「当前分支就是默认分支」，即省略该段。**不要硬编码 `master` 或 `main`**——两者在真实项目中都常见，写死会给另一半用户凭空多一层目录。

多人业务仓库上的典型形态：

```
docs/sessions/feat-coupon-stacking/2026-09-10-api-contract/
├── progress.anyu.md
├── summaries.anyu.md
└── insights.anyu.md
```

单人插件仓（如本仓）退化为：

```
docs/sessions/2026-09-10-session-handoff-impl/
├── progress.md
├── summaries.md
└── insights.md
```

⚠️ **判定必须每次实测，不得缓存或写死**：分支用 `git rev-parse --abbrev-ref HEAD`。假定"这个仓库是单人的"会在有人加入的当天静默产生文件覆盖。

### 与参照实现的路径结构差异

参照实现是 `docs/sessions/{分支}/{层}/{user}.ext`——**层在中间、按人分文件**。本 skill 是 `docs/sessions/[分支/]{任务}/{层}[.user].md`——**任务在中间、层是文件名**。

| | 参照实现 | 本 skill |
|---|---|---|
| 目录粒度 | 一分支一目录 | 一**任务**一目录 |
| 层的位置 | 中间目录 | 文件名 |
| 隐含假设 | 一个分支 = 一个任务 | 一个分支可有多个任务 |

**为什么改**：参照实现的 `progress/{user}.txt` 是单文件无限追加、恢复时 `tail -30`，隐含「一分支一任务」假设。该假设在两种常见情形下不成立：

- **同一分支跨多个不相干任务**——尤其长期停留在主干的仓库（本仓正是），所有内容会挤进一个越来越长的文件
- **同一天并行推进两件事**——混进一个文件后恢复时要人工筛

一任务一目录、目录名带日期与主题 slug，恢复时按目录名直接选。代价是目录数量增长，靠日期前缀自然排序、`ls -t` 取最近即可。

**同时也解决了参照实现一个未处理的问题**：它的 `progress/{user}.txt` 会无限增长而无归档机制（其"分支生命周期"一节只说合并后目录"归档保留"，但文件本身仍是单个大文件）。按任务分目录天然限定了单文件体量。

### slug 命名

取本次会话的**任务主题**，kebab-case，3-5 个词。不是日期的重复、不是"session-1"这类序号——序号无信息量，恢复时看不出该读哪个。

### 追加语义：同一任务的第二次交接

同一任务跨多个会话时，**目录不变，三层文件各自追加一个会话块**（参照实现的追加语义，采纳）：

```markdown
## 会话 2 — 2026-09-11

...
```

`progress.md` 的「待办队列」是例外——**它整段覆写而非追加**，因为待办是当前状态而非历史。上轮做完的项从队列消失，是队列本身在演进。

⚠️ 这条区分是参照实现里隐含但未写明的地方：它的 progress 每个 Session 块各带一份待办队列，恢复时 `tail -30` 只读末尾那份。本 skill 明确写成「队列覆写、其余追加」，避免读者误以为要保留历次队列快照。

## 四、两种模式

skill 被触发后先判定模式，不询问用户：

| 用户意图 | 模式 |
|---|---|
| "交接"、"保存进度"、"handoff"、"要下班了" | **保存** |
| "继续上次的"、"接着干"、"上次做到哪了"、"恢复进度" | **恢复** |
| 无法判定 | 询问，二选一 |

⚠️ **不采纳参照实现的「目录存在性判定模式」**。它按 `docs/sessions/{分支}/` 是否存在来决定进 Initializer 还是 Coder——这在本 skill 的路径结构下会误判：目录已存在但用户这次是要**保存新一轮**，不是恢复。**模式必须按用户意图判定，不按文件系统状态。**

### 模式 A：保存

#### 前置校验（HARD GATE）

采纳参照实现的 HARD-GATE 形式，四项：

| # | 检查 | 不通过时 |
|---|---|---|
| 1 | `git rev-parse --is-inside-work-tree` | 终止，提示"请在 Git 仓库中使用本 skill" |
| 2 | `git rev-parse --abbrev-ref HEAD` 取分支 | 为空则终止，提示配置 Git |
| 3 | 读 `references/templates.md` | 找不到则用 SKILL.md 内置的简化模板降级执行，**不终止** |
| 4 | `git status --short` | **不阻断**，但有未提交改动时须记入 `progress.md` |

第 3 项的降级设计来自参照实现（"找不到则使用 SKILL.md 内置规则降级执行"）——模板缺失不该让整个交接失败。

第 4 项**不阻断但必须记录**：下一个会话会看到一个脏工作区，需要知道那些改动是什么、为什么没提交。参照实现未处理这种情况。

⚠️ **不采纳参照实现的第 5 项「目录完整性静默修复」的具体做法**——它 `mkdir -p` 三个固定子目录来兼容老版本结构。本 skill 是新产物无历史包袱，写文件时 `mkdir -p` 任务目录即可，不需要单列一项检查。

#### 采集（全部只读，不猜测）

```bash
git rev-parse --abbrev-ref HEAD          # 分支
git log --oneline -10                    # 本次会话的落盘结果
git status --short                       # 未完成的工作区状态
git log origin/<默认分支>..HEAD --oneline # 未推送的提交
```

⚠️ 末条的默认分支名来自路径推导时已取到的值，**不要硬编码 `origin/master`**。

#### 三层内容的核心约束

> **不重复其他产物已记录的内容。** 代码改动看 `git diff`、变更历史看 CHANGELOG、已知缺陷看 known-issues.md、跨会话恒真事实看 harness memory。交接物只写这些地方**没有**的东西。

⚠️ 这条是本 skill 最容易失守的地方。把 `git log` 抄一遍很容易，且看起来很充实，但对下一个会话零价值——它自己会跑 `git log`。

参照实现的 Red Flag 里有对应的一条（"progress 写成流水账'做了一些工作'"），但它约束的是**粒度**（要具体到文件名）；本 skill 这条约束的是**归属**（该由 git 记录的就不要写进来）。两条都要，不是一回事。

#### 收尾输出

写完后向用户报告三个文件路径，并附一行入库提示：

```
交接物已写入 docs/sessions/<任务目录>/（progress / summaries / insights 三份）。
如不希望它进入版本库，可将 docs/sessions/ 加入 .gitignore。
```

**不自动提交**（决策 4）。交接物是否入库、何时入库由用户决定。

### 模式 B：恢复

#### 定位交接物

```bash
ls -dt docs/sessions/*/ docs/sessions/*/*/ 2>/dev/null | head -5
```

按修改时间倒序列出最近 5 个任务目录。**多于一个时必须让用户选**，不要默认取最新——同一天可能有多个任务，猜错会让整个会话跑偏。仅一个时直接读。

#### 分层读取顺序（这是三层结构的主要收益）

```
1. progress.md          ← 必读。做了什么 + 待办队列
2. insights.md          ← 必读。已核验的事实（避免重做）+ 踩坑（避免重踩）
3. summaries.md         ← 按需。仅当要改动上轮决定时才读
4. progress.md 的「引用」段列出的路径
5. git log --oneline -10  ← 对照交接物写入后是否有新提交
```

第 5 步发现有新提交 → 说明交接物已过时，须提示用户。

⚠️ **`summaries.md` 标为「按需」是三层拆分的意义所在**。若每次恢复都读全三层，拆分只是多了两次文件读取而无收益。判据：本次是要「继续推进」（不读）还是「改动上轮的决定」（读）。

#### 恢复后动作

向用户复述三件事，然后**停下等指令**（决策 6）：

- 上次进行到哪一步
- 下一步待办（按 `progress.md` 待办队列的优先级）
- 有无阻塞项（⏸️ 项及其原因）

⚠️ **不要读完就自动开工**。交接物里的"下一步"是上个会话的判断，用户的实际意图可能已经变了。

## 五、三层交接物模板

完整模板落在 `references/templates.md`，此处定义结构与取舍规则。

### 第一层：`progress.md` — 做了什么 + 接下来做什么

```markdown
---
task: <任务主题>
date: <YYYY-MM-DD>
branch: <分支名>
status: 进行中 | 已完成 | 已搁置
---

# <任务主题> · 进度

## 会话 N — <YYYY-MM-DD>

### 当前状态
<2-4 句。这个任务要达成什么、现在到了哪一步。让人读完知道自己接手的是什么。>

### 已完成
- <具体到文件名和产物。不是 commit message 的复述>

### 工作区状态
<仅当 git status 非空时出现：哪些文件有未提交改动、为什么没提交>

---

## 📋 待办队列（整段覆写，非追加）

- 🔴 <必须优先做的>
- 🟡 <应该尽快做的>
- 🔵 <有空再做的>
- ⏸️ <阻塞项> — 阻塞原因：<原因>

## 引用

- <路径或 URL> — <这里面有什么>
```

**待办队列的位置刻意在文件末尾**——采纳参照实现的做法，它的 Coder 模式用 `tail -30` 读队列。放末尾意味着即使文件很长，读末尾就能拿到工作清单。

#### 待办队列写入检查清单（完整采纳参照实现，7 项）

这是参照实现里最容易被低估的部分：它把「有没有漏记待办」从凭感觉变成可逐项核对。会话结束时逐项自查：

| # | 检查 | 命中则 |
|---|---|---|
| 1 | 多步任务未做完？ | 剩余步骤入列 |
| 2 | 有分流的中/低优先级未执行？ | 入列 |
| 3 | 用户说"先不做"的？ | 入列 + 注明原因 |
| 4 | 分析出问题但只修了部分？ | 未修的入列 |
| 5 | `summaries.md` 中有可执行的遗留风险？ | 入列 |
| 6 | 依赖外部未就绪？ | ⏸️ 入列 + 阻塞原因 |
| 7 | 代码审查发现问题但未修？ | 入列 |

⚠️ **第 3 项与第 6 项必须附原因**。「先不做」不写原因，下轮会重新提议一次；⏸️ 不写原因，下轮会重新排查一遍才知道为什么卡住。

### 第二层：`summaries.md` — 为什么这么选

```markdown
---
task: <任务主题>
date: <YYYY-MM-DD>
---

# <任务主题> · 决策与权衡

## 会话 N — <YYYY-MM-DD>

### 关键决策
- **<决策>**：<为什么这么选>

### 方案权衡
- **放弃的方案**：<方案>
  **放弃原因**：<原因>

### 遗留风险
- <已知但未处理的风险点>

### 待验证的假设
- <当前基于什么假设在推进，这个假设怎么验证>
```

四个维度中 **`方案权衡` 是参照实现的贡献**（本仓旧版设计漏了它）——记录「考虑过但放弃了什么」，能防止下个会话把已经论证过不可行的方案重新提一遍。这是纯增量价值，git 与 CHANGELOG 都不会记录被放弃的方案。

`待验证的假设` 是本 skill 相对参照实现的补充：参照实现有「遗留风险」（已知的坏事）但没有「待验证的假设」（尚不知好坏的前提）。两者性质不同——风险是要防的，假设是要验的。

⚠️ **不采纳参照实现的「技术洞察」维度**——它记录「API 行为、框架特性」这类内容，本仓的对等归属是 `knowledge-base/`（可被 skill 检索的规范条款）。写进交接物会让它随任务结束一起变成历史，而框架特性是长期有效的知识。**归属错了的信息等于丢了。**

### 第三层：`insights.md` — 别处装不下的

```markdown
---
task: <任务主题>
date: <YYYY-MM-DD>
---

# <任务主题> · 习得与核验

## 会话 N — <YYYY-MM-DD>

### ✅ 已核验通过的事实（下轮不必重做）
- <做过什么验证、结论是什么、用什么命令可复现>

### 🕳️ 踩坑记录
- **现象**：<你会观察到什么>
  **根因**：<为什么>
  **绕过/修复**：<怎么解决的>
  **归属判定**：<是否该沉淀到 knowledge-base / known-issues，还是仅本任务相关>

### 💡 本轮习得
- <这一轮真正学到的、且不属于以上任何一类的东西>
```

**「已核验通过的事实」是三层里价值密度最高的一段**，也是参照实现完全没有的维度。它直接省下一整轮重复劳动：下个会话看到"483 条记录已全量校验通过、命令是 `python xxx.py`"，就不必重跑一遍再确认。

**「踩坑记录」的 `归属判定` 字段是对参照实现的改造**。参照实现的踩坑走 `pitfalls.md` → `code-linter` 闭环自动沉淀（本 skill 不采纳，决策/对照表 #16），改为**在交接物里标注归属、由人决定是否搬走**。理由是自动沉淀会往知识库塞进大量仅对单个任务有效的内容，而 `knowledge-base/` 的定位是「被 skill 编程式检索的规范条款」，混入一次性内容会污染检索结果。

### 各段的取舍规则

| 层 | 段 | 必填 | 空了怎么办 |
|---|---|---|---|
| progress | 当前状态 | ✅ | 不能空。写不出来说明这次会话没有可交接的东西，应告知用户无需交接 |
| progress | 已完成 | ✅ | 同上 |
| progress | 待办队列 | ✅ | 若确实全部做完，写「已完成，无后续」并把 `status` 标为 `已完成` |
| progress | 工作区状态 | ❌ | `git status` 为空时整段删除 |
| progress | 引用 | ❌ | 整段删除 |
| summaries | 四个维度 | ❌ | 逐段判断，空则整段删除；**四段全空则整个文件不创建** |
| insights | 三个维度 | ❌ | 同上，**三段全空则整个文件不创建** |

⚠️ **维度可以为空，但不要凑数**。写"（无）"占位比删掉更糟——下一个会话要花时间确认这个"无"是真没有还是忘了写。

⚠️ **`summaries.md` / `insights.md` 允许整个文件不存在**，这是三层结构必须明确的一点：一次纯执行性的会话（照着既定计划做完、无决策无踩坑）只产出 `progress.md` 是正常的。**强制凑齐三个文件会让后两个充满空洞内容，反而降低下轮的信噪比。**

参照实现在这点上是硬性的（Red Flag 明确写"只更新 progress 不写 summary"是错的），本 skill 放宽——因为它的场景是长周期客户端开发（几乎每轮都有技术决策），而本 skill 面向的场景包含大量纯执行会话。

### 优先级标识

沿用参照实现的四档（🔴高 / 🟡中 / 🔵低 / ⏸️阻塞）。理由是这套符号在终端里视觉区分度高，且阻塞项单列一档能避免下个会话反复尝试一件根本做不了的事。

**⏸️ 必须附阻塞原因**——参照实现的 Red Flag 已列明，本 skill 升为硬约束。

## 六、Red Flags

前五条承自参照实现（标 ⬅️），后七条是本 skill 新增：

| 错误做法 | 正确做法 |
|---|---|
| ⬅️ progress 写成流水账"做了一些工作" | 具体到文件名和功能点："给 check_plugin_versions.py 补了 symlink mode 的 12 个用例" |
| ⬅️ 会话结束不写待办队列 | 有未完成任务必须入列，否则下轮无法衔接。按 7 项检查清单逐条自查 |
| ⬅️ 待办队列不标优先级 | 必须用 🔴🟡🔵⏸️ 标注，否则下次不知道先做什么 |
| ⬅️ ⏸️ 阻塞项不写原因 | 必须附「阻塞原因」，否则下次要重新排查 |
| ⬅️ 上下文告急还在写代码，留下半成品 | 感知到接近上限时主动提议交接（**提议，不自动执行**——决策 2） |
| 把 `git log` 内容抄进「已完成」 | 下个会话自己会跑 `git log`。写 git 里看不到的：为什么这么改、试过什么没成 |
| 「待办」写成"继续完善 XXX" | 具体到可执行的动作："给 check_plugin_versions.py 补 symlink mode 的测试用例" |
| 交接物写完顺手 `git commit` | 只写文件，报告路径。入不入库由用户定（决策 4） |
| 恢复模式读完交接物直接开工 | 复述三件事后停下等指令（决策 6） |
| 多个交接物时默认取最新 | 让用户选。同一天可能有多个不相干的任务 |
| 为了让三层"齐全"给空维度写"（无）"或强行创建空文件 | 空维度整段删除；`summaries`/`insights` 全空则整个文件不创建 |
| 把框架特性、API 行为写进 `summaries` | 那是 `knowledge-base/` 的内容，随任务结束变成历史等于丢了。交接物只装任务级的进行状态 |
| 单人仓库硬编码不带 `.user` 后缀 / 硬编码 `master` | 每次实测 `git log --format=%an \| sort -u \| wc -l` 与 `git symbolic-ref` |

## 七、与其他 skill / 机制的边界

### 跨插件无重复（AGENTS.md 硬约束）

发布前须确认无跨插件重叠。现有 38 个 skill 中唯一需要辨析的是 `optimus-devops-plugin:weekly-report`：

| | weekly-report | session-handoff |
|---|---|---|
| 输出面向 | **人**（主管读的周报） | **下一个会话**（恢复用） |
| 时间范围 | 一周 | 单个任务（可跨多会话） |
| 内容取向 | 已完成的成果，总结性 | 未完成的下一步，前瞻性 |
| 数据来源 | git log + 对话 | 会话内的判断与决策（git 里看不到的） |

两者都读 git log，但产出的信息类型正交——周报不写"待办队列的优先级"，交接物不写"本周工时分布"。**判定：不重叠**。

### 与本仓其他机制的关系（用户侧同理）

| 对象 | 关系 |
|---|---|
| 提交类 skill（本仓 `commit-cc-plugin`） | **不重叠**。本 skill 写文件不提交；提交仍须显式触发（决策 4） |
| harness memory 机制 | **互补**。memory 存「跨会话恒真的事实」（用户偏好、项目约束），交接物存「某个任务当前的进行状态」。任务完成后交接物成为历史，memory 条目继续有效 |
| 待办清单（`docs/todo-list/`） | **互补**。待办清单是跨任务的条目列表（"要建 session-handoff skill"），交接物的待办队列是单任务内的剩余步骤 |
| 规范知识库（`knowledge-base/`） | **不重叠但有搬运关系**。`insights.md` 的踩坑带「归属判定」字段，判定为通用规范的由人搬进知识库 |
| 提交门禁（`.githooks/pre-commit`） | **无关**。交接物是否更新不做阻断（决策 5） |
| `docs/superpowers/specs`、`plans` | **互补**。spec/plan 是任务开始前的设计，交接物是执行中的状态。交接物在「引用」段指向它们，不复述内容 |

### skill 行为

### darwin-skill 评分门禁

按 `AGENTS.md`，新插件属 Minor 升级，**提交前须用 `darwin-skill` 对 session-handoff 评分**。

门禁原文「新分数 ≥ 改动前分数」防的是同一 skill 迭代退步，新 skill 无「改动前分数」，该判据对首发不适用。**不要拿另一个 skill 当替代基线**——两者分数不可比（rubric 评的是各自 SKILL.md 的结构质量，不是同一把尺子的刻度）。首发直接看绝对分与各维度失分点，按失分点改；改完的分数即将来迭代的基线。

### test-prompts.json

至少覆盖四类：

| # | 场景 | 考察点 |
|---|---|---|
| 1 | "交接一下" + 会话有决策有踩坑 | 三层齐全，段落取舍正确 |

| 3 | "继续上次的工作" + 存在多个任务目录 | 让用户选而非默认取最新；复述后停下 |
| 4 | **指令冲突**："快速交接，别问了" + 会话内容极少 | 告知"本次无实质可交接内容"，既不无视指令追问，也不生成空洞占位符 |

第 2 与第 4 条是关键——测的是本 skill 最容易失守的地方：为了显得"完整"而输出无价值内容。

### 最小可行测试

前面都是结构性检查，这条才是真正的成败判定——**交接物能不能让一个无上下文的会话接着干**。

- **单一变量**：下一个会话除交接物外不给任何提示
- **执行**：会话结束前保存交接物 → 开新会话，只说"继续上次的工作" → 观察它能否正确说出任务是什么、下一步做什么
- **成功判定**：新会话复述的「下一步」与上个会话的实际意图一致，且无需用户补充背景
- **失败判定**：新会话问出"这个任务是要做什么"这类本该在交接物里的问题
- **失败后收集**：具体缺了哪条信息 → 反推**哪一层**缺哪一段 → 补进模板并记 CHANGELOG

⚠️ 三层结构下失败定位要多一步：先判断缺失信息**该属于哪一层**，再补对应段落。补错层会让下次恢复读不到（例如把「已核验的事实」写进 `summaries`，而恢复时 summaries 是按需读的）。

## 待确认

以下两点在实现前需要拍板：

1. **`docs/sessions/` 是否入版本库**——入库则交接物可跨机器同步、可回溯；不入库（gitignore）则纯本地。**倾向入库**，跨机器场景正是落盘方案相对参照实现的后台 agent 的主要优势。这条决定要写进 skill 的输出提示里，让用户自行决定
2. **是否需要配对的「校验」skill**——`AGENTS.md` 的新 skill 自检要求判断「引导器 vs 传感器」。本 skill 是引导器，其传感器形态（检查交接物是否过期/格式合规）**倾向不做**：为低频场景造刹车本身就是另一种过度设计
