# dotnet-diagnose-autopilot 设计规约

> 日期：2026-09-19
> 状态：设计已确认，待实施计划
> 归属插件：`plugins/optimus-devops-plugin/`
> 产物类型：**skill（编排层）**，调度既有 `dotnet-diagnose` agent，不新增 agent

## 1. 背景与定位

`dotnet-diagnose`（agent）+ `dotnet-diagnose-triage`（skill）已交付「读证据 → 定征象 → 消解假设台账 → 三档结论强度」的完整单次分析链路（见 `docs/superpowers/specs/2026-09-05-dotnet-diagnose-agent-design.md`）。用户在 `/insights` 报告的"On the Horizon"建议基础上，提出把这条链路包成一个**自主分诊工作流**：给定原始诊断素材，自动识别类型、路由到判据、必要时用独立推理路径做第二次分析、产出含根因/置信度/证据的结构化报告，两次分析不一致时标记交人工复核。

`dotnet-diagnose` agent 明确声明"无跨调用状态"，每次调用都是独立上下文——多轮调度、条件分支、置信度比对、报告合成，这些**编排逻辑**不属于 agent 该长的能力，也不该塞进 `dotnet-diagnose-triage`（它是判据承载层，不是流程编排层）。因此本次交付新建一个**编排层 skill**：`dotnet-diagnose-autopilot`，通过 `Task` 工具调度既有 agent，不修改 agent 与承载 skill 的任何既有内容。

## 2. 范围与零重叠

| 既有产物 | 它负责 | 本 skill 负责 | 切线 |
|---|---|---|---|
| `dotnet-diagnose`（agent） | 单次调用内的证据解读与假设消解 | 决定**调用几次**、**给谁看什么**、**怎么合并结论** | 单次推理 vs 多次编排 |
| `dotnet-diagnose-triage`（skill） | 判据表、征象路由、三档强度定义 | 只**消费**这些定义做置信度分档，不重新定义 | 判据来源 vs 判据消费方 |
| 官方 `dump-collect` / `dotnet-trace-collect` | 取证抓取 | 不涉及，本 skill 只接收已有素材 | 取证 vs 分析编排 |

**不做什么**（收窄边界，避免与 triage 职责重叠）：
- 不重新判定"征象"（挂起/内存增长/崩溃/…）——那是 agent 内部路由的职责，本 skill 只判断素材的**证据类型**（单时点/时间序列/崩溃日志/不可用），随素材一并转发给 agent 自行推断征象
- 不重新定义结论强度——直接复用 triage 已有的三档（已确认/推测/超出覆盖）
- 不做知识库判据裁剪——那是 agent 加载 triage 后的职责

## 3. 素材类型识别

新 skill 的第一步只做"这坨文本是不是一份可用的取证输出、属于哪类证据"这一层最外围判断，判定结果直接对应 `dotnet-diagnose-triage/references/symptom-hypothesis-map.md` 已有的证据类型二分（单时点 / 时间序列），不新造分类体系：

| 素材特征 | 归入证据类型 | 后续路由（由 agent 内部完成） |
|---|---|---|
| 含 `Index`/`SyncBlock`/`MonitorHeld`/`MT`/`Count`/`TotalSize` 等 SOS 命令列名 | 单时点证据（dump/SOS 输出） | agent 加载 triage 后走 `debugging-decision-tree.md` |
| 含托管异常类型 + 堆栈帧（`System.XXXException` + `at ...` 或 `InnerException`） | 崩溃日志 | 走 `evidence-precheck.md`「崩溃日志的定位」一节 |
| 含 counters/trace 时间序列表头（多行采样、时间戳列） | 时间序列证据 | 走 `live-monitoring-decision.md` |
| 三者均不含（纯业务日志、空文本、无异常语义的纯文字） | 不可用 | **不派发**，直接短路报错，参照 triage 已有失败处理表「粘的输出不是取证输出」一行 |

**征象判定不在本 skill 做**：素材本身通常不显式包含"界面卡死""内存持续增长"这类症状描述。若用户在触发语句中一并给出了症状描述，随素材原样转发；若没给，不替用户猜——交给 `dotnet-diagnose` agent Step 2 自行按证据推断征象。这是为了不与 agent 内部的征象路由各自维护一套判断逻辑而互相打架。

## 4. 两次调用机制（盲态双活）

主干六步：

```
Step 1  素材类型识别（见 § 3），不可用则短路结束
Step 2  首次分析：Task 派发全新、无历史上下文的子任务
Step 3  解析首次结论强度（已确认 / 推测 / 超出覆盖 / 候选集穷尽）
Step 4  置信度分档：仅"推测"触发第二次
Step 5  第二次分析（仅 Step 4 判定触发时执行）：另起一个全新、无上下文的 Task
Step 6  比对两次结论，合成报告
```

### 4.1 Step 2/5 的 dispatch prompt 硬约束

`docs/superpowers/sdd/2026-09-06-dotnet-diagnose-implementation/progress.md` 记录过一个已验证的坑：早期测试中，若 dispatch prompt 只是笼统地说"帮我看看"，外层会转述总结 agent 的回答而非原样返回，导致台账状态判断失真。因此每次 `Task` 调用的 prompt 必须固定包含：

> 把下面的内容原样作为输入转发给 `@optimus-devops-plugin:dotnet-diagnose`，然后把该 agent 的回答**逐字原样**输出。禁止总结、禁止改写、禁止补充你自己的分析或评论、禁止加任何前言后语。你的整个回复必须只包含 agent 返回的原文。

这条约束对 Step 2 和 Step 5 都适用，是复用已验证过的调用范式，不是本次新加的保险。

### 4.2 触发条件：为什么只有"推测"触发第二次

| 首次结论强度 | 是否触发第二次 | 理由 |
|---|---|---|
| 已确认 | 否 | 已命中 triage 判据的证实条件，已经足够硬，重验是浪费一次几百秒的调用 |
| 推测 | **是** | 唯一映射到需求原文"置信度较低或证据不足"的信号；证据方向一致但判据未完整命中，值得独立路径复核 |
| 超出覆盖 / 候选集穷尽 | 否 | 这是知识缺口或假设已穷尽，不是置信度问题，重跑大概率原地打转 |

不新增任何置信度数值或阈值概念，直接复用 `dotnet-diagnose-triage` SKILL.md 已有的三档定义，避免两套置信度体系并存造成语义冲突。

### 4.3 盲态双活：两次调用零信息传递

第二次调用是**另起一个全新、无上下文的 Task**，只传入原始素材本身，不告诉它"这是复核""第一次说了什么"、不传第一次的台账或结论。这是"不同推理路径"的具体实现：两次分析完全独立产生，而不是"对抗式"地让第二次去挑战第一次的结论（后者会让第二次的判断被第一次结论锚定，偏离"独立观察"的字面含义）。

### 4.4 结论比对与合并

| 两次结论关系 | 处理 |
|---|---|
| 强度一致 + 假设台账指向同一根因 | 合并为一条结论，标注"两次独立盲态分析交叉确认"，置信度可视为高于单次 |
| 强度不同，或指向不同根因 | **不擅自取舍、不加权投票、不选"更详细的那份"**。两份结论并列展示，标记 🔴 需人工复核 |

"不一致"不是错误，是这套流程存在的意义——如果永远不出现分歧，双活验证就没有存在必要。自动裁决分歧会让流程在缺乏依据时假装能替用户做判断，直接违背需求原文"标记出来交给我人工复核"。

## 5. 结构化报告与落盘

### 5.1 报告骨架

```markdown
# .NET 自主分诊报告

## 素材摘要
- 类型：{单时点证据/崩溃日志/时间序列证据}
- 判定依据：{命中的特征，如 "含 MonitorHeld 列"}

## 首次分析
{dotnet-diagnose 原样输出：结论 / 修复方向 / 台账 / 免责声明}

## 复核分析
{未触发时：「未触发：首次已确认/超出覆盖，复核条件未命中」}
{触发时：第二次盲态调用的原样输出}

## 一致性判定
- 结论：{一致 / 不一致 / 未触发复核}
- {一致时：合并陈述，标注"两次独立盲态分析交叉确认"}
- {不一致时：并列列出两份结论，🔴 标记"需人工复核"，不擅自取舍}

## 最终建议
{仅当"一致"或"仅首次触发"时给出；"不一致"时写"见上方两份结论，需人工裁决后再确定修复方向"}
```

四段固定顺序，与 `dotnet-diagnose` agent 自身的四段输出格式（结论/修复方向/台账交接块/免责声明）保持同构，只是在外层多包一层"两次调用对比"，读者不必学习两套报告语言。

### 5.2 落盘位置

复用 `dotnet-diagnose-triage/test-cases/golden.md` 已经验证过的目录选址逻辑——诊断素材可能含敏感数据，按 `knowledge-base/dotnet-debugging/rules/01-dump-handling.md § 2. 版本库隔离` 不得落进 git 工作树：

```
$HOME/dd-autopilot/report-<timestamp>.md
```

与既有的 `$HOME/dd-golden/`（golden 测例输出目录）同级但分开命名，不新造一套版本库隔离约定。落盘前须确认该目录存在且可写（前置校验第 3 类：输出参数检查）。

## 6. 目录结构与配套文件

```
plugins/optimus-devops-plugin/skills/dotnet-diagnose-autopilot/
├── SKILL.md              ← 六字段 frontmatter + 六步主干
├── README.md             ← 六章节规范（所处层级/触发词/流程图/数据流/依赖图）
├── CHANGELOG.md           ← 起始 1.0.0
└── evals/
    └── 01-syncblk-monitor-lock/
        └── prompt.md      ← CI new-skill-eval-case 门禁强制要求
```

**frontmatter 要点**（遵循 `.claude/rules/skill-conventions.md`）：

| 字段 | 取值 | 理由 |
|---|---|---|
| `metadata.category` | `workflow` | 多阶段、条件分支、交接式编排，正是 category 表对 workflow 的定义 |
| `allowed-tools` | `Task Write Read` | `Task` 派发 agent；`Write` 落盘报告；`Read` 用于素材类型识别时读取用户提供的文件（若素材以文件路径给出而非直接粘贴） |
| `compatibility` | 声明依赖 `optimus-devops-plugin:dotnet-diagnose` agent 已安装同一插件内 | 与 triage skill 的 `compatibility` 写法一致（声明知识库依赖同一工作树） |

**版本联动**：新增 skill 触发插件两份 `plugin.json` 同步升 **Minor**（`1.2.4` → `1.3.0`），因为是"新增 skill"而非"修改已有内容"（按 `AGENTS.md` 触发矩阵与升级幅度表）。

**README 所处层级图**：标注本 skill 与 `dotnet-diagnose-triage`、`dotnet-diagnose` agent 的关系——编排层调度承载层通过 agent 间接消费，用 `★` 标记本 skill。依赖关系图注明"调度 `optimus-devops-plugin:dotnet-diagnose` agent（经 Task 工具，非直接 Skill 加载）"。

## 7. 失败处理

| 触发条件 | 处置 | 理由 |
|---|---|---|
| Step 2/5 的 `Task` 调用超时或无响应 | 不设短超时熔断；`dotnet-diagnose` 单次正常耗时可达 300 秒以上（见 `test-cases/golden.md` 已验证的实测特征），先等待。若最终仍失败（工具报错、非超时类失败），如实转发失败原因，标注"首次分析未能完成"，**不重试、不静默跳过**——参照 triage 已有失败处理表统一处置基调，重试属于掩盖问题 | 特意不引入新的超时数值，避免与 agent 自身已经隐含的耐心假设打架 |
| Step 1 素材类型识别判定为"不可用" | 短路结束，不派发任何 Task，报错提示"未识别出可用的取证输出类型"，并引用 `evidence-precheck.md`「粘的输出不是取证输出」一行给出的排查方向 | 不可用的素材派发下去只会让 agent 在 Step 1（证据清点）重新判一次同样的失败，白白消耗一次几百秒的调用 |
| Step 2 首次分析返回的内容**仅是症状描述、无任何取证结论**（如 agent 判定证据不足以进入分析，直接反问用户要更多信息） | 不进入 Step 3 的强度判定、不触发 Step 4/5 的第二次调用；原样转发 agent 的反问内容，报告落盘时"复核分析"段落写"未触发：首次分析要求补充证据，未产生可比对的结论" | 双活机制比对的是两份**结论**；连一份结论都没有，比对无从谈起，若仍勉强进入双活会让第二次调用重复同一个证据不足的死路 |
| Step 5 第二次分析同样超时或失败 | 报告的"复核分析"段落写明失败原因，"一致性判定"写"复核未完成"，不当作"一致"或"不一致"处理，仍标 🔴 交人工复核 | 复核失败本身就是一种需要人工介入的情形，不能因为拿不到第二份结论就假装第一份结论已经过双活验证 |
| `Write` 落盘失败（如 `$HOME/dd-autopilot/` 不可写） | 报告内容仍在对话中完整输出，附加提示"落盘失败：{原因}，请手动保存以下内容" | 落盘是交付形式的加分项，不是报告本身能否产出的前提条件，不能让磁盘 IO 问题挡住整个分诊结论 |

## 8. 反例与黑名单

以下做法在设计讨论中被明确排除，记录理由以防日后重新引入：

- **不重新判定"征象"**。曾考虑过在本 skill 里预先识别"挂起/内存增长/崩溃"等症状类别再转发给 agent，但 `dotnet-diagnose` 内部已有一套基于证据自行推断征象的路由逻辑（见 `symptom-hypothesis-map.md`）。两边各判一次会在结论不一致时无法定位是谁判错了，见 § 3 已确认的做法：只判"证据类型"，不判"征象"。
- **不新增置信度数值或阈值体系**。曾考虑给"推测"结论内部再细分"60% 置信"这类数值分级，用于更精细地决定是否触发第二次分析。这会与 `dotnet-diagnose-triage` 已有的三档结论强度（已确认/推测/超出覆盖）并存，两套语言混用会让读者不知道该看哪一个。§ 4.2 已确认只复用既有三档。
- **不让第二次调用知晓第一次的结论或中间台账**。曾考虑把第一次的假设台账作为"已排除项"提示给第二次调用，让它别浪费时间重复验证同一批假设。但这违背"盲态"的核心目的——第二次调用一旦看到第一次的排除结果，其独立性就被污染，等价于伪装成两次分析的一次半分析。§ 4.3 已明确两次调用完全零信息传递。
- **不对不一致结论自动加权、投票或择一裁决**。曾考虑当两次结论强度不同时（如一次"已确认"一次"推测"），自动采信强度更高的那份。但用户在原始需求中明确要求"标记出来交给我人工复核"，自动裁决等于绕开了这个明确要求，且"强度更高"不代表"更接近事实"——推测有时反而抓住了确认判据遗漏的边缘线索。§ 4.4 已明确不一致时并列展示、不擅自取舍。
- **不把"对抗式复核"当作"不同推理路径"的实现**。曾考虑让第二次调用带着"请挑战第一次的结论"这类提示词，模拟同行评审的质疑过程。但这样第二次调用从一开始就被第一次结论锚定，产生的不是独立观察，而是针对既有结论的辩论——这与需求原文"不同的推理路径"的字面含义（两条独立产生的路径）相悖。
- **不复制或改写 `dotnet-diagnose-triage` 的判据内容**。本 skill 全程不直接读取 `references/*.md` 下的判据文件，只经由 `dotnet-diagnose` agent 间接消费；如果发现某类素材路由不到判据，问题出在 triage 或 agent 层，不该在本 skill 里加一份本地兜底判据表——那会导致同一份知识出现两处真源。
