# sync-cc-tips 优化设计文档

**日期：** 2026-08-18
**状态：** 已批准

---

## 背景

`sync-cc-tips` 是从 Claude Code 官方 changelog 自动同步 `tips.txt` 的 skill（`.claude/skills/sync-cc-tips/SKILL.md`，仅本仓库自用不发布）。当前流程存在以下问题（在 2026-08-18 的一次实际执行中集中暴露）：

1. **抓取效率**：`curl` 直接拉取完整 `CHANGELOG.md`（当前 500KB+，且只会随时间持续增长），单次输出触发工具截断，需要二次 `Read` 才能拿到内容。
2. **判重方式脆弱**：Step 2 判断"changelog 功能点是否已被 tips.txt 覆盖"依赖模型通读全文（当前 573 行/290 条）并凭印象比对，成本和漏判风险随文件增长线性上升。
3. **窗口固定、无进度锚点**：每次固定处理"最近 10 个版本"，若中途间隔较久未运行（例如发布了 15+ 个版本），窗口外的更早版本会被静默跳过，且没有任何机制记录或提示"上次同步到了哪个版本"。
4. **差异识别不可审计**：Step 3 直接给出"新增/修改/删除"结论，没有逐条 bullet 的中间判定记录，无法事后核实是否漏看了某条 changelog 内容。
5. **摘要不完整**：执行摘要只统计新增/修改/删除数量，没有"跳过（已覆盖）N 条"这一栏，无法验证本轮是否完整过了一遍所有 changelog 条目。
6. **CHECKPOINT 依赖自由文本**：三处人工确认点都要求用户手打 `y`/`yes`/`n`/`no`，容易产生输入歧义。
7. **小项可维护性问题**：分类清单硬编码了"现有 11 个"这一计数，新增/删除分类时容易忘记同步这个数字。

本次优化针对以上 7 类问题重构 skill 内部的抓取、判重、差异识别与交互逻辑，不改变 skill 的对外触发方式和职责边界（仍是"changelog → tips.txt 同步 → 提交"）。

---

## 目标

- 抓取阶段直接截断到所需版本范围，避免大文件二次读取
- 判重阶段从"通读全文凭印象"改为"结构化清单查表"
- 引入持久化的"上次同步版本"锚点，替代固定的"最近 N 个版本"窗口，避免跨间隔运行时静默漏看
- 差异识别过程可审计：新增中间过程表，逐条 bullet 展示判定依据
- 执行摘要补充"跳过（已覆盖）"计数，作为完整性校验的旁证
- 三处 CHECKPOINT 改用 `AskUserQuestion` 结构化确认，替代自由文本输入
- 清理硬编码的分类计数

---

## 文件位置

```
.claude/skills/sync-cc-tips/SKILL.md          （修改）
.claude/skills/sync-cc-tips/.last-synced-version  （新增，持久化状态文件）
```

`.last-synced-version` 是纯文本文件，仅存一行版本号（如 `2.1.234`），随每次同步流程一并被 `commit-cc-plugin` 提交进 git，作为跨会话/跨机器共享的同步进度锚点。

---

## 整体数据流

```
读 .last-synced-version（锚点）
      │
      ▼
curl changelog | awk 按锚点截断（从最新往回截到锚点版本为止，命中即停）
      │
      ▼
grep 预提取 tips.txt 全部主标识符 → 结构化清单（一次性，非通读）
      │
      ▼
逐条 bullet 与清单比对 → 中间过程表（对话内展示：bullet摘要｜提取标识符｜命中情况｜判定）
      │
      ▼
三类差异（新增/修改/删除）+ 跳过计数
      │
      ▼
AskUserQuestion 结构化确认（替代 y/yes/n/no 自由文本）
      │
      ▼
写入 tips.txt → 更新 .last-synced-version 为本次处理到的最新版本号 → commit-cc-plugin
```

将"上次同步到哪个版本"做成随 git 提交的文件而非运行时状态，使得即使换一台机器、换一次会话继续运行本 skill，也能从仓库历史中读到正确的锚点，与 `tips.txt` 本身的持久化方式保持一致。

## Step 1 改动 —— 持久化锚点 + 截断抓取

**新增子步骤（在原「抓取 changelog」之前插入）：**

```
读取 .claude/skills/sync-cc-tips/.last-synced-version
├─ 文件不存在（首次运行）→ 锚点为空，回退到「最新 10 个版本」作为默认窗口（保留旧行为兜底）
└─ 文件存在 → 读取其中版本号作为锚点，如 "2.1.224"
```

**抓取命令改为管道截断：**

```bash
curl -s --max-time 15 https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md \
  | awk -v anchor="## 2.1.224" '
    /^## /{ if ($0 == anchor) exit; print; next }
    { print }
  '
```

逻辑：从文件顶部（最新版本）开始逐行输出，一旦遇到 `## {锚点版本}` 这一行就立即停止 —— 锚点版本本身**不包含**在本次输出里（因为已在上次同步中处理过），只输出锚点之后（更新）的所有版本。

**原有的 curl 失败降级（WebFetch）与重试逻辑保持不变**，仅在原 curl 命令后追加 awk 管道。

**边界情况：**

| 情况 | 处理 |
|---|---|
| 锚点版本在 changelog 中找不到（如相隔太久，CHANGELOG.md 只保留近期版本，锚点已被滚出文件） | awk 跑到文件末尾都没 exit，等于输出了全部可见内容 —— 检测输出的版本数，若 > 30，通过 `AskUserQuestion` 提示「距离上次同步已超过 30 个版本，changelog 中未找到锚点版本，是否继续处理全部可见版本」 |
| 输出为空（锚点就是最新版本，无新版本） | 直接判定为 0 新版本，等同于触发「🚦零变更总闸」，跳过后续所有步骤 |
| 用户仍传入 `/sync-cc-tips N` 参数 | 忽略锚点截断逻辑，改为强制只处理最新 N 个版本（用于"重新看看最近 N 个版本"的手动场景），且**不更新** `.last-synced-version`（范围受限的临时查看，不代表真实进度） |
| 本轮 changelog 有版本可处理，但全部 bullet 均判定为 ⏭️ 跳过（已覆盖/非用户可操作），无任何新增/修改/删除 | 仍推进 `.last-synced-version` 到本轮处理到的最新版本，并单独提交（不写入 tips.txt，不触发 marketplace 版本升级）——避免下次运行重新扫描这段已确认无实质变更的区间 |

## Step 2 改动 —— grep 预提取标识符清单

原方式为"通读 tips.txt 全文，凭印象判断是否命中"。改为：先用 grep 一次性抽取所有候选标识符，生成结构化清单，后续判重直接查表，不再重新扫读全文。

**提取命令（分类别跑，每类一条 grep，去重排序）：**

```bash
f=plugins/optimus-devops-plugin/hooks/sessionstart/tips.txt

echo "=== CLI flags ==="
grep -oE -- '--[a-z][a-z-]*' "$f" | sort -u

echo "=== 交互命令 ==="
grep -oE '/[a-z][a-z-]*' "$f" | sort -u

echo "=== 环境变量 ==="
grep -oE '\b(CLAUDE_CODE|OTEL|ANTHROPIC)_[A-Z_]+\b' "$f" | sort -u

echo "=== settings.json 键名 ==="
grep -oE '\b[a-z][a-zA-Z]*\.[a-zA-Z][a-zA-Z]*\b|\b[a-z][a-zA-Z]{3,}\b' "$f" | sort -u

echo "=== 子命令/CLI 命令名 ==="
grep -oE 'claude [a-z][a-z-]*( [a-z][a-z-]*)?' "$f" | sort -u
```

> settings.json 键名类别的正则较宽泛（camelCase 变量名和普通英文单词区分度低），生成清单后仍需模型过一遍剔除明显噪音（如英文助词、通用词），但这是对一份**短清单**做筛选，而非对 500+ 行全文做模糊记忆匹配，工作量级不同。

**产物形态：** 一份结构化清单（五个类别，每类去重排序的列表），进入对话上下文，供 Step 3 逐条比对时查表用，不落盘。

**判重方式改变：**
- 原来：「在已覆盖标识符集中逐一查找」（集合隐式、靠通读记住）
- 现在：「在这份结构化清单中查找」（集合显式、可逐行核对）

**边界情况：**

| 情况 | 处理 |
|---|---|
| grep 提取的候选标识符里混入明显噪音（如把普通英文单词误判成 settings 键名） | 生成清单后模型过一遍做可读性清洗，只保留看起来像真实标识符的项，不追求正则完美 |
| tips.txt 文件不存在/为空 | 沿用原有 CHECKPOINT 逻辑不变 |

## Step 3 改动 —— 差异识别中间过程表 + 摘要跳过计数

**新增中间过程表（对话内展示，不写入任何文件）：**

在做出新增/修改/删除判定之前，先按 changelog 每条 bullet 生成一行记录，汇总成一张表：

| Bullet 摘要 | 提取的主标识符 | 命中情况 | 判定 |
|---|---|---|---|
| Added CLAUDE_CODE_PROJECT_DIR_NAME env var... | `CLAUDE_CODE_PROJECT_DIR_NAME` | 未命中 | 🆕 新增 |
| Fixed auto mode in very long sessions... | （无用户可操作标识符，纯 bug fix） | — | ⏭️ 跳过（非用户可操作功能） |
| Added GitLab merge request badge to footer... | `GitLab`, `footer`, `glab` | 命中已有「GitLab 支持扩展」条目 | ⏭️ 跳过（已覆盖，需修改） |

这张表覆盖 changelog 窗口内的**每一条** bullet（不只是最终判定为新增/修改的那些），包括被跳过的 —— 使"是否完整过了一遍所有条目"变得可核对，而非黑盒结论。

**判定归类为四种（比原来三种多了"跳过"）：**
- 🆕 新增
- ✏️ 修改
- ⏭️ 跳过（已覆盖 / 非用户可操作功能，两种子原因均需在"命中情况"列写明）
- 🗑️ 删除（仍走原有「changelog 明确标注 Removed/Deprecated」判定，针对已有 tips 条目而非 changelog bullet，不在此表中逐条列出，单独处理）

**摘要格式新增一栏（详见「摘要格式」章节）：**

跳过计数 = 中间过程表里判定为"⏭️ 跳过"的行数，起完整性校验作用：changelog 窗口内共 M 条 bullet，新增 + 修改 + 跳过（针对 bullet 的删除判定不计入，因删除源于已有条目而非 bullet）应约等于 M，数量对不上说明中间过程表本身有遗漏。

**边界情况：**

| 情况 | 处理 |
|---|---|
| 一条 bullet 涉及多个可拆分的独立功能点（如一条 bullet 合并宣布两个不相关的新 flag） | 中间过程表中拆成两行分别判定，不强行捏合成一条 |
| bullet 数量很大（如窗口跨度很长，一次有 100+ 条） | 中间过程表仍逐条生成，不因数量大而抽样或省略 —— 这是完整性校验的核心，抽样等于放弃了这张表的意义 |

## CHECKPOINT 交互方式 —— AskUserQuestion 取代自由文本

原方案要求用户手打 `y`/`yes`/`n`/`no` 等自由文本，容易产生输入歧义。全部三处 CHECKPOINT 改为结构化选项：

**① Step 4 写入前确认（变更预览后）**

```
AskUserQuestion:
  question: "以上是本次识别到的变更（N 新增 / N 修改 / N 删除 / N 跳过），是否写入 tips.txt 并继续后续提交流程？"
  options:
    - "确认写入并提交"（推荐）
    - "取消，不做任何修改"
```

选"取消" → 输出「操作已取消，tips.txt 未修改」，流程终止，`.last-synced-version` 也不更新（因为没有真正处理完这次变更）。

**② Step 5 数字不一致确认（marketplace.json / README.md 两处更新后数值对不上时）**

```
AskUserQuestion:
  question: "同步文档数字时发现不一致：{具体差异位置}。是否以 tips.txt 实际 `^\[` 行数（{X}）为准继续提交？"
  options:
    - "以 tips.txt 实际行数为准，继续提交"（推荐）
    - "取消本次提交，我要手动检查"
```

**③ 锚点滚出 changelog 文件时的确认（Step 1 新增边界情况）**

```
AskUserQuestion:
  question: "距离上次同步（v{锚点版本}）已超过 30 个版本，changelog 中已找不到该锚点。是否继续处理当前可见的全部 {N} 个版本？"
  options:
    - "继续处理全部可见版本"（推荐）
    - "取消，我需要先确认是否漏看了历史内容"
```

三处统一模式：一个推荐选项 + 一个取消选项，选取消统一走"停止流程，不写入不提交"的路径，不再需要模型解析用户输入的自由文本变体。

**边界情况：**

| 情况 | 处理 |
|---|---|
| 用户在 AskUserQuestion 里选了"Other"并输入自定义文本 | 视为非明确同意，按"取消"路径处理，不强行解析意图 |

## 硬编码分类计数清理

原 SKILL.md 中：

```
分类从现有 11 个中选最匹配：`[交互]`、`[工具]`、`[Hook]`、`[配置]`、`[CLI]`、`[集成]`、`[工作流与自动化]`、`[排障]`、`[Skill]`、`[MCP]`、`[高级]`
```

"11 个"是硬编码计数，新增或删除分类时容易忘记同步。改为：

```
分类从现有分类中选最匹配：`[交互]`、`[工具]`、`[Hook]`、`[配置]`、`[CLI]`、`[集成]`、`[工作流与自动化]`、`[排障]`、`[Skill]`、`[MCP]`、`[高级]`
```

仅去掉"现有 X 个"这一计数表述，分类名清单本身保留（模型选择时仍需要这份清单）。纯文本改动，无边界情况。

## 执行摘要格式

```
✅ sync-cc-tips 完成 · v{锚点版本} → v{最新版本}

📥 新增  N 条
  · [分类] 条目标题
  · ...

✏️  修改  N 条
  · [分类] 条目标题 → 修改说明
  · ...

🗑️  删除  N 条
  · [分类] 条目标题（删除原因）
  · ...

⏭️  跳过  N 条（已覆盖 / 非用户可操作功能）

📊 条目总数：{旧数} → {新数}
📄 已同步：marketplace.json · hooks/README.md
🔖 版本：{旧版本} → {新版本}（Patch）
🔖 同步锚点：v{锚点版本} → v{最新版本}

---
进入提交流程...
```

新增两处：`⏭️ 跳过 N 条` 一栏（对应 Step 3 的完整性校验），以及`🔖 同步锚点` 一行（展示 `.last-synced-version` 的更新前后值，便于用户确认锚点确实被推进）。

- 不改变 skill 的触发方式（`/sync-cc-tips`、语义触发词、`/sync-cc-tips N` 参数语法均保留，仅内部处理逻辑变化）
- 不改变 `commit-cc-plugin` 提交流程本身
- 不对 `.claude/` 下的改动升级 marketplace 版本号（遵循 CLAUDE.md 规范）；但按 `skill-authoring.md` 规范，本次修改需同步升级 `sync-cc-tips` 自身的 `metadata.version`（Minor：新增锚点机制、中间过程表等功能性内容）
