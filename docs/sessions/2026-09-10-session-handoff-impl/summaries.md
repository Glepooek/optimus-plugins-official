# session-handoff skill 实现 · 决策与权衡

## 会话 1 — 2026-09-10

### 关键决策

- **交接物用三层分文件，不用单文件六段**：用户在两个选项间选了三层。收益在恢复侧——`summaries.md` 只在「要改动上轮决定」时读，日常恢复读两层即可。若三层都必读，拆分就只剩额外的文件读取开销，这是判断三层结构是否值得的唯一标准
- **第三层定位从 fltrp 的「逐轮对话」改为「习得与核验」**：这不是偏好选择，是「三层 + 仅显式触发」两个决定的**连带推论**。fltrp 的 `conversations` 是每轮静默追写累积出来的；仅显式触发时到会话末尾回溯补写，早期轮次已被 context 压缩，凭印象重编等于编造。改成会话末尾能一次性可靠写出的「结论类」内容
- **后两层允许整个文件不创建**：与 fltrp 相反（它的 Red Flag 把"只更新 progress 不写 summary"列为错误）。差异根源是场景不同——fltrp 面向长周期客户端开发几乎每轮有决策，本 skill 面向的场景含大量纯执行会话
- **SKILL.md 行数上限从旧版的 150 放宽到 180**：三层结构比单文件六段多出「分层读取顺序」与「三层各自的创建判定」两块，且 7 项检查清单必须落进正文。150 行会逼出两种坏结果：砍掉检查清单，或把约束压缩成暗示

### 方案权衡

- **放弃的方案**：完全照搬 fltrp 的 `docs/sessions/{分支}/{层}/{user}.ext` 路径结构
  **放弃原因**：层在中间、按人分文件，隐含「一分支 = 一任务」假设。本仓长期停留 master，所有任务会挤进同一个 `progress/anyu.txt` 且无归档机制。改为「一任务一目录」后单文件体量天然受限

- **放弃的方案**：采纳 fltrp 的 `pitfalls.md` → code-linter 自动沉淀闭环
  **放弃原因**：自动往知识库塞内容会混入大量仅对单任务有效的条目，而 `knowledge-base/` 的定位是「被 skill 编程式检索的规范条款」，污染后检索结果不可用。改为在 `insights.md` 的踩坑记录里加「归属判定」字段，标注但不代为搬运

- **放弃的方案**：采纳 fltrp 的 stop hook（session-guard）
  **放弃原因**：三条独立理由，任一条都足够——① 本仓 hook 的对等位置是 pre-commit，而交接物漏写不是仓库一致性问题、不该阻断；② 它的检测手段是对 assistant 回复文本做正则匹配，这类触发极易误报漏报；③ Codex 侧无对应机制，做了就是单 harness 特性

- **放弃的方案**：保留 fltrp 的「技术洞察」维度（记 API 行为、框架特性）
  **放弃原因**：那是长期有效的知识，该进 `knowledge-base/`。写进交接物会让它随任务结束变成历史——**归属错了的信息等于丢了**

### 遗留风险

- **三层结构对单人小任务可能过重**——这是本次结构选择的主要代价，plan 风险表标为「中高」。缓解手段是「后两层可不创建」。若实测发现绝大多数会话只产 `progress.md`，说明三层拆分收益为负，届时按数据回退为单文件。**要等实测数据，不要现在预判**
- **`summaries.md` 的「按需读」依赖恢复时的自觉判断**——若实际使用中每次都读全三层，分层收益归零而成本仍在。目前无机制强制，只有 SKILL.md 里的一句判据

### 待验证的假设

- **假设：交接物能让无上下文的会话正确接手。** 这是全部验收项里唯一能判定成败的一条。验证方式：另开新会话只说「继续上次的工作」，成功判定是它能说出任务是什么、下一步做什么且无需补充背景；失败判定是它问出「这个任务是要做什么」
- **假设：三层的读取必要性划分（两必读一按需）符合真实恢复需求。** 若验证时发现恢复必须读 `summaries.md` 才能接手，说明该层放了本该在 `progress.md` 的内容，需要重新划分而非简单补段
- **假设：多人与非 master 默认分支的路径推导逻辑正确。** 仅经静态审查（确认用的是 `git symbolic-ref` 输出与 `AUTHORS > 1` 判断，而非字面量），无实测环境。已在 CHANGELOG「已知限制」标注，不假装验证过

## 会话 2 — 2026-09-10

### 关键决策

- **评估方法从「自评 + 子 agent 探索」改为「独立盲评 + 沙箱化 dim8」**：上一轮 baseline 组因子 agent 读到仓库内 SKILL.md 而失效。本轮两个评审都不接触仓库，dim8 用虚构场景把 git 命令输出预先喂给执行者。代价是失去真实环境维度，换来可复现性与无污染
- **不给 Round 1 一个总分**：两个评审用的是「逐行执行模拟」尺子，首评 68.4 用的是「文档质量」尺子。硬拼一个数字是假精确。results.tsv 记为 `keep` 并注明下轮基线须以执行模拟重建
- **`templates.md` 拆分时不新立第四个文件**：跨三层的「追加语义」「取舍规则」两节分解进各层。这不只是为了避免第四个文件——三层的语义本就不同，只有 `progress` 有「队列整段覆写」这条特例，原来的跨层表把特例摊平成了通用规则
- **放弃自定的 180 行上限**：本轮修的全是静默出错路径，SKILL.md 从 178 涨到 213 行。该上限是写 plan 时定的软目标，不是外部规范，与正确性冲突时让位

### 方案权衡

- **放弃的方案**：按评审建议把 `allowed-tools` 改为逗号分隔
  **放弃原因**：本仓 11 个 skill 全部使用空格分隔。评审是按通用规范提的，与仓库既定约定冲突时以约定为准

- **放弃的方案**：为了守住 180 行上限，把待办队列 7 项清单完全下沉到模板、SKILL.md 只留指针
  **放弃原因**：那份清单是执行时逐项核对用的，放在主流程里才会被真正过一遍。下沉到模板等于多一次跳转，实际会被跳过

### 遗留风险

- **本轮修复全部未经真实环境实测**。`SLUG_BRANCH` 净化、CWD 锚定、glob 过滤三条都只做了静态推理，需要在含斜杠的分支名下实跑一次才算验证（已入待办 🟡）
- **修复批次密集但缺回归**。三批共 21 处改动叠加在同一份文件上，后改的可能与先改的冲突。目前只核对了章节结构完整性，没有重跑一次完整执行模拟

### 待验证的假设

- **假设：这批修复没有引入新的执行分歧。** 验证方式是修完后再跑一次同样的沙箱化 dim8，看新的执行者是否还会报告「需要自行猜测」的地方。本轮时间关系未做
