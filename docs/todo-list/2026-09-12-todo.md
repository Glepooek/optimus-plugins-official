## 主干推送方式的规范冲突（待裁决作用域）

`knowledge-base/git/` 与 `commit-cc-plugin` skill 对「怎么把改动合入主干」给出**相反**的答案，三方并存：

- `knowledge-base/git/rules/03-pull-requests.md:24` —— **必须**：主干分支开启保护规则，**禁止直接推送**、禁止 force push，只能通过 PR 合入；`:25` —— **必须**：至少一名 reviewer 批准且 CI 全绿才允许合并
- `commit-cc-plugin` skill 第五步 —— `git pull --rebase origin master && git push origin master`，即**直推主干**；而 `AGENTS.md`「提交与推送」规定提交**必须**用这个 skill、禁止手动 git 工作流
- 实际历史 —— `origin/master` 无任何 PR 合入记录，全部直推（另有若干本地分支 merge commit，如 `a179b11 Merge branch 'auto-optimize/20260817-1610'`，那也不是 PR）

冲突的死结在于：`commit-cc-plugin` 自己声明「若本文件与 Git 知识库的通用规范冲突，**以知识库为准**」。按这句执行，它的第五步就该被知识库的「禁止直推主干」否决——但那一步正是 `AGENTS.md` 强制的唯一提交路径。**一份规范把裁决权让给另一份，而另一份禁止它自己的核心动作。**

两条可能的处置（**未定，需要人拍板**）：

1. 给 `03-pull-requests.md` 的主干保护条款加**作用域限定**（如「适用于多人协作仓库；单人维护的插件仓库按 `commit-cc-plugin` 直推主干」）。若走这条，需一并判断 `01-branching.md:17` 的分支命名条款（`<type>/<简短描述>`）是否也只对多人仓库生效——本仓 trunk-based，长期不建特性分支
2. 或者承认本仓也该走 PR，改 `commit-cc-plugin` 第五步与 `AGENTS.md` 的提交约定

⚠️ 处置 1 要改 `knowledge-base/git/`，属规范条目变更，**必须走 `knowledge-base-maintain` skill**（同步 `index.jsonl`、CHANGELOG 与领域版本号，跑一致性校验）。不要直接编辑条目正文。
