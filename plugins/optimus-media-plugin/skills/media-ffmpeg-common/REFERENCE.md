# 环境检测与通用报错处理

## 环境检测

执行任何 media-* skill 的命令前，先确认 ffmpeg/ffprobe 已安装：

```bash
ffmpeg -version && ffprobe -version
```

若提示命令不存在，引导用户参考 `INSTALL.md` 完成安装，不要尝试自动安装。

## 通用报错处理表

| 错误现象 | 原因 | 处理建议 |
|---|---|---|
| `Unknown encoder 'libx264'` | ffmpeg 编译时未包含该编码器 | 执行 `ffmpeg -encoders \| grep x264` 确认，提示用户更换包含完整编码器的发行版（如 Windows 用 gyan.dev 的 full 构建） |
| `Permission denied` | 输出路径无写权限，或目标文件正被其他程序（如播放器）占用 | 确认输出目录存在且当前用户有写权限；关闭占用该文件的程序后重试 |
| `Invalid data found when processing input` | 输入文件已损坏，或格式/编码不受当前 ffmpeg 构建支持 | 先用 media-analyze 对应的 `ffprobe` 命令探测确认文件是否可读 |
| 命令挂起无输出，等待用户输入 | ffmpeg 检测到输出文件已存在，交互式询问是否覆盖 | 命令中加入 `-y`（覆盖）或 `-n`（不覆盖，存在则跳过） |

## 组合请求处理约定

当用户在一句话里同时提出跨越 ≥2 个 media-* skill 职责范围的诉求时（如"转720p顺便压缩一下""截取中间那段再转小分辨率"），适用本约定。各 skill 自身 description 里的 "Not for ..." 边界不因组合请求而改变——组合请求由 Claude 依次调用对应 skill 完成，不是某个 skill 单独扩展自己的能力去覆盖别的 skill 的职责。

### 判定

用户诉求的关键词命中 ≥2 个 skill 的触发词范围（分辨率转换/压缩体积/片段截取/帧率转换/格式转换），即视为组合请求。media-analyze 属于只读查询、media-play 属于只读播放，二者均不参与本约定的顺序编排，可随时按需先行或穿插调用（media-analyze 确认原始参数，media-play 预览效果）。

### 执行顺序（固定，不随用户描述顺序改变）

**trim → resize → framerate → compress → convert**

| 顺序 | 原因 |
|---|---|
| trim 放最前 | 先削减无关时长，减少后续步骤需要处理的数据量，避免在稍后会被剪掉的画面上浪费编码算力 |
| resize 在 framerate 之前 | 分辨率与帧率是正交维度，但均属于"改变视频时空网格"的操作，先固定空间尺寸再处理时间采样，避免顺序颠倒时的心智负担 |
| framerate 在 compress 之前 | compress 的 CRF 取值是针对最终画面尺寸与帧率做的画质/体积权衡，应作用于调整后的时空网格，而非对原始参数算完 CRF 后再变更 |
| compress 在 convert 之前 | 体积压缩是针对内容（像素/时长）的取舍，应在内容层面全部确定后才进行，避免压缩完的产物又被 convert 的转码分支二次有损编码抵消体积优化效果 |
| convert 放最后 | 格式转换只改变封装容器/编码方式，不改变时空网格或内容取舍，作为交付前的收尾环节，默认走 remux 不引入额外画质损失 |

若组合请求只涉及顺序中的其中几项，按上表相对顺序执行，跳过未涉及的项即可。

### 执行方式：分步调用、每步产出中间文件

依次调用对应 skill，每步产出一个中间文件作为下一步输入；**不得**把多个 skill 的 ffmpeg 参数合并进同一条命令（如同时出现 `-vf scale` 与 `-crf`）。

原因：
- 保持每个 skill 命令可独立复现、独立排障——报错时能立刻定位是哪一步、哪个参数的问题
- 与各 skill 自身"不要做什么"/边界声明保持一致，不因组合场景开例外

### 必须告知用户的权衡

多步骤会带来重复编码的画质损耗累积（每次重新编码都是一次有损压缩）。执行组合请求前，需向用户说明这一点，让用户确认是否接受；不确认默认按上述顺序执行。

### 中间文件

命名建议 `<原文件名>.step1.<ext>`、`.step2.<ext>` 依次递增，产出目录与最终输出一致。全部步骤完成后询问用户是否保留中间产物，默认不保留。
