# known-issues

真实使用中暴露的问题记录。发现当下一行带过即可，不必整理成完整 bug report。"待处理"条目累积满 3 条时，发起一次 darwin-skill 优化循环（须人工在对话中显式发起）。已解决的条目改状态为"已优化"并标注版本号，**不删除**——保留可追溯的问题史。

| 日期 | 问题描述 | 触发场景/prompt | 状态 | 优化后版本 |
|---|---|---|---|---|
| 2026-09-01 | **「二次有损损失比首次明显」不成立**：judge 用 SDR 客观测量，首次有损 30.47 dB vs 二次有损 30.01 dB，**仅差 0.46 dB**。当前措辞会让 agent 向用户夸大风险。judge 建议的替换表述：转换会在已丢失细节的基础上再压一次，结果质量只会低于现有文件、不存在变好的可能；体积也不一定减小——目标码率高于源码率时反而会增大 | 有损→有损（如 mp3→aac）时向用户说明代价 | 已优化 | 1.0.1 |
| 2026-09-01 | **「无损→有损体积会明显减小」对 FLAC/ALAC 源为假**：实测 flac 44649 B → aac 73394 B（**涨 64%**）。该断言只对 PCM（wav）源成立，因为 FLAC/ALAC 本身已做无损压缩 | flac→mp3 / alac→aac 时向用户预告体积走向 | 已优化 | 1.0.1 |
| 2026-09-01 | **Step 4 探测未包含 `bit_rate`**——上面两条错误断言的共同根因。不知道源码率，就无法判断目标码率是升是降，只能给出方向固定的经验陈述 | 全部需重新编码的分支 | 已优化 | 1.0.1 |
| 2026-09-01 | **m4a→ADTS 会丢 gapless 元数据**，实测产物比源多 1844 个采样（含 1024 采样的 AAC priming），造成约 23 ms 起始偏移。文档在"编码相同仅容器不同"分支只写"无音质损失"，未提这一真实副作用 | `.m4a` 用 `-c:a copy` 转 `.aac` | 已优化 | 1.0.1 |
| 2026-09-01 | **「无损编码器不接受 `-b:a`，传入会报错」不实**：实测无报错、无警告，属纯 no-op（带与不带 `-b:a` 产物 MD5 完全相同）。judge 定性为"不防任何真实故障，属纯文档洁癖" | 转 flac/wav 时误传 `-b:a` | 已优化 | 1.0.1 |
| 2026-09-01 | **按扩展名 `.m4a` 硬编码推定目标编码为 AAC**：用户要求"wav 转 ALAC 存成 song.m4a"时，会被归类成「无损→有损」执行，并向用户播报错误的 CHECKPOINT 内容。`.m4a` 是容器，既可装 AAC 也可装 ALAC | 用户明确指定编码但用了通用容器扩展名 | 已优化 | 1.0.1 |
| 2026-09-01 | **视频输入拦不住**（与 media-audio-extract 的边界失明互为镜像）：`-select_streams a:0` 对含视频的文件同样正常返回音频 `codec_name`，与纯音频文件无法区分。"输入应为纯音频"这条边界只活在「不要做什么」的文字里 | 用户拿 mp4 要求"转成 mp3" | 已优化 | 1.0.1 |
