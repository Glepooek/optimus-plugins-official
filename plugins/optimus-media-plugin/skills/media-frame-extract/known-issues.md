> 以上 6 条均来自 2026-09-01 darwin-skill 基线评估（`eval_mode=full_test`，独立 judge 用真实 ffmpeg 样本实测），dim8 得 6/10。

> 同一轮评估**确认成立**的设计（无需改动）：
>
> 1. **不为 `-ss` 区分快速/精确双模式的论证正确。** judge 用 md5 三重对照（`-ss` 前置 / 后置 / 地面真值逐字节一致，均为 `21b23d41…`）+ GOP=15 样本复核 + `-noaccurate_seek` 反证（得到不同哈希）+ 长视频测速（120s 视频截 110.567s，前置 172ms vs 后置 1116ms，6.5×）验证：默认路径确实在做"seek 到关键帧后解码丢弃至目标时间戳"，既精确又快。judge 特别指出原样本整段只有 1 个关键帧，反而是验证"精确 seek"最强的条件——若只用该样本，"哈希相同"可能源于目标时间点恰好是关键帧这个平凡原因，故必须另造 GOP=15 版本才能排除。
> 2. **多帧模式选 `-vf fps=1/N` 而非 `-r` 正确。** 实测二者产出张数不同（`-r 0.5` 得 4 张、`-vf fps=1/2` 得 3 张）：前者在输出端丢帧（`drop=147`），后者在滤镜层按时间重采样。将来若有人试图"简化"成 `-r`，此处是反证。
>
> **两条错误描述的根因归因**：judge 指出"多帧输出会覆盖同一文件"是**旧版本 ffmpeg 的行为**，在当前构建（N-126086）image2 muxer 对非 pattern 文件名已改为只允许写一张、写第二张即硬失败。本 skill 的错误描述源自沿用这类流传说法而未实测——不是笔误，是靠文档推演写 skill 必然会踩的坑。修复时应以实测报错串为准。
