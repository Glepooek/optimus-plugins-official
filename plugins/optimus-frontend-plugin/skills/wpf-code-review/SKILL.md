# WPF 代码审查

## 概述

基于团队 WPF 开发规范集（[`knowledge-base/wpf/`](../../../../knowledge-base/wpf/00-README.md)）的系统化代码审查，覆盖架构、XAML、绑定、控件、线程、性能到异常/安全的全量维度。**核心原则**：通过全面的 checklist 驱动审查，确保不遗漏任何违规；规范不是约束，而是帮助团队写出一致、可维护、可扩展、可测的界面代码。

## 审查流程

先整体扫读把握结构，再**明确界定审查范围**，随后按用户场景在两档审查深度与两种输入模式中择一执行，最后统一输出报告：

1. **整体扫读（30 秒）**：先看整体结构和明显问题。
2. **确定审查范围**：按以下优先级收敛范围，**从窄到宽，除非用户明确要求，否则不越过当前层级**——
   - 用户已**明确指定**文件/目录/代码片段 → 就用它，绝不扩大
   - 用户指定了功能/模块但**未定位文件** → 用 Glob/Grep 定位到该模块相关文件
   - 未指定、但审查对象是**本次改动**（PR/合并前）→ 用 `git diff` 聚焦改动文件
   - 未指定且无改动上下文 → 收敛到用户提示中最相关的单点，并在报告中注明"本次只审了 X，需更大范围请指出"
3. **选择输入模式与审查档位**：
   - **输入模式**：粘贴代码片段 → 基于可见代码审查；扫描 → 仅按第 2 步确定的范围用 `Grep`/`Glob` 定位，**禁止无边界全仓 `Glob "**/*.xaml"`**
   - **审查档位**：
     - 时间紧迫 / 用户只求快速自查 → 走**快速初审**（1-2 分钟，见「快速初审」）
     - PR 合并前 / 用户要全面报告 → 走**完整审查**，逐项核对下方「审查清单」12 个类别（5-10 分钟）
4. **生成报告**：使用标准报告格式（见下方模板），报告"审查摘要"里注明本次实际覆盖的范围（文件/目录）。

## 范围护栏

审查范围必须可追溯、不肆意扩大：

- **先定边界再扫描**：任何 Glob/Grep 扫描前先确定目录边界。🔴 **CHECKPOINT**——确需全仓扫描时，须用户明确同意后才继续（默认只审第 2 步收敛出的范围，绝不擅自扩大到全仓）
- **单次审查文件数可控**：扫描文件过多（如约 20 个 XAML 相关文件以上）时，提示用户圈定更小范围，避免报告失控、耗时超预期
- **范围写进报告**：报告"审查摘要"需注明本次覆盖了哪些文件/目录，让用户明确知道审了哪些、未审哪些

## 报告格式

**务必使用此标准模板**，便于用户快速理解问题：

```markdown
# WPF 代码审查报告

## 审查摘要
- 审查范围：[文件/代码片段描述]
- 发现问题：[总数] 个
- 严重级别分布：🔴 严重 [X]个 / 🟡 重要 [X]个 / 🟢 建议 [X]个

## 问题清单

### 🔴 严重问题（必须修复）
[列出可能导致 bug、崩溃或严重违反规范的问题]

### 🟡 重要问题（建议修复）
[列出影响可维护性或明显违规的问题]

### 🟢 改进建议（可选）
[列出可以提升代码质量的建议]

## 修正后的代码
[提供完整的修正版本]
```

| 触发条件 | 一线处理 | 仍失败兜底 |
|---|---|---|
| 用户未提供代码，只是询问规范/建议本身 | 直接解答具体规范问题，不套用完整报告模板 | 若问题范围不清，询问用户想了解哪个类别 |
| 代码片段不完整（缺少上下文，如引用未定义的类型/资源） | 基于可见部分审查，报告中标注"因缺少上下文，以下判断基于可见代码" | 不臆测缺失部分的实现细节，只审查确实可见的代码 |
| 提供的代码不是 WPF（如 WinForms/纯 C# 无 UI/其他框架） | 明确提示"这不是 WPF 代码"，不强行套用 WPF 规则审查 | 若用户坚持要求，说明本 skill 规则不适用后停止，不产出误导性报告 |
| 代码完整核对 12 个类别后未发现任何违规 | 如实报告"发现问题：0 个"，说明已完整核对 12 个类别 | 不为了让报告显得"有产出"而编造 🟢 建议凑数 |
| 某问题的严重级别判定存在歧义（如"绑定路径过深"介于严重与重要之间） | 按"是否可能导致运行时错误/安全问题"区分：会导致 bug、崩溃、异常 → 🔴；仅影响可维护性/风格一致性，不会立即出错 → 🟡 | 若判定依据仍不充分，在该问题旁注明"级别存疑"并列出支持两种级别的理由，交由用户判断 |
| 修正代码用到了新语法/特性，但不确定目标框架版本 | 在修正代码旁注明该特性所需的最低 .NET/WPF 版本 | 若无法确认版本，额外提供兼容更早版本的替代写法 |
| 识别到疑似刻意为之的写法（如 TwoWay、DynamicResource） | 先说明"通常应为 X，但如果业务需要 Y，当前写法合理"，不要武断判定为错误 | 缺乏业务上下文时列入"需要确认的假设"而非既成事实 |

## 性能专项诊断速查

性能类问题（上方第 8 类）检查时，按以下检查点定位具体瓶颈。这些操作级模式对应 `rules/10-performance.md`：
- **数据绑定**：集合用 `ObservableCollection<T>`；常量/只读用 `OneTime`；绑定路径 ≤3 层；昂贵转换器缓存
- **虚拟化**：长列表开启虚拟化 + `VirtualizationMode="Recycling"`；确认数据量超出可视区再讨论；ItemTemplate 用轻量布局
- **图形渲染**：动态高频图形用 `DrawingVisual`/`DrawingGroup`；静态用 `Path`/`StreamGeometry`；循环外创建并 `Freeze()` Brush
- **启动时间**：`SplashScreen` + 延迟初始化（`Loaded` 异步、按需加载资源字典）
- **布局性能**：`Grid` 嵌套控制；动画用 `RenderTransform`；面板优先级 `Canvas > StackPanel > DockPanel > Grid`
- **资源**：默认 `StaticResource`，主题敏感才 `DynamicResource`；内联资源提为可共享资源
- **事件泄漏**：事件订阅配对取消（`Unloaded` / `WeakEventManager` / `IDisposable`）；禁止静态对象长期持有订阅者
- **UI 线程**：耗时操作 `async/await + Task.Run`；`Dispatcher.InvokeAsync` 替代同步 `Invoke`

## 快速初审

时间紧迫或用户只求快速自查时选用（1-2 分钟），是「审查清单」12 类里**最易出错、且不依赖上下文即可判断**的子集。覆盖 **#1 #2 #3 #4 #5 #7 #8**（其中性能相关点又见「性能专项诊断速查」）。未列入的类别多为依赖具体上下文或易被高频项顺带覆盖，时间紧时不必展开；出现可疑点可升级「审查清单」完整档复核。

1. **项目结构与 MVVM**（#1）：View 无 code-behind 业务逻辑；ViewModel 用 `INotifyPropertyChanged` 通知
2. **XAML 资源**（#2、#5）：资源用 `StaticResource`（非无理由 `DynamicResource`）、`x:Key` 唯一、命名规范
3. **数据绑定**（#3）：集合用 `ObservableCollection`；绑定路径 ≤3 层；只读展示用 `OneWay`/`OneTime` 非 `TwoWay`
4. **控件与依赖属性**（#4）：依赖属性有 `PropertyChangedCallback`；附加属性命名规范
5. **线程**（#7）：UI 元素只在 UI 线程访问；后台更新 UI 走 `Dispatcher`；无同步 `Invoke` 死锁
6. **性能**（#8）：长列表虚拟化 + `Recycling`；循环外 `Freeze()` 共享 Brush；无 `BitmapEffect`；事件订阅已取消

## ⛔ 不要做什么（反例黑名单）

| 反模式 | 原因 | 替代做法 |
|---|---|---|
| 代码本身已合规时，为了让报告"显得有产出"而编造或吹毛求疵到无意义程度的违规 | 制造噪音，浪费用户时间去反驳不成立的问题，损害审查报告的可信度 | 如实报告"发现问题：0 个"，只列出真正命中审查清单类别的违规 |
| 只审查性能类问题（#8），忽视其他类别（#1-7、#9-12） | WPF 的全量规范不止性能，只查性能会漏掉架构、绑定、线程、异常等关键问题 | 审查清单 12 类逐一核对，不能因为某类已发现问题就跳过其他类别 |
| 严重级别凭直觉打分，不说明判定依据 | 同一问题在不同执行中被判成不同级别，报告不可复现、不可信任 | 套用"会导致bug/崩溃/异常/安全漏洞→🔴，仅影响可维护性/风格→🟡"的二分测试，并在报告中说明判定理由 |
| 代码片段明显不完整（引用了未定义的类型/资源）时，臆测缺失部分并据此下结论 | 基于猜测的审查结论可能完全偏离真实代码，误导用户做出错误修改 | 只审查确实可见的代码，在报告中注明"因缺少上下文，以下判断基于可见代码" |
| 报告只给问题清单，省略"修正后的代码"部分 | 报告格式模板明确要求提供修正版本，用户往往需要直接参考可用的正确写法 | 即使问题很少，也提供完整的修正后代码块，哪怕改动只有一两行 |
| 把仅影响风格一致性的 🟢/🟡 问题包装成"必须修复"的阻塞项 | 过度严格会让代码审查变成摩擦源，团队会开始抵触甚至绕过这个 skill | 严格按报告模板的三级分类展示，只有 🔴 才标注"必须修复"，🟡/🟢 保持"建议"措辞 |
