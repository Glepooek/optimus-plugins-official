## 验证单位的选择（先于三重验证的结构决策）

阶段 0 已估算"约 8 个 skill"，且用户已确认这个方向。阶段 1 产出的 16 条 framework
候选彼此天然聚合成 8 个主题簇，与 36 条 principle、22 条 case、23 条 counter-example
逐一对应（详见下方每个 skill 的"合并证据"）。因此本轮三重验证**以簇（未来的 skill）
为验证单位**，而不是对 117 条候选逐条孤立打分——原因：

- principle/case/counter-example 三类候选在提取阶段就被要求填 `bound_to` 字段，
  设计上就是"依附于某个 framework 的证据"，不是竞争独立 skill 地位的单元；
  单独对它们跑 V1（跨域）没有意义，它们本身就是跨域证据的来源。
- glossary（20 条术语）在阶段 0 已被明确排除在"可 skill 化"范围之外
  （"提供不适合skill化的内容"），只汇入 `GLOSSARY.md`，不参与本轮通过/淘汰判定。

## 通过标准的适用范围说明

三重验证以"框架簇"（未来的 skill）为验证单位，而非对 117 条候选逐条判定，理由见上一节。
36 条原则、22 条案例、23 条反例的角色是"证据"而非"待裁决的独立主张"——它们在提取阶段
就被 extractor 要求填 `bound_to` 指明所属框架，设计上不参与独立的 V1 跨域检验。117 条候选
的"通过率"因此不适用阶段 1.5 文档中"30–80% 健康区间"这一针对独立候选单元的经验值；
本次实际的验证颗粒度（8 个候选 skill 全部通过）与"一本方法论/实操密度极高的工程手册"的
预期相符，不构成"验证标准过松"的信号——过松的风险点应落在"这 8 个框架本身是否真的各自
独立、值得单开一个 skill"，而这正是下面逐一执行 V1/V2/V3 的对象。

```yaml
  passed: true

    用框架 f02（空间换时间权衡）+ 原则 p06（双向队列可替代栈实现有限深度撤销）可以推导：
    这本质是"栈的后进先出语义 + 栈底淘汰需求"的组合，普通栈无法从栈底删除，需要用双向队列
```

```yaml
    退化反例都指向不同的根本机制（划分不均 vs 递归深度 vs 值域失配），跨域证据充分。
V2_predictive_power:
  passed: true
  novel_question: |
    "要对一个日志系统里的十万条记录先按用户ID排序、再按时间戳排序，该注意什么？"
    （书中没有直接讨论"日志系统"这个场景）
  derived_answer: |
    用 f05（五维评价体系）中的稳定性维度 + p21（稳定排序是多级排序必要条件）可推导：
    第二次按时间戳排序必须选稳定算法（归并/插入/计数），否则第一次按用户ID排好的组内顺序
    会被打乱——这是把书中"姓名+年龄"的教学案例迁移到"用户ID+时间戳"的具体工程场景。
V3_exclusivity:
  passed: true
  why_not_common: |
    "快排平均更快"是通识；但"为什么更快"（缓存局部性 + 常数系数最小 + 最差情况概率低，
```

```yaml
id: skill-05

type: skill

  cases: [c17, c18, c22]

  evidence:
    - 归并排序（对半均分）与汉诺塔问题（c17，(n-1)+(n-1)+1 非均分）两个结构完全不同的分解方式，
      都满足同一套三条件判据，证明该判据不依赖具体分解形态
    - 构建二叉树问题（c18）额外揭示"子问题划分本身的计算开销也需要被优化"这一独立教训
    - 二分查找的分治重新诠释（c22，来自 cases.md）证明该判据同样适用于"子问题无须合并"的
      特例场景，即三条件中的"合并"允许退化为空操作
  independence_check: |
    汉诺塔、构建二叉树、二分查找三个应用案例分别来自第12章不同小节，且三者的子问题分解形态
    彼此差异很大（对半/不均分/无需合并），不是同一个例子的重复。
V2_predictive_power:
  passed: true
  novel_question: |
    "要计算一个数组所有元素两两之间的最大差值，能用分治吗？"（书中未直接讨论此问题）
  derived_answer: |
    用三条件自检（f03）：可分解（拆两半分别求最大最小值）、子问题独立（左右两半互不依赖）、
    可合并（合并时需额外比较跨越左右两半的情况，例如左边最小值与右边最大值之差）——三条件
    均满足，可用分治，但需注意合并步骤不是简单拼接而要额外处理跨界情况，这正是三条件自检法
    "合并方式需要具体设计"这一隐含要求的体现。
V3_exclusivity:
  passed: true
  why_not_common: |
    "分而治之"是日常语言中的泛义说法（任何拆分问题的做法都可以自称分治）；本书把它收紧为
    一个精确的三条件判据，尤其是"子问题必须相互独立"这一条——这正是区分分治与动态规划的
    分水岭，普通人凭直觉不会意识到"能拆成子问题"和"能用分治"之间还有一个必要条件的缺口。
verdict: PASS → 进入阶段 2
```

```yaml
id: skill-06

    - 子集和问题（c20）：start 指针剪枝——排除"选择顺序不同但结果相同"的重复分支
    - N 皇后问题（c21）：逐行放置+列/对角线数组剪枝——排除"结构性冲突"分支
    三个应用场景的剪枝对象完全不同（非法性/重复性/结构冲突），都统一套入"尝试-剪枝-回退"
    这一同一个框架，证明该框架的跨场景适用性不是巧合。
V2_predictive_power:
  passed: true
  novel_question: |
    "要生成一个数独的所有合法填数方案，能不能用同一套'状态/选择/剪枝'框架？"
    （书中没有直接讨论数独问题）
  derived_answer: |
    可以：状态=当前棋盘填数情况，选择=当前空格可填的候选数字（1-9），合法性检查（剪枝）=
    同行同列同宫是否已存在该数字。这与 N 皇后的"列约束+对角线约束"结构高度同构，只是
    约束规则从"行列对角线"换成了"行列宫格"，验证了框架的抽象层级足够高、可正确迁移到
    书中未提及的新问题。
V3_exclusivity:
  passed: true
  why_not_common: |
    "回溯就是试错加回退"是模糊直觉；本书把它精确到"状态/选择/剪枝/解的判定"四要素框架，
    且明确澄清"回溯是算法策略、递归只是实现工具"这一层次区分——很多人会把"用递归写的搜索"
    和"回溯"混为一谈，本书的四要素分解与澄清具有独特性。
verdict: PASS → 进入阶段 2
```
