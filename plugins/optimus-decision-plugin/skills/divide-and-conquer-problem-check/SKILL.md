# 分治问题判断

<!-- 蒸馏来源：《Hello 算法》(Hello Algo) krahets，第 12 章 · 分治。verified.md skill-05。 -->

## R — 原文 (Reading)

> "问题可以分解……子问题是独立的……子问题的解可以合并。"
>
> — krahets，《Hello 算法》第 12 章 · 分治

## I — 方法论骨架 (Interpretation)

判断一个问题是否适合用分治策略求解，可用三条件自检：原问题能否递归分解为规模更小、结构相似的子问题；子问题之间是否相互独立（无重叠、不依赖彼此的中间结果）；子问题的解能否合并还原为原问题的解。三者同时满足才是"纯"分治问题。三条件中最关键、也最容易被误判的是"子问题独立"——如果这一条不满足（子问题相互重叠、依赖），就应该转向动态规划而非分治，这是分治与动态规划最核心的分界判据，也是区分两者的分水岭。

一个常见误区是以为分治必须"对半均分"，但书中明确展示分解方式不必均分——只要满足三条件，无论是对半分（归并排序）还是不均分（汉诺塔的 (n-1)+(n-1)+1）都算合规分治。另一个容易被忽视的点是：三条件中的"合并"允许退化为空操作（如二分查找不需要合并子问题的解），且子问题划分本身的计算开销也需要被优化——如果每次划分子问题都需要额外的线性扫描（如从遍历中定位分界点），这个开销会累积拖累整体复杂度，需要用哈希表等手段加速定位。

## A1 — 书中的应用 (Past Application)

### 案例 1: 汉诺塔问题——非均分分解仍满足分治三条件
- **问题**：汉诺塔问题（n个圆盘的移动）如何用分治求解，其分解方式与归并排序的"对半均分"完全不同。
- **方法论的使用**：作者把问题 f(n) 划分为两个子问题 f(n-1) 和一个子问题 f(1)，按固定顺序解决三者后原问题即解决，验证三条件（可分解、子问题独立、解可合并）依然全部满足。
- **结论**：分治的分解方式不必对半均分，可以按问题结构灵活设计，这是分治"不必对半分解"的典型反例式教学。
- **结果**：递归树高度为 n，时间复杂度 O(2^n)，印证了作者引用的"64个圆盘需约5850亿年"的传说计算。

### 案例 2: 前序中序遍历构建二叉树——用哈希表消除子问题划分的额外开销
- **问题**：从前序+中序遍历构建二叉树时，每层递归都需要在中序遍历中查找根节点位置来划分左右子树区间，如果每次线性扫描会引入额外 O(n) 开销。
- **方法论的使用**：作者预先用哈希表建立"元素值→索引"的映射，把查找操作降至 O(1)，使整体递归时间复杂度维持在 O(n) 而非退化到 O(n²)。
- **结论**：分治问题中，子问题划分本身的计算开销也需要被优化，不能假设"划分免费"。
- **结果**：这展示了分治实现的一个容易被忽视的工程细节——三条件自检只保证"策略上适用"，实现时仍需为划分步骤本身做效率优化。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 面对一个可以递归拆解的问题，不确定子问题之间是否真的相互独立，还是存在重叠依赖
2. 已经写出递归分解的代码，但性能远低于预期，怀疑是子问题划分本身引入了额外开销
3. 纠结一个新问题该用分治还是动态规划——问题表面上"可以拆子问题"，但不确定该选哪种范式
4. 需要为一个自定义的分解策略（非对半均分）验证是否仍然合规
5. 面对"子问题的解需不需要合并"这类边界判断（如二分查找是否算分治）

### 语言信号 (用户的话里出现这些就应激活)

- "这个问题能用分治解吗" / "can I use divide and conquer here"
- "子问题需要合并吗" / "do the subproblems need to be merged"
- "分治和动态规划该怎么区分" / "how to distinguish divide and conquer from dynamic programming"
- "子问题之间是不是独立的" / "are these subproblems really independent"
- "划分子问题的时候要不要优化查找开销" / "should I optimize the subproblem partitioning cost"

### 与相邻 skill 的区分

- 与 `dynamic-programming-problem-solving` 的区别：分治要求子问题相互独立、无重叠；若子问题存在重叠依赖，应转向动态规划而非本skill——这是两者最核心的分野，遇到"看起来能拆但不确定该用哪个"的问题应先用本skill的三条件自检排除，若"独立"这一条不满足再转交对方。
- 与 `backtracking-algorithm-template` 的区别：回溯把解看作一系列决策步骤的产物，通过尝试与回退穷举决策树上所有路径；分治要求子问题能够独立求解后直接合并，不需要"回退"这一动作，两者对子问题关系的假设完全不同。

## E — 可执行步骤 (Execution)

1. **核对可分解性**
   - 完成标准：确认原问题能否递归分解为规模更小、结构相似的子问题
   - 判停条件：若无法分解，本skill不适用，跳到步骤 4 说明结论

2. **核对子问题独立性（关键判据）**
   - 完成标准：检查子问题之间是否存在重叠或相互依赖（可用画递归树的方式验证是否有重复调用相同参数的子问题）
   - 判停条件：若子问题相互重叠依赖，判定分治不适用，建议转向 `dynamic-programming-problem-solving`，不再继续本skill后续步骤

3. **核对是否为回溯式穷举决策树模式**
   - 完成标准：检查问题是否需要"尝试候选解、遇到不合法/不优时回退撤销再尝试其他分支"这一穷举模式（常见于排列、组合、子集、约束满足类问题），而非"子问题各自独立求解后合并"
   - 判停条件：若问题本质是决策树上的试探+回退穷举（而不是可独立求解的子问题），判定分治不适用，建议转向 `backtracking-algorithm-template`，不再继续本skill后续步骤——这一判停条件与步骤2对动态规划的判停条件对称设计，因为"子调用参数不重复"（步骤2会判定为独立）不代表就适合分治，穷举决策树的分支同样互不重复参数，但需要试探+回退而非独立求解

4. **核对是否可合并及合并开销**
   - 完成标准：确认子问题的解能否合并还原为原问题的解（允许合并退化为空操作，如二分查找）；同时检查子问题划分本身是否存在额外的计算开销（如需要额外查找定位分界点），若有，评估是否需要引入哈希表等手段优化

5. **输出结构化建议**
   - 完成标准：给出"是否适用分治的结论 + 三条件核对依据 + 若子问题独立性不满足或实为穷举决策树时的替代方案（分别转向动态规划/回溯）"

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户已经确定要用分治，只是想要具体某语言的代码实现，而非适用性判断
- 用户只是询问某个具体分治算法（归并排序、快速排序等）本身的实现原理，而非"该不该用分治"的决策问题
- 问题本质是穷举所有满足约束的方案/排列/组合，需要试探+回退而非独立求解后合并——即使子调用参数互不重复、表面满足"子问题独立"，也应转向 `backtracking-algorithm-template` 而非本skill

### 作者在书中警告的失败模式

- 看到一个问题"可以递归拆解为子问题"就直接套用分治思路（各子问题独立求解后合并），但如果子问题之间实际存在重叠（如爬楼梯、背包问题），按分治方式实现会导致大量重复计算，时间复杂度从动态规划的多项式阶劣化为指数级 O(2^n)，且这种低效在小规模输入下不易察觉
- 每层递归都对子问题划分做线性扫描定位分界点，未意识到这个"划分开销"会累积拖累整体复杂度，导致总体从预期的 O(n) 退化为 O(n²)

### 作者的盲点 / 时代局限

- 全书对"子问题独立"这一判据主要通过具体案例（归并排序、汉诺塔、二分查找）建立直觉，未给出一个可操作的通用检验步骤（如递归树画图法），读者面对结构更复杂的新问题时容易在"看起来独立"和"实际独立"之间产生误判

### 容易混淆的邻近方法论

- `dynamic-programming-problem-solving`：子问题独立（分治）vs 子问题重叠依赖（动态规划），是两者最核心的分野，也是本skill执行流程中判停条件的直接依据
