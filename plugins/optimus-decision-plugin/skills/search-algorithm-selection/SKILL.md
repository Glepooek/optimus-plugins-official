# 搜索算法选型

<!-- 蒸馏来源：《Hello 算法》(Hello Algo) krahets，第 10 章 · 搜索。verified.md skill-04。 -->

## I — 方法论骨架 (Interpretation)

搜索算法选型不能只看渐近时间复杂度的高低，而要在一张多维表格上综合比较：查找/插入/删除效率、额外空间开销、数据预处理成本、是否要求数据有序。二分查找看似"渐近最优"，但它有三个具体局限——依赖跳跃式随机访问（只能用在数组上，链表不适用）、要求数据预先有序（若数据本身无序，专门排序的 O(n log n) 开销可能比直接线性查找还贵）、每轮需要 4~6 个单元操作（数据量很小时这个常数开销反而让线性查找更快）。这三个局限共同说明"渐近更优"不等于"总是更优"。

在存储结构已确定为哈希表或树结构之后，还要在哈希查找和树查找之间取舍：哈希查找平均 O(1)，适合只追求精确查询、不需要有序遍历或范围查询的场景，但存在冲突退化风险；树查找（AVL/红黑树）是 O(log n)，适合需要维护有序数据、支持范围查询、且数据量巨大的场景。判断依据很简单：只需精确查找用哈希表，需要有序或范围查询用平衡树。

## A1 — 书中的应用 (Past Application)

### 案例 1: 两数之和——用哈希表替代线性查找
- **问题**：暴力枚举两层循环求两数之和，时间 O(n²)、空间 O(1)，大数据量下耗时严重。
- **方法论的使用**：引入一个"元素值→索引"的哈希表映射，把查找操作从 O(n) 降到 O(1)，整体降为单层循环 O(n)。
- **结论**：这是"以空间换时间"策略最直接的收益体现——用 O(n) 额外空间换取时间复杂度降一个数量级。
- **结果**：作者明确指出在可接受额外空间开销的前提下，这是该题的最优解法，是"搜索算法选择"框架具体落地为可执行工程决策的示范。

### 案例 2: 二分查找的三个适用局限
- **问题**：工程师容易看到"O(log n) 比 O(n) 快"就默认二分查找永远优于线性查找。
- **方法论的使用**：作者逐一拆解二分查找依赖的前提——有序性、数组存储、数据规模足够大——任一前提不满足，二分查找的理论优势就会被抵消甚至反转。
- **结论**：小数据量、链表存储、频繁更新且无法低成本维护有序性的场景，都应该反过来选线性查找。
- **结果**：这条边界判断成为后续所有"是否要为了用二分查找而付出额外成本"决策的判据来源。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 数据存储结构已确定（数组/哈希表/树），需要判断在其上该用哪种查找算法
2. 纠结"要不要为了能用二分查找，专门维护一份有序索引"，尤其是数据频繁更新的场景
3. 数据规模较小（几十到几百个元素），怀疑"渐近更优的查找算法"实际反而更慢
4. 在哈希查找和树查找之间犹豫，尤其是涉及"要不要支持范围查询/有序遍历"的需求
5. 遇到查找性能问题，怀疑是查找算法与数据结构/规模不匹配导致的选型错误

### 语言信号 (用户的话里出现这些就应激活)

- "该用二分查找还是线性查找" / "binary search or linear search"
- "要不要为了查找快维护有序索引" / "should I maintain a sorted index just for binary search"
- "哈希查找和树查找该选哪个" / "hash lookup vs tree lookup"
- "数据量很小，二分查找是不是反而更慢" / "is binary search overkill for small data"
- "配置中心几十个key，要不要建索引" / "is an index worth it for a few dozen keys"

### 与相邻 skill 的区分

- 与 `data-structure-selection` 的区别：本 skill 的前提是存储结构已经确定，回答"在已确定的结构上该用什么算法找数据"；若存储结构本身尚未确定，应先触发 `data-structure-selection`。两者常在"存了之后怎么快速查"这类跨界问题中连续触发。
- 与 `sorting-algorithm-selection` 的区别：本 skill 判断"是否值得为了二分查找而排序"这一决策，依赖对方的排序成本评估作为输入，但本 skill 关注查找侧的收益，后者关注排序本身的选型。

## E — 可执行步骤 (Execution)

1. **确认存储结构与数据特征**
   - 完成标准：明确以下三项——当前存储结构（数组/链表/哈希表/树）、数据规模量级、更新频率（是否频繁增删）
   - 判停条件：若存储结构尚未确定，跳过本 skill 的后续步骤，转交 `data-structure-selection`

2. **核对二分查找的三个前提**
   - 完成标准：检查是否同时满足——数据存储在数组中（非链表）、数据已经有序或可低成本维护有序、数据规模足够大以抵消二分查找的常数开销；三者全部满足才考虑二分查找，否则默认线性查找

3. **在哈希查找与树查找之间取舍（若涉及哈希表/树结构）**
   - 完成标准：只需精确查找、不需要有序遍历或范围查询 → 哈希查找；需要维护有序数据或支持范围查询 → 树查找（AVL/红黑树，避免普通 BST）

4. **输出结构化建议**
   - 完成标准：给出"查找算法结论 + 判断依据（前提是否满足） + 若数据规模/更新频率变化会如何调整结论"

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户在做面试刷题式提问，要求"实现一个二分查找"而非选型决策——这类问题应直接给出实现代码
- 用户已经明确指定必须使用某种查找算法，选型决策已经不存在
- 存储结构本身尚未确定，此时应先触发 `data-structure-selection` 确定容器，再回到本 skill 判断查找算法

### 作者在书中警告的失败模式

- 为了能用二分查找专门对一份无序数据排序，排序本身 O(n log n) 的开销比直接线性查找还贵
- 把二分查找用在链表或频繁插入的场景，插入需保持有序需 O(n)，得不偿失
- 对几十个元素的小数组也套二分查找，单轮判断次数（4~6 个单元操作）反而比线性查找（1 次判断）慢

### 作者的盲点 / 时代局限

- 全书对"何时数据规模算大到值得用二分查找"没有给出具体的数值临界点，只给出方向性判断，实际工程中该临界点因语言/硬件而异，需要读者自行测量而非照搬书中结论

### 容易混淆的邻近方法论

- `data-structure-selection`：数据结构选型是本 skill 决策的前提，两者常连续触发但决策对象不同（存储容器 vs 查找算法）
