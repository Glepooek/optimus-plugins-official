## I — 方法论骨架 (Interpretation)

回溯问题表面各异（全排列、子集和、N皇后），但都可以套入同一个通用骨架：给定当前状态 state 和可选集合 choices，先判断 state 是否已构成解，否则遍历每个选择，对每个选择先做合法性检查（剪枝），若合法则"尝试"（更新状态并递归），递归返回后再"回退"（撤销状态更新，恢复到尝试前）。面对新的搜索/约束满足问题，先分别定义清楚"状态""选择集合""解的判定条件""合法性检查（剪枝规则）"这四个要素，再套用统一框架实现，比从零设计专用递归结构更省心也更不容易漏边界条件。

剪枝不只是效率优化手段，更重要的作用是提前排除"根本不满足题意的非法分支"——它消除的不是"较差的解"，而是"不合法的搜索路径"。回溯本质是DFS+穷举，处理大规模问题时复杂度可能达到指数阶或阶乘阶，因此当必须使用回溯时（因无法预测哪些分支能产生有效解，必须遍历），应优先加入剪枝逻辑尽早排除明显不可能产生解的分支；若剪枝仍不够，可引入启发式估计值优先探索最可能成功的路径。同时要清楚回溯的适用边界：对于有明确最优子结构和重叠子问题的组合优化问题（如0-1背包），动态规划效率远高于回溯；对于NP-Hard级别问题（旅行商问题），穷举回溯根本无法在可接受时间内求解，应改用启发式/近似算法。

## A1 — 书中的应用 (Past Application)

### 案例 1: 全排列问题——selected 数组剪枝把搜索空间从 O(n^n) 降至 O(n!)
- **问题**：未加剪枝的全排列搜索每一轮都从完整候选集合中选择，导致搜索树分支因子恒为n、深度为n，形成O(n^n)的搜索空间，但全排列要求每个元素只能用一次。
- **方法论的使用**：引入一个 selected 布尔数组记录哪些元素已被选过，遍历候选列表时跳过已选元素。
- **结论**：这个剪枝直接把搜索空间从O(n^n)削减到O(n!)，它去掉的不是"较差的解"，而是"根本不满足题意（重复选择同一元素）的非法分支"。
- **结果**：这是"剪枝不只是加速，而是消除本质上不合法的搜索分支"的典型例证，n=10时搜索空间从10^10降至约3.6×10^6，降低约4个数量级。

### 案例 2: N皇后问题——逐行放置策略与列/对角线数组剪枝
- **问题**：若不加约束地在n×n棋盘所有格子中选择n个皇后位置，搜索空间是组合数级别的爆炸增长。
- **方法论的使用**：作者通过观察问题结构（每行只能放一个皇后）设计"逐行放置"策略直接编码进搜索框架，再针对列约束和对角线约束设计辅助布尔数组（cols记录列占用，diags1/diags2利用"同一对角线上格子的row-col或row+col恒定"这一数学规律记录对角线占用），实现O(1)冲突检测。
- **结论**：这是"通过对问题几何/组合结构的分析设计专用剪枝数据结构"的典型案例，体现了如何把抽象约束转化为可O(1)判断的具体数据结构。
- **结果**：逐行放置将搜索空间从组合爆炸降至O(n!)，加上对角线剪枝后实际搜索效率通常优于该理论上界。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 面对一个"求所有满足约束的方案"类问题（排列组合、子集、路径配置），不确定该怎么设计状态和选择集合
2. 已经用回溯实现了一个搜索，但效率不理想，想知道该怎么设计剪枝逻辑
3. 需要判断一个组合优化问题是该用回溯穷举，还是有更适合的算法（DP/启发式）
4. 面对一个新的约束满足问题（如数独），想知道能否复用已有的"状态/选择/剪枝"框架
5. 回溯实现出现重复解或漏解，需要排查是状态设计还是剪枝逻辑的问题

### 语言信号 (用户的话里出现这些就应激活)

- "这个问题怎么用回溯解" / "backtracking template for this problem"
- "怎么设计剪枝逻辑" / "how to design pruning logic"
- "回溯效率太低怎么优化" / "my backtracking solution is too slow"
- "这个约束满足问题能套回溯框架吗" / "can I apply the backtracking framework here"
- "回溯出现重复解/漏解了" / "my backtracking produces duplicate or missing solutions"

### 与相邻 skill 的区分

- 与 `dynamic-programming-problem-solving` 的区别：若问题目标是求单一最优解（而非穷举所有方案）且具备重叠子问题/最优子结构/无后效性，动态规划效率远高于回溯，应优先转向对方；回溯更适合"求所有解"或"是否存在解"类问题。
- 与 `divide-and-conquer-problem-check` 的区别：分治要求子问题独立求解后合并，不涉及"尝试-回退"；回溯把解看作一系列决策步骤的产物，通过尝试与回退穷举决策树上的所有路径，两者对子问题关系的假设完全不同。

## E — 可执行步骤 (Execution)

1. **定义四要素**
   - 完成标准：明确"状态"（state，问题当前进展）、"选择集合"（choices，当前状态下可做的选择）、"解的判定条件"（何时认为state已构成一个完整解）、"合法性检查规则"（剪枝依据）

2. **判断是否该用回溯而非其他范式**
   - 完成标准：确认问题目标是求所有可行方案或判断解是否存在（适合回溯），而非求单一最优解（若具备重叠子问题/最优子结构/无后效性，优先转向动态规划）
   - 判停条件：若目标是求最优解且满足DP三大特性，跳到步骤 4 建议转向 `dynamic-programming-problem-solving`

3. **套用尝试-剪枝-回退框架并设计剪枝规则**
   - 完成标准：按框架实现——遍历每个选择，先做合法性检查（剪枝），合法则尝试（更新状态+递归），递归返回后回退（撤销状态更新）；剪枝规则应基于"排除根本不合法的分支"设计（如selected数组防重复选择、start指针防重复子集、列/对角线数组防结构冲突），而非事后对结果去重

4. **评估规模上限并决定是否需要启发式优化**
   - 完成标准：估算解空间随输入规模的增长阶数（指数/阶乘），若生产规模会超出可接受时间，建议引入启发式估计值优先搜索最可能成功的路径，或评估是否该改用DP/近似算法

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户已经确定要用回溯，只是想要具体某语言的代码实现，而非框架设计判断
- 问题目标是求单一最优解而非穷举所有方案，且具备重叠子问题/最优子结构/无后效性——这类问题应优先转向动态规划

### 作者在书中警告的失败模式

- 用回溯/穷举解决排列组合类问题时，只在小规模测试数据（几个到十几个元素）下验证过，未评估复杂度阶数随规模的增长曲线，一旦规模增大（如从10个选项变为20个），指数级/阶乘级增长会导致运行时间从秒级暴增到不可接受
- 面对组合优化问题（0-1背包、旅行商、最大团），因回溯"思路直观、容易实现"而直接采用，跳过了"是否存在更适合的算法（DP/启发式/近似算法）"的调研步骤，导致方案功能正确但性能远低于可达到的水平
- 用"事后对结果列表去重"处理重复解问题，而非在搜索过程中用剪枝在源头避免生成重复分支，效率低且随数据规模增大代价更高

### 作者的盲点 / 时代局限

- 全书对"回溯是算法策略、递归只是实现工具"这一层次区分有明确澄清，但对"如何针对全新问题结构设计专用剪枝数据结构"（如N皇后的对角线数组）更多依赖具体案例演示，没有给出一般性的设计方法论，读者面对结构差异较大的新约束满足问题时仍需要较强的类比迁移能力

### 容易混淆的邻近方法论

- `dynamic-programming-problem-solving`：求所有解/判断解是否存在（回溯）vs 求单一最优解且满足三大特性（动态规划），是两者最核心的分野
