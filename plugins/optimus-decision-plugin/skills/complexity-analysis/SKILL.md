# 复杂度分析方法

<!-- 蒸馏来源：《Hello 算法》(Hello Algo) krahets，第 2 章 · 复杂度分析。verified.md skill-02。 -->

## R — 原文 (Reading)

> "最差时间复杂度更为实用，因为它给出了一个效率安全值，让我们可以放心地使用算法。"
>
> — krahets，《Hello 算法》第 2 章 · 复杂度分析

> "我们通常只关注最差空间复杂度。这是因为内存空间是一项硬性要求，我们必须确保在所有输入数据下都有足够的内存空间预留。"
>
> — krahets，《Hello 算法》第 2 章 · 复杂度分析

---

## I — 方法论骨架 (Interpretation)

复杂度分析不是给代码贴一个"O(...)"标签就完事，而是要先回答"用哪种复杂度视角"这个前置问题，因为时间复杂度天然有三副面孔：最佳情况（输入对算法最有利，几乎不用于工程决策）、最差情况（输入最不利，是效率的"下限保证"）、平均情况（更贴近真实分布，但推导难度大）。工程决策时该用哪个，取决于场景的性质：如果系统对延迟有硬性上限（SLA、支付网关、实时系统），必须以最差复杂度为依据，因为它保证"任何输入都不会比这更慢"；如果追求的是吞吐/均摊表现，平均复杂度更有参考价值；最佳复杂度仅用于判断算法是否具备"自适应性"。

空间复杂度分析则不做这个三视角区分，永远只看最差情况——原因是内存分配是硬性约束，一旦某次运行超出可用内存就直接崩溃，不像时间超预期"慢一点也能忍"。这个不对称处理本身就是一个反直觉的洞察：时间维度允许"看运气"，空间维度必须"按最坏打算"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三种时间复杂度视角在工程决策中的取舍
- **问题**：同一个算法在不同输入下运行时间差异很大，只报告单一数字会误导决策。
- **方法论的使用**：作者区分最佳/最差/平均三种复杂度，并明确指出"最差时间复杂度最常用"，因为它是"效率安全值"。
- **结论**：工程决策应默认以最差复杂度为基准，平均复杂度作为补充参考，最佳复杂度基本不用于选型。
- **结果**：这条区分成为全书后续所有算法选型讨论（排序、搜索、DP）的隐含前提——凡涉及"哪个方案更快"的讨论，都是在最差或平均复杂度的框架下比较。

### 案例 2: 空间复杂度分析的不对称处理
- **问题**：如果空间复杂度也按最佳/平均/最差三视角分析，会引入不必要的复杂度且没有工程价值。
- **方法论的使用**：作者直接指出空间复杂度只统计最差情况，因为内存超限是硬性崩溃而非"变慢"。
- **结论**：容量规划、内存预算评估必须按最差输入和运行峰值预留空间，不能按平均情况估算。
- **结果**：这一原则在后续案例（如快速排序递归深度优化）中被反复应用——即便平均空间复杂度低，只要最差情况可能栈溢出，就必须做工程加固。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 在两个及以上实现方案之间做选型，需要判断"哪个方案更适合当前场景"，而不是单纯"哪个复杂度数字更小"
2. 系统存在明确的延迟 SLA 或硬性响应时间要求，需要判断该以哪种复杂度视角评估候选方案
3. 做内存容量规划或预算评估，不确定该按最差、平均还是峰值场景估算
4. 怀疑某个方案"理论复杂度低但实际很慢"或"理论复杂度高但实际够快"，想搞清楚复杂度分析本身的局限
5. 在评审/设计阶段需要为"选 X 方案而非 Y 方案"给出可辩护的复杂度依据

### 语言信号 (用户的话里出现这些就应激活)

- "这个方案的时间复杂度该怎么评估" / "how should I evaluate the time complexity here"
- "该用最差情况还是平均情况来判断" / "worst case vs average case for this decision"
- "为什么空间复杂度只看最差情况" / "why does space complexity only consider worst case"
- "这两个方案哪个更适合有延迟要求的场景" / "which is better under a hard latency SLA"
- "复杂度看起来更优但实际跑起来更慢，为什么" / "lower big-O but slower in practice"

### 与相邻 skill 的区分

- 与 `data-structure-selection` / `sorting-algorithm-selection` 等具体选型 skill 的区别：本 skill 回答"该用哪种复杂度视角来评估/比较方案"这一更底层的方法论问题，后续 7 个 skill 的选型结论都建立在本 skill 的判断之上——遇到"该选什么结构/算法"的具体决策问题时，应先用本 skill 确认评估视角，再交给对应的选型 skill 给出结论。
- 与纯粹"帮我算一下这段代码的大 O"式提问的区别：本 skill 面向的是"评估视角该如何选择"的工程决策，不是"如何从代码推导出复杂度表达式"这类纯技术性计算——后者属于 Boundary 中明确排除的场景。

## E — 可执行步骤 (Execution)

1. **判断决策场景的性质**
   - 完成标准：明确以下三项——是否存在硬性延迟/内存上限（SLA、崩溃风险）、追求的是单次响应速度还是长期吞吐/均摊表现、当前讨论的是时间复杂度还是空间复杂度
   - 若用户未说明场景性质，先询问这三项而非直接给出复杂度数字

2. **选定复杂度评估视角**
   - 完成标准：时间维度——存在硬性延迟要求 → 用最差复杂度；追求吞吐/均摊 → 用平均复杂度；判断算法是否有自适应性 → 参考最佳复杂度。空间维度——恒定使用最差复杂度，不做三视角区分
   - 判停条件：若用户只是要求"帮我推导这段代码的复杂度表达式"（无选型决策诉求），跳过本步骤和步骤 3，直接给出推导过程

3. **交叉核对大 O 的局限性**
   - 完成标准：若讨论涉及"理论上更优的方案实际表现更差"的疑惑，提示大 O 只刻画渐近增长趋势，忽略常数项、缓存命中率、分支预测等实际因素（对照 Boundary 段说明）

4. **输出结构化建议**
   - 完成标准：给出"推荐的评估视角 + 该视角的选择依据 + 若场景假设变化会如何调整结论"——不是孤立给一个"用最差复杂度"式答案，而是体现场景条件性判断

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户只是要求"用大 O 表示法写出某段代码的复杂度"这类纯粹的静态推导作业式提问，应直接给出推导过程，不套用场景决策流程
- 用户已经自己算好复杂度，只是想确认计算是否正确（这是校验类需求，不是评估视角选型决策）
- 讨论聚焦具体语言/运行时的底层性能调优细节（如 JIT 优化、GC 停顿），这类问题已超出"复杂度视角选择"的范畴，应转向对应语言的性能剖析工具

### 作者在书中警告的失败模式

- 尾递归理论上可省栈帧空间，但 Java/Python/C++/Go/C# 等主流语言默认不做尾递归优化，误以为"写成尾递归就能省空间"会导致实际空间复杂度评估错误
- 只用平均复杂度做容量规划，忽略最差情况下的内存峰值，可能在生产环境触发内存溢出崩溃
- 把"平均更快"的方案直接当作"更优"选择，忽视对延迟 SLA 有硬性要求的场景应以最差复杂度为安全依据

### 作者的盲点 / 时代局限

- 全书默认"大 O 能完全刻画算法优劣"，但在解释某些算法"实际更快"的原因时（如后续排序算法选型 skill 中快速排序的缓存局部性优势），又不得不承认常数项、缓存命中率等大 O 之外的因素才是决定性的——这种"理论工具与实际解释"之间的张力，作者没有把它作为一个需要读者时刻警惕的方法论前提明确指出，而是当作零散的补充细节处理

### 容易混淆的邻近方法论

- 与"具体选型决策"（该用数组还是链表、该用哪种排序算法）的区别：本 skill 提供的是"该用哪种复杂度视角来评估"这一更底层的判断力，具体选型决策建立在本 skill 之上，两者层次不同，不应混为一谈
