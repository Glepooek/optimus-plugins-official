## I — 方法论骨架 (Interpretation)

数据结构选型不是找"最优解"，而是在一条"空间换时间 / 时间换空间"的权衡轴上，根据当前场景的瓶颈选边站。全书反复用同一个模式验证这条元框架：数组用连续内存换来 O(1) 随机访问，代价是插入删除要搬移数据；链表放弃连续性换来 O(1) 插入删除，代价是访问要线性遍历；哈希表用额外的桶数组空间换来平均 O(1) 查找，代价是丧失有序性且要处理冲突；邻接矩阵用 O(n²) 空间换来任意边 O(1) 判断，邻接表反过来省空间但查边要遍历。

判断该往哪边站，先问两个问题：当前瓶颈是内存还是延迟/吞吐？操作是读多写少还是写多读少、要不要有序遍历或范围查询？没有回答清楚这两个问题就直接套用"哈希表最快"或"树结构更专业"之类的直觉结论，是最常见的选型错误来源。

## A1 — 书中的应用 (Past Application)

### 案例 1: Top-k 问题的三层解法演进
- **问题**：从长度 n 的数组中找出最大的 k 个元素，暴力遍历选择法是 O(nk)，先排序再取尾部是"超额完成任务"的 O(n log n)。
- **方法论的使用**：作者没有停在"哪个复杂度最低"，而是引入 k 与 n 的相对大小作为选型变量——维护一个大小为 k 的小顶堆，只有当新元素大于堆顶时才替换。
- **结论**：堆方案把复杂度精确控制在 O(n log k)，k 越小越接近 O(n)，且天然支持动态数据流的增量更新，这是排序法和遍历法都不具备的额外优势。
- **结果**：这不是"哪个数据结构更好"的抽象比较，而是"先找出控制复杂度的自由变量（k），再按变量量级选结构"的可迁移方法。

### 案例 2: 两数之和——用哈希表替代线性查找
- **问题**：暴力枚举两层循环求两数之和，时间 O(n²)、空间 O(1)，大数据量下耗时严重。
- **方法论的使用**：引入一个"元素值→索引"的哈希表映射，把查找操作从 O(n) 降到 O(1)，整体降为单层循环 O(n)。
- **结论**：这是"以空间换时间"策略最直接的收益体现——用 O(n) 额外空间换取时间复杂度降一个数量级。
- **结果**：作者明确指出在可接受额外空间开销的前提下，这是该题的最优解法，而不是"哈希表总是更好"的泛化结论。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 在写代码时纠结"这里该用数组还是链表/该用 List 还是 LinkedList"，尤其是涉及频繁插入删除或频繁随机访问的场景
2. 设计一个需要频繁查找的功能（缓存、去重、映射关系），在"用哈希表"和"用有序结构（树）"之间犹豫
3. 需要实现一个"撤销""最近使用记录""滑动窗口"之类有容量上限、且要从两端操作的功能，不确定该用什么容器
4. 图相关需求（社交关系、依赖图、路由）中纠结邻接矩阵和邻接表该选哪个
5. 自己实现或调优一个哈希表/缓存结构，遇到性能随数据量增长而劣化的问题，怀疑是容量规划或冲突处理不当

### 语言信号 (用户的话里出现这些就应激活)

- "用数组还是链表" / "array or linked list"
- "要不要用哈希表" / "should I use a hash map / hash table"
- "这个场景该用什么数据结构" / "which data structure fits this case"
- "邻接矩阵还是邻接表" / "adjacency matrix vs list"
- "查询变慢了是不是哈希表设计有问题" / "hash table performance degraded"

### 与相邻 skill 的区分

- 与 `search-algorithm-selection` 的区别：本 skill 回答"该用什么容器/结构来存数据"，后者回答"在已确定的存储结构上该用什么算法找数据"——遇到"存了之后怎么快速查"这类跨界问题时，两者会连续触发，本 skill 先给出结构建议，再交给搜索选型细化查找算法。
- 与 `sorting-algorithm-selection` 的区别：排序是"数据静态排布"问题，与本 skill 的"数据动态存取"决策正交；但两者都共享同一条"空间换时间"底层框架，可能同时被引用。

## E — 可执行步骤 (Execution)

1. **收集场景信息**
   - 完成标准：明确以下四项——数据规模量级、读写操作比例（读多写少 / 写多读少 / 均衡）、是否需要维护有序性或做范围查询、是否有内存约束
   - 若用户触发语句中已缺失关键项，一次性列出缺失项统一询问，不逐步追问；若用户提供了代码库路径，可用 Read/Grep/Glob 快速核对现有实现规模，减少询问项

2. **定位核心权衡轴**
   - 完成标准：判断当前瓶颈落在"空间换时间"轴的哪一侧——只追求访问速度且能接受额外空间 → 倾向哈希表/数组/邻接矩阵；追求省空间或数据高度动态 → 倾向链表/邻接表；需要有序性+范围查询 → 排除哈希表，转向平衡树
   - 判停条件：若用户已经明确指定必须使用某结构（如面试要求手写特定结构），跳过本步骤和步骤 3，直接说明"已指定结构，本 skill 不再做选型判断"

3. **交叉核对已知陷阱**
   - 完成标准：对照 Boundary 段列出的反例，检查候选方案是否会踩坑（如普通 BST 未加平衡、哈希表未设扩容阈值、开放寻址直接置空删除）；若命中，给出修复方向（换用 AVL/红黑树、设置负载因子扩容阈值、改用懒删除+定期整理）

4. **输出结构化建议**
   - 完成标准：给出"选型结论 + 复杂度依据 + 触发条件性说明"——即"如果场景变成 X，结论会变成 Y"，体现选型是条件性判断而非一次性定论，不是只给一个孤立的"用哈希表"式答案

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户在做面试刷题式提问，要"标准答案"而非工程取舍分析（如"LeetCode 这道题用什么数据结构"）——这类问题应直接给出常见解法，不套用本 skill 的场景采集流程
- 用户已经明确指定必须使用某种数据结构（教学要求、面试考察点、既有代码约束），选型决策已经不存在
- 问题聚焦具体语言标准库的内部实现细节对比（如 Java `HashMap` 的红黑树转换阈值 vs Python `dict` 的开放寻址实现），这类问题应查阅对应语言官方文档，本 skill 的框架是语言无关的通用取舍逻辑

### 作者在书中警告的失败模式

- 二叉搜索树在反复插入/删除后可能退化为链表，所有操作从 O(log n) 静默劣化为 O(n)，且不会报错（普通 BST 频繁增删场景必须换用 AVL/红黑树）
- 哈希表负载因子过高会导致查询效率退化至 O(n)，且这种劣化是渐进的，容易被误诊为"服务器资源不足"而非数据结构设计问题（自定义哈希表必须设置扩容触发阈值）
- 开放寻址哈希表直接删除（置空）会破坏后续线性探测的查找逻辑，必须用懒删除（TOMBSTONE）标记；但懒删除堆积又会反过来拖慢查询，需要定期整理机制
- 哈希函数选用含小因子的合数（如 9、100）作模数，遇到有周期性规律的 key（自增 ID）会导致严重聚堆冲突，容量/模数设计应优先选质数
- "均匀分布"不等于"抗碰撞性"——分布均匀的简单哈希函数（如取模）可能极易被逆向，不能直接用于密码/签名等安全场景

### 作者的盲点 / 时代局限

- 全书的选型建议以主流编程语言内置实现（Java/Python/C#）为权威参照，隐含假设读者已在用某个主流语言写业务代码，对"语言设计者为何这样选"缺乏批判性追问，容易让读者把"常见实现"等同于"唯一正解"
- 复杂度分析框架本身默认大 O 能完全刻画优劣，但实际性能常受缓存命中率、分支预测等大 O 之外因素影响（书中在解释"数组比链表缓存命中率高"时也承认了这一点）

### 容易混淆的邻近方法论

- `search-algorithm-selection`：数据已经选好容器后，在其上该用什么查找算法（线性/二分/哈希/树查找），是本 skill 决策之后的下一层问题
