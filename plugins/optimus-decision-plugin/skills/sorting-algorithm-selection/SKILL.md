## I — 方法论骨架 (Interpretation)

排序算法选型不是找"最快"的那一个，而是在五个独立维度上打分后做取舍：运行效率（时间复杂度及常数项）、就地性（是否需要辅助数组）、稳定性（相等元素相对顺序是否保持）、自适应性（能否利用输入已有序性提速）、是否基于比较（决定理论下限是 O(n log n) 还是可达 O(n)）。没有一种算法能在五个维度上都拿满分，选型的本质就是"当前场景最看重哪个维度，就往哪个方向选"。

同一渐近复杂度的算法之间，实际效率差异往往由维度之外的因素决定：常数系数（冒泡排序每次交换涉及3个单元操作，插入排序只需1个赋值）、缓存局部性（快速排序哨兵划分能把子数组整体载入缓存，堆排序的跳跃式访问则不能）。此外，几乎每种排序算法都有已知的退化场景（快速排序遇完全倒序/完全有序/大量重复值退化，桶排序遇数据分布不均退化，计数/基数排序有明确的适用值域前提），选型不仅要选对算法，还要判断是否需要针对已知退化场景做工程加固。

## A1 — 书中的应用 (Past Application)

### 案例 1: 插入排序为何比冒泡/选择排序更受欢迎
- **问题**：三种排序算法理论时间复杂度都是 O(n²)，但实践中插入排序使用频率显著更高。
- **方法论的使用**：作者从常数系数（1次赋值 vs 3次交换）、自适应性（部分有序数据下插入排序更快，选择排序恒为 O(n²)）、稳定性（选择排序不稳定，无法用于多级排序）三个维度逐一对比。
- **结论**：时间复杂度相同不代表实际效率相同，常数项、自适应性、稳定性才是决定工程选型的关键。
- **结果**：这正是许多语言标准库对短数组采用插入排序、长数组采用快速排序的混合策略的原因。

### 案例 2: 快速排序为何快，以及两个具体退化场景的工程修复
- **问题**：快速排序、归并排序、堆排序平均都是 O(n log n)，但快速排序通常实际更快；同时存在完全倒序（基准数持续失衡）和完全有序（递归深度线性增长、栈溢出风险）两个退化场景。
- **方法论的使用**：作者先论证快速排序更快的三个具体原因（最差情况概率低、缓存局部性好、常数系数小），再针对已知退化场景给出工程修复：三数取中位数作为基准数降低劣化概率，仅递归较短子数组把最差空间复杂度从 O(n) 压到 O(log n)。
- **结论**：选定算法后，还需要针对该算法已知的退化场景做工程加固，而不是假设理论平均复杂度总能实现。
- **结果**：这两项优化成为工程级快速排序实现的标准配置，而非可选项。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 需要实现"先按字段 A 排序、再按字段 B 排序"的多级排序需求，纠结该选哪种排序算法才能保证第一次排序建立的顺序不被破坏
2. 处理体量很大的数据（百万级以上），系统内存无法一次性加载全部数据，需要判断该用什么排序策略
3. 数据可转换为非负整数且数值范围有限（如学号、年龄），纠结该用比较排序还是计数/基数排序这类非比较排序
4. 观察到排序结果出现"相等元素顺序被打乱"或"性能远低于预期"的异常，怀疑是排序算法选择不当
5. 在内存受限或对递归栈深度有顾虑的场景下，需要判断某个排序算法实现是否存在退化风险

### 语言信号 (用户的话里出现这些就应激活)

- "这个场景该用哪种排序算法" / "which sorting algorithm fits this case"
- "多级排序结果乱了" / "sort stability broke my multi-level sort"
- "要排序的数据量很大，内存放不下" / "sorting large-scale data, memory constrained"
- "快排/归并/堆排该选哪个" / "quicksort vs merge sort vs heap sort"
- "数据范围小的整数排序该怎么优化" / "counting sort or radix sort for this range"

### 与相邻 skill 的区分

- 与 `data-structure-selection` 的区别：本 skill 处理"数据静态排布"问题（一批数据如何整体排序），前者处理"数据动态存取"决策（该用什么容器存储/访问数据），两者正交但共享同一条"没有全能选项、需要多维权衡"的底层框架，可能同时被引用。
- 与 `search-algorithm-selection` 的区别：本 skill 是"查找的前置条件"之一（二分查找要求数据已排序），后者关注"如何在已排布好的数据上查找"——遇到"要不要为了能用二分查找而先排序"这类跨界问题时，两者会连续触发，本 skill 先判断排序本身是否值得，再交给搜索选型判断查找算法。
- 与 `complexity-analysis` 的区别：本 skill 的选型结论建立在复杂度分析给出的评估视角之上（如"稳定性是多级排序的必要条件"这类判断依赖对最差情况的复杂度分析），后者是更底层的方法论前提。

## E — 可执行步骤 (Execution)

1. **收集场景信息**
   - 完成标准：明确以下四项——数据规模量级、是否为多级/多字段排序、数据类型与值域（是否可转换为有限范围的非负整数）、内存/栈深度约束
   - 若用户触发语句中已缺失关键项，一次性列出缺失项统一询问；若用户提供了代码库路径，可用 Read/Grep/Glob 快速核对现有排序实现和数据规模

2. **核对稳定性硬性要求**
   - 完成标准：若为多级排序，排除选择排序、堆排序、未加处理的快速排序（均为非稳定），只在冒泡/插入/归并/计数/基数排序中选择
   - 判停条件：若非多级排序场景，跳过本步骤，直接进入步骤 3

3. **按五维评价体系匹配候选算法**
   - 完成标准：数据量小 → 插入排序；数据量大且内存受限 → 原地排序（快速/堆排序）；数据量极大且分布可预估 → 桶排序；数据是有限值域非负整数 → 计数/基数排序；数据近乎有序 → 优先考虑插入排序的自适应优势

4. **交叉核对已知退化场景**
   - 完成标准：对照 Boundary 段列出的反例，检查候选方案是否会踩坑（如快速排序未做基准数优化/递归深度优化、桶排序分桶不均、计数排序值域远大于数据量）；若命中，给出修复方向

5. **输出结构化建议**
   - 完成标准：给出"选型结论 + 五维依据 + 已知退化场景的规避方案"，体现选型是多维权衡而非单一"更快"结论

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户在做面试刷题式提问，要求"手写快速排序代码"而非工程选型分析——这类问题应直接给出实现代码，不套用本 skill 的五维评价流程
- 用户已经明确指定必须使用某种排序算法（教学要求、面试考察点），选型决策已经不存在
- 用户只是询问某个排序算法本身的实现原理/步骤，而非"该选哪个算法"的决策问题，这类问题应直接讲解算法原理

### 作者在书中警告的失败模式

- 快速排序固定选取首元素/末元素作为基准数，遇到完全倒序或对抗性构造的输入会退化为 O(n²)（应做三数取中或随机化基准数）
- 快速排序未做递归深度优化，遇到完全有序或近似有序的大规模数据会导致递归深度逼近 n，触发栈溢出（应仅递归较短子数组）
- 快速排序对大量重复元素使用标准双路划分会导致划分严重不平衡退化为 O(n²)（低基数字段应用三路划分或改用计数排序）
- 桶排序采用固定等距分桶而实际数据分布高度不均（如价格集中在某区间），会导致所有元素落入同一桶退化为 O(n²)
- 计数排序在数据量远小于值域时（n≪m），O(m) 的开销反而比 O(n log n) 排序更慢
- 基数排序用于浮点数或位数过大的数据时，位数 k 过大会导致 O(nk) 反而超过普通比较排序
- 多级排序场景误用非稳定排序算法（选择排序、堆排序、未加处理的快速排序），会破坏前一次排序建立的顺序

### 作者的盲点 / 时代局限

- 全书用"许多语言标准库对短数组用插入排序"作为插入排序优越性的权威佐证，但未深入讨论不同语言标准库排序实现的具体阈值差异，容易让读者把"某个语言的实现细节"当作普适真理

### 容易混淆的邻近方法论

- `search-algorithm-selection`：排序完成后，在有序数据上该用什么查找算法（二分查找等），是本 skill 决策之后可能的下一层问题
