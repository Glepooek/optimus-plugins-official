# 动态规划解题三步法

<!-- 蒸馏来源：《Hello 算法》(Hello Algo) krahets，第 14 章 · 动态规划。verified.md skill-07。 -->

## R — 原文 (Reading)

> "第一步：思考每轮的决策，定义状态……第二步：找出最优子结构……第三步：确定边界条件和状态转移顺序。"
>
> — krahets，《Hello 算法》第 14 章 · 动态规划

> "给定一个确定的状态，它的未来发展只与当前状态有关，而与过去经历的所有状态无关"是无后效性的定义。
>
> — krahets，《Hello 算法》第 14 章 · 动态规划

---

## I — 方法论骨架 (Interpretation)

判断一个问题是否真正适合动态规划，要核对三大特性同时具备：重叠子问题（子问题会被多条路径重复引用，值得用表/缓存消除重复计算）、最优子结构（原问题最优解可由子问题最优解直接构建）、无后效性（当前状态的未来走向只取决于当前状态本身，与如何到达该状态的历史路径无关）。三者缺一，动态规划就不适用或需要额外修复——最常见的坑是无后效性被业务约束悄悄破坏（"上一步的选择会限制下一步"这类规则），此时原状态转移方程会给出错误结果，但错误往往只在特定历史路径下暴露，常规测试很难覆盖。

一旦确认适用，落地遵循固定三步：定义状态（用最少变量刻画问题状态，确定 dp 表维度）→ 推导状态转移方程（分析原问题解如何由子问题最优解构建）→ 确定边界条件和遍历顺序（保证被依赖的子问题总是先被算出）。这套三步法对背包、路径规划、编辑距离等表面完全不同的问题给出统一施工蓝图。实现路径建议按"暴力搜索→记忆化搜索→动态规划"三级递进——先用回溯穷举验证递推关系，再加缓存消除重复计算，最后改写成自底向上迭代，每一步都可先跑通再优化，降低设计难度。空间优化（滚动数组降维）时，遍历方向必须与状态依赖方向匹配，否则会用本轮已更新的值覆盖还需读取的旧值。

## A1 — 书中的应用 (Past Application)

### 案例 1: 带约束爬楼梯——扩展状态维度修复无后效性
- **问题**：爬楼梯问题叠加"不能连续两轮跳1阶"的约束后，原状态转移方程 dp[i]=dp[i-1]+dp[i-2] 失效，因为下一步选择不再只依赖当前状态，还依赖上一轮跳了几阶，无后效性被打破。
- **方法论的使用**：将状态从一维 [i] 扩展为二维 [i, j]（j 表示上一轮跳了几阶），使新状态重新满足无后效性。
- **结论**：无后效性被打破时，不必放弃动态规划，可以通过扩展状态维度修复——但这不是万能手段，当约束依赖"过去所有状态"而非"有限个前置状态"时，扩展维度也无法解决，需转向启发式搜索等替代方案。
- **结果**：这一修复手段成为后续排查"DP 结果为什么不对"问题的标准诊断方向。

### 案例 2: 0-1背包与完全背包——约束差异如何逐层传导到遍历方向
- **问题**：0-1背包每种物品只能选一次，完全背包每种物品可重复选取，这个约束差异会如何影响实现细节？
- **方法论的使用**：作者展示约束差异（能否重复选取）导致状态转移方程下标从 i-1 变为 i，进而导致空间优化后的遍历方向从倒序反转为正序。
- **结论**：状态依赖"正上方+左上方"必须倒序遍历（避免左上方值被本轮覆盖），依赖"正上方+正左方"必须正序遍历（需要利用本行已更新值）。
- **结果**：方向选反会产生错误结果而不报错，这是空间优化 DP 最容易踩的隐蔽坑。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 面对一个包含"最大/最小/最多/最少"等最优化描述的问题，纠结是否该用动态规划求解
2. 已经写出状态转移方程，但结果不对，怀疑是无后效性被某个业务约束破坏
3. 在做空间优化（滚动数组、降维）时不确定该正序还是倒序遍历
4. 面对一个新的组合优化问题（任务调度、资源分配），想知道能否套用已有的DP解法迁移过来
5. 纠结一个问题该用动态规划还是回溯——问题看起来能拆子问题，但不确定该选哪种范式

### 语言信号 (用户的话里出现这些就应激活)

- "这个问题能用动态规划解吗" / "can I solve this with dynamic programming"
- "怎么定义dp状态" / "how to define the dp state"
- "我的DP转移方程结果不对" / "my dp transition formula gives wrong results"
- "空间优化的时候该正序还是倒序遍历" / "should I iterate forward or backward for space optimization"
- "这个任务调度问题能套动态规划的三步法吗" / "can I apply the dp three-step method here"

### 与相邻 skill 的区分

- 与 `divide-and-conquer-problem-check` 的区别：两者都基于"子问题分解"，但分治要求子问题相互独立、无重叠；若子问题存在重叠依赖，应转向本 skill 而非分治——这是判断该用哪个范式的分水岭。
- 与 `greedy-algorithm-applicability` 的区别：贪心是动态规划在"贪心选择性质成立"这一更强前提下的高效捷径；若无法证明该性质成立或已知存在反例，应退回动态规划以保证正确性。
- 与 `backtracking-algorithm-template` 的区别：若问题目标是穷举所有可行方案而非求单一最优解，或带有明显排列组合特征，应转向回溯而非本 skill——这是"加分项/减分项启发式"给出的分类判据。

## E — 可执行步骤 (Execution)

1. **用加分项/减分项快速初筛**
   - 完成标准：检查问题是否含"最大/最小/最多/最少"等最优化描述，且状态可用数组/矩阵表示、状态间存在递推关系（加分项）；若目标是穷举所有方案或带明显排列组合特征（减分项），判停并建议改用回溯

2. **核对三大特性**
   - 完成标准：确认重叠子问题（画递归树验证是否有重复节点）、最优子结构（原问题最优解能否由子问题最优解直接构建）、无后效性（当前状态是否完全刻画了通往未来的所有必要信息）
   - 判停条件：若无后效性因某业务约束被破坏，尝试扩展状态维度修复；若依赖"过去所有历史状态"而非有限前置状态，说明动态规划难以解决，跳到步骤 5 给出替代方案建议

3. **按三步法定义状态转移方程**
   - 完成标准：依次完成——定义状态（最少变量刻画问题、确定dp表维度）→ 推导状态转移方程（子问题最优解如何构建原问题解）→ 确定边界条件和遍历顺序（保证依赖的子问题先被算出）

4. **判断空间优化的遍历方向**
   - 完成标准：分析当前状态依赖的方向（上方/左方/左上方等），依赖"正上方+左上方"需倒序遍历，依赖"正上方+正左方"需正序遍历；若依赖三个及以上方向（如编辑距离的三向依赖），需引入暂存变量替代简单的遍历方向选择

5. **输出结构化建议**
   - 完成标准：给出"是否适用DP的结论 + 状态定义与转移方程 + 遍历方向依据"，若三大特性有一项不满足，明确说明该转向哪个替代范式（分治/回溯/贪心/启发式）

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用户在做面试刷题式提问，要求"这道题标准解法是什么"而非工程设计分析——应直接给出常见解法
- 用户已经确定要用DP，只是想要某个具体语言的代码实现——这是实现请求而非选型/设计决策
- 问题目标是穷举所有可行方案而非求最优解，或带有明显排列组合特征——这类问题应直接转向回溯，而非套用本skill的三步法

### 作者在书中警告的失败模式

- 业务规则叠加"某次选择会影响未来所有轮次可选项"的约束时，仍沿用原状态定义和dp表结构，无后效性已被破坏但未被察觉，导致特定历史路径下结果错误且难以被常规测试覆盖
- 空间优化时遍历方向与状态依赖方向不匹配（如0-1背包误用正序遍历），会用本轮已更新值覆盖还需读取的旧值，产生错误结果且不报错
- 依赖"过去所有历史状态"而非有限前置状态的问题（如障碍物随历史路径动态生成），扩展状态维度这一常规修复手段也会失效，此时动态规划本身不再适用

### 作者的盲点 / 时代局限

- 全书把"何时该扩展状态维度""扩展到什么程度算合理"更多依赖具体案例演示而非给出一般性的判定标准，读者面对全新问题结构时仍需要较强的类比迁移能力才能正确应用

### 容易混淆的邻近方法论

- `divide-and-conquer-problem-check`：子问题独立（分治）vs 子问题重叠依赖（动态规划），是两者最核心的分野
- `backtracking-algorithm-template`：求最优解（DP更高效）vs 求所有解（回溯更合适），是另一个关键分野
