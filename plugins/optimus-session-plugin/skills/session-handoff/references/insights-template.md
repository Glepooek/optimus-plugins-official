# insights.md 模板

**回答**：前两层装不下的。**恢复时必读**——它直接决定下轮少做多少无用功。

**写作取向：简洁但完整**。它是必读层，每次恢复都要付读取成本；但省下的重复劳动值这个成本，不要为了短而砍掉可复现命令。

---

## 格式

```markdown
---
task: <任务主题>
date: <YYYY-MM-DD>
---

# <任务主题> · 习得与核验

## 会话 N — <YYYY-MM-DD>

### ✅ 已核验通过的事实（下轮不必重做）

- <验证了什么、结论是什么、用什么命令可复现>

### 🕳️ 踩坑记录

- **现象**：<你会观察到什么>
  **根因**：<为什么>
  **绕过/修复**：<怎么解决的>
  **归属判定**：<仅本任务相关 | 建议沉淀到知识库 | 建议记入 known-issues>

### 💡 本轮习得

- <这一轮真正学到的、且不属于以上任何一类的东西>
```

## 「已核验通过的事实」是三层里价值密度最高的一段

它直接省下一整轮重复劳动。写的时候带上**可复现的命令**，下轮才敢信：

❌ `- 校验都通过了`
✅ `- 483 条知识库记录全量校验通过（python knowledge-base/scripts/validate.py，输出 "OK: 共检查 483 条记录"）`

判据：**下个会话可能会重新做一遍的事，做过了就写下来。**

## 「归属判定」为什么必须填

踩坑分两种，处置完全不同：

| 类型 | 例子 | 处置 |
|---|---|---|
| 仅本任务相关 | "这个 JSON 的缩进是 2 空格，改的时候别用 json.dump 重写" | 留在交接物，任务结束即失效 |
| 通用规范 | "Bash 工具是 Git Bash、Python 是 Windows 原生，`/tmp` 对后者不可见" | 搬进知识库或 known-issues |

不填这个字段，通用踩坑会随任务一起变成历史，下个任务再踩一次。

⚠️ **判定只做标注，不代为搬运**。自动往知识库塞内容会混入大量一次性内容，污染检索结果——搬不搬由人决定。

## 本层的追加与覆写语义

与 `summaries.md` 相同：`## 会话 N` 块整块追加，旧块原样保留，frontmatter 的 `date` 覆写为本轮日期，会话号与 `progress.md` 对齐（首个块的编号可能不是 1）。本层同样无「当前状态」性质的段落，本轮无内容时整个文件保持原样不动。

⚠️ **已核验的事实不因新会话失效就删除**——若某条结论在后续会话被推翻，在**新的会话块**里写明「会话 N 的结论 X 已被推翻，实际是 Y」，不要回头改旧块。改旧块会让读者失去"当时为什么那样判断"的线索，而这恰恰是下轮避免重蹈覆辙的依据。

## 本层是否创建

**三个维度全空则整个文件不创建。** 与 `summaries.md` 同理。

单个维度空则整段删除，不写「（无）」。

⚠️ 但先自查一遍：真的一次核验都没做、一个坑都没踩吗？这一层最容易被"感觉没什么好写的"跳过，而它恰恰是省下下轮重复劳动的那一层。**跑过的校验命令、试错后才走通的路径，都属于这里。**
