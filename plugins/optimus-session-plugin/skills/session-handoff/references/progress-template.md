# progress.md 模板

**回答**：做了什么 + 接下来做什么。**恢复时必读**，读它就能开工。

**写作取向：简洁**——它是每次恢复的必付成本。决策的完整论证过程写 `summaries-template.md` 那一层，不要写进这里，否则每次恢复都得读一遍已经定了的事。

---

## 格式

```markdown
---
task: <任务主题>
date: <YYYY-MM-DD>
branch: <分支名>
status: 进行中 | 已完成 | 已搁置
---

# <任务主题> · 进度

## 会话 N — <YYYY-MM-DD>

### 当前状态

<2-4 句。这个任务要达成什么、现在到了哪一步。让人读完知道自己接手的是什么。>

### 已完成

- <具体到文件名和产物>

---

## 🔧 工作区状态

<仅当 git status 非空时出现：哪些文件有未提交改动、为什么没提交>

## 📋 待办队列

- 🔴 <必须优先做的>
- 🟡 <应该尽快做的>
- 🔵 <有空再做的>
- ⏸️ <阻塞项> — 阻塞原因：<原因>

## 引用

- <路径或 URL> — <这里面有什么>
```

⚠️ **「工作区状态」与「待办队列」在会话块外、且放在文件末尾**。两个原因：① 它们描述的是**当前**状态不是历史，放进会话块会随会话累积成多份互相矛盾的快照；② 即使会话块累积到很长，读末尾就能拿到完整工作清单，无需通读全文。

待办全部做完时，队列写「已完成，无后续」并把 frontmatter 的 `status` 标为 `已完成`——不要删掉这一段。

## 本层的追加与覆写语义

同一任务的第二次交接，本文件内按段落分别处理：

| 内容 | 语义 | 为什么 |
|---|---|---|
| `## 会话 N` 块（当前状态 + 已完成） | **追加** | 历史需要保留——下轮要知道前几轮做过什么 |
| 🔧 工作区状态 | **整段覆写**；本轮干净则**整段删除** | 描述当前工作区，旧快照即刻失效 |
| 📋 待办队列 | **整段覆写** | 待办是当前状态。上轮做完的项应从队列消失 |
| 引用 | **覆写**（与旧清单去重合并）；本轮无新增则原样保留 | 当前有效的引用清单 |
| frontmatter 的 `date` | **覆写**为本轮日期 | 同上 |
| frontmatter 的 `status` | 仅在待办队列**清空**时才改 `已完成` | 队列还有项就说明没完 |

⚠️ **`?? docs/sessions/` 不记入工作区状态**——交接物目录是本 skill 自己的产物，记进去是自指的噪声。

⚠️ **上轮的 ⏸️ 阻塞项，本轮阻塞条件解除时必须改标**：已做完 → 移入「已完成」并注明原阻塞已解除；还没做 → 改标 🔴/🟡 留在队列。原样留着 ⏸️ 会让下轮以为还卡着。

⚠️ **覆写待办队列前先读一遍旧队列**。「覆写」指用**当前完整状态**替换整段——不是只写本轮新增的，也不是保留旧段另起一段。旧队列里未完成的项要原样带进新队列，漏带会静默丢掉上轮记下的待办。

⚠️ **覆写的对象是过期的事实，不是仍然有效的意图**。旧段落里两者混在一起：「SKILL.md 等 12 个文件未提交」是事实快照，过期了就该换掉；「等自举验证通过后一次性提交」是意图，本轮没推翻它就仍然成立，覆写时要带过来。机械地整段替换会把后者一起丢掉，而丢了不会有任何提示。

⚠️ **不要保留历次队列快照**。留着历史队列会让下轮分不清哪份是当前的，且已完成项混在里面会被重新做一遍。

第二次交接后的文件形态：

```markdown
---
task: session-handoff skill 实现
date: 2026-09-11        ← 覆写为本轮
status: 进行中
---

# session-handoff skill 实现 · 进度

## 会话 1 — 2026-09-10     ← 保留
...

## 会话 2 — 2026-09-11     ← 追加
...

---

## 📋 待办队列              ← 整段替换为当前剩余项
- 🔴 ...
```

### 会话号 N 怎么取

读文件里已有的 `## 会话` 块，取最大编号 + 1。文件不存在则从 1 开始。**不要按日期推算**——同一天可能交接两次。

## 待办队列写入检查清单

会话结束时**逐项**核对，命中即入列。这份清单的价值在于把「有没有漏记待办」从凭感觉变成可核对：

| # | 检查 | 命中则 |
|---|---|---|
| 1 | 多步任务未做完？ | 剩余步骤入列 |
| 2 | 有分流的中/低优先级未执行？ | 入列 |
| 3 | 用户说"先不做"的？ | 入列 + **注明原因** |
| 4 | 分析出问题但只修了部分？ | 未修的入列 |
| 5 | 本轮识别出可执行的遗留风险？ | 入列 |
| 6 | 依赖外部未就绪？ | ⏸️ 入列 + **阻塞原因** |
| 7 | 代码审查发现问题但未修？ | 入列 |

⚠️ **第 3 项与第 6 项必须附原因**。「先不做」不写原因，下轮会重新提议一次；⏸️ 不写原因，下轮要重新排查一遍才知道为什么卡住。

⚠️ **第 5 项不依赖 `summaries.md` 是否存在**——遗留风险在本轮会话里就能识别，不必先写完那一层再回头查。纯执行会话（不产 `summaries.md`）同样要过这一项。

## 优先级四档

| 标识 | 含义 | 判据 |
|---|---|---|
| 🔴 | 必须优先做 | 不做则后续工作无法推进 |
| 🟡 | 应该尽快做 | 不做会累积成本，但不阻塞 |
| 🔵 | 有空再做 | 改善性质，可无限期推迟 |
| ⏸️ | 阻塞 | **自己做不了**，等外部条件 |

⚠️ ⏸️ 与 🔴 的区别是**能不能做**，不是重不重要。一件很重要但自己做不了的事是 ⏸️ 不是 🔴——标错会让下轮反复尝试一件根本做不了的事。

## 「已完成」写什么、不写什么

| 写 | 不写 |
|---|---|
| 为什么这么改 | 改了哪些行（`git diff` 有） |
| 试过什么没成、为什么放弃 | commit message 的复述（`git log` 有） |
| 产物落在哪个文件 | 变更历史（CHANGELOG 有） |

❌ `- 提交了 3 个 commit，修复了若干问题`
✅ `- check_plugin_versions.py 补了 symlink mode 的 12 个用例；原先只测 100644，漏了符号链接以 120000 入库的情况`

### 纯执行性会话怎么写「已完成」

照既定计划做完、无自主决策时，「已完成」写起来会与计划文档重复——此时**允许指向计划的任务编号**，只补计划里没有的实际情况：

✅ `- plan 任务 1 完成（脚手架 + 两处 marketplace）。实际执行时与计划的差异：Codex 侧顶层无 version 字段，未按计划预留的位置改动`

这不违反「不重复其他产物」——指针不是复述，而「实际与计划的差异」恰恰是计划里没有的。

⚠️ **但不要因此把「已完成」写空**。「照计划做完了」本身是有效信息（下轮知道进度到哪），写不出来才说明本次无可交接内容。

## 本层是否创建

**总是创建。** 必填三段——当前状态 / 已完成 / 待办队列——写不出来说明本次会话无可交接内容，此时应告知用户无需交接，而不是创建一个空壳文件。

「工作区状态」与「引用」两段可空，空则整段删除，**不写「（无）」占位**。
