# 06 · 现代语言特性对模式的替代

> 更新历史：2026-08-29 创建。

**本篇是本领域唯一允许点名具体语言特性的一篇**——「现代特性替代模式」的判断绕不开特性名称。但约束仍在：**只点名特性，不写 API 用法**。可以说「用委托替代策略接口」，不能写委托类型的签名与注册方式；后者归 `knowledge-base/csharp/`。

多数 GoF 模式诞生于只有类与继承可用的年代。模式的**意图**依然有效，但当语言把该意图内置为特性后，手写模式的类结构就成了纯粹的成本。判断依据不是「模式过时了」，而是「这个意图在本语言里有更便宜的表达」。

## 1. 替代关系总览

| 被替代的模式 | 替代特性（.NET / C#） | 意图是否保留 |
|---|---|---|
| 策略、命令（无撤销需求时） | 委托 / lambda | 保留——行为可替换，只是不再需要接口与实现类 |
| 观察者 | 语言内置事件机制、`IObservable<T>` | 保留——一对多通知由语言承载 |
| 原型 | 带值语义的不可变类型（`record`） | 多数场景消失——拷贝由类型自身语义提供 |
| 访问者 | 模式匹配 / `switch` 表达式 | 保留——按类型分派不再需要双分派的类结构 |
| 单例、工厂方法（仅创建单一类型时） | DI 容器的生命周期管理 | 转移——唯一性与创建时机由装配层承载 |
| 迭代器 | 语言内置迭代机制（`IEnumerable<T>` + `yield`） | 完全内置——手写迭代器类无任何理由 |

- **必须**：引入上表左列的模式前，先确认右列特性不能满足需求
- **禁止**：为上表中「完全内置」的模式手写类结构
- **应该**：替代后在代码中保留意图的痕迹（命名、注释），让读者知道这里是可替换的扩展点

## 2. 委托替代策略与命令

- **必须**：算法族的成员是无状态的单一操作时，用委托参数替代策略接口与实现类
- **必须**：命令无撤销、无排队、无序列化需求时，用委托替代命令对象
- **禁止**：为单方法接口定义实现类，仅为了「符合策略模式」
- **应该**：算法族成员需要携带状态、需要命名、或需要被独立测试时，才升级为接口 + 实现类
- **可以**：算法族有 5 个以上成员且需分组管理时使用接口，此时接口的价值在于可发现性而非可替换性

**升级为接口的判据**：这个行为需要一个名字吗？需要单独的单元测试吗？两个都是「是」才值得接口。

## 3. 事件机制替代观察者

- **必须**：一对多通知用语言内置的事件机制，不手写主题与观察者列表
- **禁止**：手写订阅者集合的维护逻辑——语言已提供，自己写只会漏掉线程安全与异常隔离
- **应该**：需要通知流的组合、过滤、节流时使用响应式序列（`IObservable<T>`）而非裸事件
- **必须**：订阅须与取消配对。语言特性解决了通知机制，不解决生命周期泄漏
- **必须**：C# 与 WPF 侧的订阅泄漏防护是落地约束，见 `knowledge-base/wpf/rules/03-mvvm.md § 7. 事件与订阅`

## 4. 值语义类型替代原型

- **必须**：需要「拷贝一份并改几个字段」时，用带值语义与非破坏性修改能力的类型，不实现原型模式的克隆契约
- **禁止**：为已提供值语义拷贝的类型再实现自定义克隆方法
- **应该**：深拷贝需求确实存在且类型含引用成员时，才考虑显式克隆——此时也应优先重新设计为不可变结构
- **可以**：需要在运行时按原型实例动态创建未知类型时保留原型模式，这是它未被替代的少数场景

## 5. 模式匹配替代访问者

- **必须**：类型层次封闭（实现者集合已知且不由外部扩展）时，用模式匹配做分派，不引入访问者
- **禁止**：为封闭的类型层次实现访问者的双分派结构
- **应该**：类型层次开放（第三方可添加新类型）且操作集合稳定时，访问者仍是正确选择——它把「新增操作」的成本转移为「新增类型」的成本
- **必须**：用模式匹配分派时，须处理未匹配情形并使其在新增类型后可被发现（编译期告警或显式失败），否则新增类型会静默走入错误分支

**选择判据一句话**：类型多而操作少 → 模式匹配；类型少而操作多且类型开放 → 访问者。

## 6. 容器生命周期替代单例与简单工厂

- **必须**：实例唯一性由装配层的生命周期注册表达，不由类型自身的静态访问点表达
- **必须**：创建逻辑只是「按接口取得唯一实现」时，由容器解析，不写工厂类
- **禁止**：在有装配容器的代码库中新增静态单例访问点
- **应该**：创建需要运行时参数、需按条件分派多个产品类型、或需要延迟到调用时刻决定时，才写工厂——此时工厂的职责是**分派**，不是「包装一次实例化」
- **必须**：装配层面的通用约束见 `knowledge-base/architecture/rules/09-composition-root.md § 3. 生命周期选择的架构含义`
