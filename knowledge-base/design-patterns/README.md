# 设计模式选用与反模式

> 面向团队的设计模式**判断层**规范。**语言无关**——本领域回答「该不该用这个模式、什么信号说明用错了」，不回答「怎么写」。

本领域负责模式的选用判据与误用识别；架构风格的选型（分层/六边形/整洁/DDD）归 `knowledge-base/architecture/`，模式的语言落地归 `knowledge-base/csharp/`，WPF 中的特有形态归 `knowledge-base/wpf/`。需要判断「这段代码该不该改成某模式」时用本领域，需要「在 C# 里怎么写」时引用 `csharp`。

## 文档目的

模式的教材已经很多，本规范不重复讲模式是什么。它解决的是实际工作中真正难的那一半：**判断一个模式该不该引入，以及识别已引入的模式是否用错了。** 只知道「策略模式用于算法族」无法用于 review——本规范把每个模式写成「引入信号 / 误用信号 / 不该用的情形」三段可检验形式。

## 适用范围与读者

- **适用范围**：所有代码库的设计评审、Code Review 与重构决策；新增抽象、引入模式、拆除已有模式时适用
- **读者**：团队全部开发者。新人用于避免过度模式化，资深成员用于对齐「什么时候不用模式才是对的」

## 四领域边界

这是本领域最容易被误用的地方。四方各回答一个不同的问题，以「策略模式」为例：

| 领域 | 回答的问题 | 该主题下的例子 |
|---|---|---|
| `architecture` | 系统该怎么切分、边界在哪 | 「算法族属于领域层还是应用层」 |
| **`design-patterns`（本领域）** | **该不该用这个模式、用错的信号是什么** | **「只有一个实现且无扩展预期时禁止引入策略；出现按类型分派的连续条件分支是引入信号」** |
| `csharp` | 在 C# 里怎么落地 | 「策略用接口 + DI 注册，简单场景优先委托」 |
| `wpf` | 在 WPF 里的特有形态 | 「WPF 中交互策略走 Behavior」 |

**判据一句话**：出现「什么时候」「该不该」「误用信号」→ 本领域；出现具体类型名与 API → `csharp`/`wpf`；出现「哪一层、哪个边界」→ `architecture`。

**与 `architecture` 的分工**：两者是同一立场在两个粒度上的表述。「模式成本须与问题复杂度匹配」这条通用立场的**权威在 `architecture/rules/06-style-selection.md § 1. 架构成本与问题复杂度匹配`**，本领域只引用不重写。反向地，`architecture` 不写任何单个模式的判据。

| | `architecture` | 本领域 |
|---|---|---|
| 粒度 | 架构风格（分层/六边形/整洁/DDD） | 单个模式（策略/工厂/装饰…） |
| 决策影响面 | 整个系统或一个限界上下文 | 一个类族 / 一处扩展点 |
| 典型问句 | 「这个项目该不该上 DDD」 | 「这三个条件分支该不该改成策略」 |

## 规范级别

沿用 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 语义。各篇正文使用对应措辞，级别决定违反后的处置：

| 级别 | 措辞 | 含义 | 违反处置 |
|---|---|---|---|
| **必须 MUST** | "必须"、"禁止" | 硬性要求，无正当理由不得违反 | 视为缺陷，CI / review 拦截 |
| **应该 SHOULD** | "应该"、"不应" | 推荐做法，除非有明确理由 | review 说明理由后可豁免 |
| **建议 MAY** | "可以"、"建议" | 可选做法，团队不强制 | 无 |

## 撰写约束（维护者须知）

- **语言无关**：`rules/` 正文出现具体语言的类型名即越界。`06-modern-alternatives.md` 是**唯一例外**——「现代语言特性替代模式」必须点名特性，但只点名不写 API 用法
- **每条必须给「误用信号」**：只说「策略模式用于算法族」是教材语气，无法用于合规判断。写不出误用信号的内容不该做成 rule，应移入 `reference/`
- **不写代码示例**：`rules/` 与 `reference/` 均不含代码，实现归 `csharp`

## 索引与机器消费

本领域下的 `index.jsonl` 是供 skill 编程式检索的索引（不重复正文，只做定位），字段说明与维护约定见仓库根 `knowledge-base/README.md`。`02`-`04` 三篇按**判断单元**登记而非按模式名——高频模式各一条，低频模式按型合并一条，避免给按 `MUST` 检索的消费者返回在本场景永不适用的硬性要求。新增/修改任一类内容都需同步 `index.jsonl`，建议通过 `/knowledge-base-maintain` skill 完成。

## 更新与豁免

- 每篇文件头部记录本文件更新历史（日期 + 变更摘要），随变更提交
- 规范修订走 PR，review 通过后合入，并同步更新本文件的地图与阅读路径
- **豁免**：遇规范与场景冲突，在 PR 中显式注明"豁免原因"，由 reviewer 裁量；系统性豁免需求应推动规范修订，而非长期例外
