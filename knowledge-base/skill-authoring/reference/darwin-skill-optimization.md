# Darwin Skill 2.0：验证门控的持续优化方法

> 来源：用户于 2026-08-29 提供的 Darwin Skill 2.0 说明；其中论文结论、受控实验数据和第三方集成状态均为原始材料的声明，尚未在本仓库独立复核。
>
> 相关项目：<https://github.com/alchaincyf/darwin-skill>；原始材料引用 SkillLens（arXiv:2605.23899）、SkillOpt（arXiv:2605.23904）和 Karpathy autoresearch。

Darwin 是对既有 skill 进行**受控持续优化**的方法：一次只调整一个 `SKILL.md`，以结构评分和实际任务效果共同评价候选改动；只有验证优于基线的改动才保留。它补充本领域的 `rules/03-skill-evaluation.md`：后者规定评估必须有 with/without-skill 基线、证据和人工复核；本文说明怎样以棘轮（ratchet）方式组织连续优化实验。

## 1. 适用边界

适用于已有真实使用记录、需要提高触发准确性、执行可靠性或输出质量的 skill。不用它改变 skill 的核心用途，也不把模型评分当作发布决策的唯一依据。

每轮实验只编辑一个 `SKILL.md`，并维持以下边界：

- 不新增原 skill 没有的运行时依赖、脚本或参考资料；
- 不将文件膨胀到原大小的 150% 以上；
- 对已有 skill 的功能或接口变更，仍按仓库的 Skill/插件版本管理规则办理；
- 评分者与改动者隔离。优先使用独立 agent 或独立上下文；无法运行时必须记录为 `dry_run`，不能伪装为实测；
- 每个 skill 优化完成后由人审改动、证据和回归结果，再继续下一个目标。

## 2. 评价模型

Darwin 的本地 rubric 将分数分为三组，满分 100。各维按 1–10 评分，再按权重折算；候选版本的未四舍五入总分必须**严格高于**基线才可保留。

| 分组 | 维度 | 权重 | 关注点 |
|---|---|---:|---|
| 结构 | frontmatter 质量 | 7 | 名称与描述是否清晰表达能力、触发场景和边界 |
| 结构 | 工作流清晰度 | 12 | 有序步骤、明确输入输出和可执行路径 |
| 结构 | 失败模式编码 | 12 | 显式的“若 X 失败，则 Y”分支及兜底 |
| 结构 | 检查点设计 | 6 | 高影响决策前以 `🔴 CHECKPOINT` / `🛑 STOP` 明示人审点 |
| 结构 | 可执行具体性 | 17 | 参数、格式、例子和可直接操作的指令；避免空泛软化措辞 |
| 结构 | 资源整合度 | 4 | scripts/references/assets 是否准确可达 |
| 效果 | 整体架构 | 12 | 层次、篇幅、冗余和职责边界 |
| 效果 | 实测表现 | 23 | 典型任务的完成度，以及相对无 skill/前一版本的增益 |
| 元技能 | 反例与黑名单 | 6 | 独立列出不该做的行为、危险动作与反模式 |

前六项可通过静态审查获得初步评价；“整体架构”和“实测表现”必须结合执行证据。原始材料特别提醒：LLM 评审可识别明显退化，但对细微质量差异不可靠，因此关键发布决策必须人工复核。

## 3. 实测设计与独立性

在评分前为每个 skill 准备 2–3 个典型用户 prompt，至少覆盖一个常见路径和一个较复杂或有歧义的路径。每个用例应声明预期结果，但不应把预期写成容易被模型机械迎合的关键词。

对每个 prompt：

1. 从干净上下文运行带 skill 的版本；
2. 运行不带 skill 的版本，或在优化已有 skill 时运行上一版本快照；
3. 由独立 agent 或盲评者比较完成度、格式、冗余、偏离意图和负面影响；
4. 保存输出、评分依据、耗时和模式标识。

资源不足时可以作流程推演（`dry_run`），但结果日志必须标记该模式。若超过 30% 的评估是 `dry_run`，应将总分标为低置信度并暂停依赖该分数作自动保留决定；至少应补做一个真实的完整测试。

推荐将结果以 TSV 追加记录：

```tsv
timestamp	commit	skill	old_score	new_score	status	dimension	note	eval_mode
2026-08-29T21:30	baseline	example-skill	-	78.0	baseline	-	初始评估	full_test
2026-08-29T21:45	abc1234	example-skill	78.0	83.5	keep	失败模式	补充三段式 fallback	full_test
```

`status` 使用 `baseline`、`keep`、`revert` 或 `error`；`eval_mode` 使用 `full_test` 或 `dry_run`。日志应记录事实和证据位置，不能只写“效果更好”。

## 4. 验证门控优化循环

### 4.1 建立基线

1. 确定单个或一组待优化 skill，并读取已有评估历史。
2. 审查 runtime 中立性：将只适用于某个宿主的措辞、路径和命令限制在明确的 runtime-specific 段落；若 skill 没有明确绑定运行时，不应暗示它只能用于某个 agent 产品。
3. 审查结构维度，执行测试集，并记录基线评分、证据和评估模式。
4. 展示测试 prompt、基线和已知短板，设置 `🔴 CHECKPOINT`，经人确认再改动。

### 4.2 单变量改进

每轮只针对一个主要问题提出一个可归因的改动，例如补充失败分支、明确输出模板、删除造成跑偏的过度约束，或补充高风险操作前的检查点。工作流、失败处理与检查点往往相关，诊断时可共同观察，但提交的候选改动仍应有单一、可解释的主假设。

候选改动后：

1. 重新执行同一测试集并由独立评审比较；
2. 同时检查结构评分、测试证据和成本变化；
3. 仅当新分数严格高于旧分且无关键回归时保留；
4. 否则恢复到上一通过版本，并在日志保留失败尝试及其原因。

Git 仓库中，恢复已经提交的候选改动应使用可追溯的反向提交（`git revert`），而不是会清除未提交工作和历史的 `git reset --hard`。本仓库任何提交仍必须交由 `commit-cc-plugin` 执行。

### 4.3 停止条件与探索

默认每个 skill 最多三轮。若连续两轮提升低于 2 分，应视为边际收益触顶，停止微调，避免为取悦评分器增加冗余内容。

只有在两个目标都快速触顶且人审明确同意时，才可提出探索性重写：保存当前已验证版本，重组整个 `SKILL.md`，用同一测试集重新评估，并仅在优于已验证版本时采用。探索性重写不是绕过验证门控的理由。

### 4.4 每个目标的人工关口

`🔴 CHECKPOINT · 🛑 STOP`：每个 skill 优化结束后，向维护者展示：

- 改动前后的 diff；
- 各维分数和总分变化；
- 典型 prompt 的带 skill / 基线输出及评分证据；
- `full_test` 与 `dry_run` 的比例；
- 已保留和已回滚的候选尝试。

维护者可以接受、要求回滚，或指定下一轮假设。没有明确确认，不进入下一 skill 或发布步骤。

## 5. 高价值改进模式

- **显式检查点**：在不可逆、成本高或会扩大范围的决定前使用视觉明确的暂停标记，而非埋在模糊建议里。
- **三段式 fallback**：以“触发条件 → 一线修复 → 仍失败时的兜底”代替仅列“症状/解法”的表格。
- **校准具体性**：为顺序敏感或脆弱任务给足参数和格式；对多种合理方案保留必要裁量，避免把 skill 变成长篇菜单。
- **反例清单**：单列“不要做什么”，覆盖诸如跳过基线、同上下文自评、静默吞掉异常、为凑分堆文字、在一轮中修改多个无关变量等反模式。
- **运行时中立性**：将通用指令写成与宿主无关的操作；确有宿主限定的工具或路径，要说明范围并给出可行降级路径。

## 6. 与现有规范的关系

本文是方法参考，不取代现有规范。实际执行时：

- 评估用例、基线、断言、盲评和人工 review 按 `rules/03-skill-evaluation.md`；
- description 的触发优化和 train/validation 切分按 `rules/02-description-optimization.md`；
- runtime 中立的 frontmatter 与正文结构按 `rules/01-skill-format.md`；
- 脚本接口与安全性按 `rules/04-script-usage.md`；
- 真实经验、上下文预算、验证循环按 `rules/05-best-practices.md`。

Darwin 的“只保留已验证改进”是这些规则在连续优化场景中的组织方式，而非新的、可替代的质量真源。
