# 06 · 持续优化

> 更新历史：2026-08-30 创建；2026-09-12 新增 §5-§10（优化轮的成本控制：入场条件、判据双向实跑、机械检查前置、评审范围、台账封顶与归档、一手规范优先）。
>
> 本篇覆盖 skill **交付后运营期**的持续改进机制，与 `01`-`05` 篇的**创建期**技法互补：01-05 回答"如何创建一个好 skill"，本篇回答"skill 上线后如何随真实使用持续变好"。方法参考 `reference/darwin-skill-optimization.md`（验证门控的持续优化方法）。
>
> §1-§4 是机制（做什么），§5-§10 是**优化轮的成本约束**（怎么做才不会越优化越贵）。后者从实际教训中提炼：一个 skill 连续 6 轮优化而其功能一次未执行，评审成本随台账体量正反馈增长，新写的检查项本身成为高危缺陷的主要来源。

## 1. 创建后强制基线评估

- **必须**：新 skill 交付后，必须用 darwin-skill 跑一次基线评估，建立初始分数记录——即使当前没有明显优化空间，也要留基线，为后续棘轮机制（新分数不得低于基线）提供比较基准
- **必须**：基线评估记录评分依据与评估模式（`full_test` 或 `dry_run`），不能只写最终分数
- **区分于 `03-skill-evaluation.md`**：03 是创建阶段作者自驱的 eval 迭代（`evals.json` 驱动，聚焦"这个 skill 达到预期效果没有"）；本节是交付后独立于作者视角的结构性基线扫描（darwin-skill 驱动，含 runtime 中立性红灯扫描、frontmatter 质量、失败模式编码等结构维度），两者不是重复劳动

## 2. known-issues.md：使用期反馈记录

- **必须**：每个 skill 目录维护 `known-issues.md`，记录真实使用中暴露的问题——触发误判（该触发未触发/不该触发却触发了）、输出质量差、边界 case 遗漏
- **必须**：记录格式为表格：`日期 | 问题描述 | 触发场景/prompt | 状态(待处理/已优化) | 优化后版本`
- **应该**：记录成本必须足够低——发现问题当下一行带过即可，不必等整理成完整 bug report；忠实记录问题本身比措辞规范更重要

## 3. 累积阈值触发优化

- **必须**：`known-issues.md` 中"待处理"状态条目累积满 3 条时，必须发起一次 darwin-skill 优化循环
- **必须**：每条问题描述转化为一条测试 prompt，追加进该 skill 现有的 `test-prompts.json`（追加，不重写既有条目）
- **必须**：优化完成后，被解决的条目改状态为"已优化"并标注解决版本号，**不删除**——保留可追溯的问题史，与 cangjie-skill 蒸馏流程中 `rejected/` 目录"淘汰项附理由不删除"是同一治理逻辑。⚠️ 台账体量超出封顶时，"不删除"由归档文件承载，见 §9

## 4. 与 darwin-skill 的现实边界

darwin-skill 本体（`SKILL.md`）不随本仓库分发，通常安装在用户全局 `~/.claude/skills/darwin-skill`，不受本仓库版本管辖，也无法被仓库内脚本自动读取或调用。因此：

- "触发优化"这一动作、以及把 `known-issues.md` 内容作为 Phase 0.5 测试素材传递给 darwin-skill，**必须由人工在对话中显式发起**，不存在自动化钩子
- 本篇各节的 `enforcement` 统一标 `review`，不得标 `ci`——"满 3 条强制触发"是流程约定，不是可被工具无歧义拦截的机制；§7 列举的机械检查虽可脚本化，但检查脚本是否存在因仓库而异，规则本身仍标 `review`

## 5. 优化轮的入场条件：必须真实运行过

- **必须**：发起一次优化轮之前，该 skill 自上次改动以来**至少真实执行过一次**。仅靠阅读产物发现的问题不构成入场理由
- **理由**：阅读发现的缺陷真伪混杂、需逐条人工判真，真实运行暴露的缺陷全部为真；且判据在真实环境下的行为（路径形式、退出码、字段取值、命令作用域）无法靠阅读推断
- **应该**：把那次运行中「卡住、给错答案、需要人工兜」的点作为本轮范围，其余不动
- **禁止**：连续多轮只读不跑。可观测的症状是**该 skill 的连续提交全为 fix/refactor，而它的实际功能在这些提交期间一次都没执行过**——此时优化对象已经是文档自身而非产物行为
- **与 §3 的关系（本条优先）**：§3 的「待处理满 3 条必须发起优化」触发的是「**下一次真实运行之后**开一轮」，不是「立刻开一轮」。两条同时生效时按本节裁定，否则会互相锁死——台账满了却跑不起来，只能靠继续阅读产出更多台账

## 6. 新增判据必须双向实跑

- **必须**：新增的检查、判据、门禁，落笔后必须**同时实跑「应通过」与「应拦截」两侧**。只验通过侧会漏掉恒通过（形同虚设），只验拦截侧会漏掉恒拒绝（每次都跑不起来）
- **必须**：新增的命令类动作，除验证「流程能否继续推进」外，还须验证**该命令的作用域**——它实际会改动、收走或删除多少东西
- **必须**：引入的每一个副作用都配一条归还路径（临时挪走的要挪回、临时改写的要复原），并写明归还时机
- **禁止**：拿聚合字段（整体 `ok`、退出码）代替单项字段作为判据——聚合字段为假的原因可能与本判据无关，据此分支会抢走另一条分支的入口
- **理由**：新写一个检查比修改已有内容更容易出错，且错法是「检查看着在跑、实际什么都没拦住」，不会有任何报错

## 7. 机械可判定的检查不进人工评审

- **必须**：派生值（行数、条目数、确认点数、测试数）不写死在文档里；确因可读性必须写出时，**落笔前即时重跑一次统计**，不得凭工作中途的印象写
- **必须**：以下类别用脚本拦，不消耗人工或评审 agent 的上下文——正文行数上限、文档声明的计数与实际标记数是否一致、引用是否悬空、文档里的示例形态与真实数据形态是否一致、文档声明的派生值与实测值是否一致
- **理由**：人工评审的成本与**语料总量**成正比，机械检查的成本与**检查项数**成正比。把后者混进前者，等于按语料总量付费去做按项数就能完成的事
- **应该**：该类检查一旦有脚本承载，即在该仓库落为提交门禁

## 8. 评审范围与成本控制

- **必须**：darwin-skill 用作**门禁**（新分数不低于基线即放行），不用作缺陷猎场
- **禁止**：与评审 agent 就分数往复论证。论证改变的是那个数字、不是产物——除非其扣分依据是事实错误，否则接受数字并进入下一轮
- **应该**：缺陷发现与门禁评分分开派发。缺陷发现的评审范围是**本轮 diff 及其影响半径**，不是全部产物；仅需要全局结构的维度（如渐进披露）才提供完整正文
- **应该**：一轮只改一个主题。一轮内叠加多个主题，会让每个主题都要重跑一次全量核对

## 9. 台账封顶与归档

- **必须**：`known-issues.md` 正文只保留三类内容——① 状态为「待处理」的条目 ② 仍在生效、且被 SKILL.md 正文指向的判据与教训 ③ 归档指针
- **必须**：§3 要求的可追溯性由归档承载，**归档不是删除**——已解决条目的**逐轮叙事**（某轮查出什么、怎么修、当时的取证过程）移入同目录 `known-issues-archive.md`
- **必须**：正文封顶 **150 行**；超出即归档，**不靠压缩措辞**（压缩措辞是用判据可读性换行数）
- **必须**：发起评审时明确告知评审 agent **不读归档文件**
- **应该**：归档时把反复发作的教训**去叙事化**后留在正文——去掉日期、轮次、当时的取证过程，只留判据本身。同一病灶第二次出现说明它是规则缺口，而叙事细节对下一次执行没有用
- **理由**：台账每轮增长、而每轮被完整重读，轮数越多每轮越贵，是正反馈。不封顶的台账最终会比它所描述的产物更大

## 10. 定性问题先查一手规范

- **必须**：写「某字段/某写法是否合规」这类规范条款前，先读**一手规范文档**，不得凭印象定性
- **必须**：分清**运行时拒绝**与**移植时拒绝**——前者是缺陷，后者是取舍。给取舍登记「例外/豁免」会把正常取舍写成违规，让规范自相矛盾
- **理由**：成本不对称。读一手文档是分钟级的事，基于错误前提写出的规范条款需要整轮撤销，且在撤销前会污染所有引用它的产物
