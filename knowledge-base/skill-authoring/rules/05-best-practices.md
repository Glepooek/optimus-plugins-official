# 05 · 最佳实践

> 更新历史：2026-08-22 创建。
>
> 来源：[Agent Skills 最佳实践](https://agentskills.io/skill-creation/best-practices)。本篇约束如何创建 scope 得当、校准到任务的 skill——从经验来源到上下文预算再到指令模式。

## 1. 从真实经验出发

- **必须**：创建 skill 时提供**领域专属上下文**，不靠 LLM 通用训练知识生成——否则产出的是"恰当处理错误"这类空泛流程，而非具体 API 模式、边界情况、项目约定这些真正让 skill 有价值的细节
- **应该**：从**实操任务**提取——在对话中完成一个真实任务（提供上下文、纠错、偏好），再提取可复用模式；重点记录：有效的步骤、你做的纠正、输入输出格式、你提供的项目专属事实
- **应该**：从**现有项目产物**综合——内部文档/runbook/风格指南、API spec/schema/配置、code review 评论/issue（捕捉反复出现的关注点）、版本控制历史（通过实际变更揭示模式）、真实失败案例与修复
- **禁止**：基于通用"XX 最佳实践"文章生成——真实团队 schema、失败模式、恢复流程远超通用参考

## 2. 用真实执行来打磨

- **必须**：初稿跑真实任务后修订；把结果（**全部**，不只失败）反馈进创建流程
- **必须**：问"什么触发了误报？什么被漏掉了？什么可以砍？"
- **应该**：读 agent 执行记录而不只看最终输出——agent 浪费步骤的常见原因：指令太模糊（试几种方法才找到）、指令不适用当前任务（还是照做了）、给了太多选项没默认值
- **应该**：一次 execute-then-revise 就能明显提升质量；复杂领域常需多轮

## 3. 上下文预算

skill 激活后，整个 `SKILL.md` 正文进上下文，与对话历史、系统上下文、其他激活 skill 竞争注意力。**每个 token 都在抢 agent 的注意力。**

- **必须**：只加 agent 没有就不知道的信息——项目专属约定、领域专属流程、非显而易见的边界、要用的特定工具/API
- **必须**：不解释 agent 已懂的常识——什么是 PDF、HTTP 怎么工作、数据库迁移是什么
- **必须**：对每段内容自问"没有这条指令 agent 会做错吗？"——不会就砍；不确定就测；agent 本就能完全处理的任务，skill 可能没在增值
- **必须**：设计**相干单元**——skill 该覆盖什么就像函数该做什么：封装一个能与其他 skill 良好组合的工作单元；太窄 → 单任务要加载多个 skill（开销+指令冲突）；太宽 → 难以精确触发
- **必须**：适度细节——过度全面的 skill 反而有害（agent 难提取相关部分，可能走上被不适用指令触发的低效路径）；简洁的分步指引 + 可用示例优于穷举式文档
- **必须**：大 skill 用 progressive disclosure 拆（见 `01` 章）——详细参考移 `references/`，关键是告诉 agent **何时**加载每个文件

## 4. 控制校准

不是每个部分都需要同样的规定性。**把指令的具体程度匹配到任务的脆弱度。**

- **应该**：多方案皆可、容忍变化时**给 agent 自由**——灵活指令里解释 *why* 比死板指令更有效（懂目的 agent 能做更好的上下文决策）
- **必须**：操作脆弱、一致性重要、必须按特定顺序时**给规定指令**（"严格按此序列运行 `python scripts/migrate.py --verify --backup`，不得改动命令或加 flag"）
- **必须**：多工具都能用时**给默认值**而非菜单——"用 pdfplumber 提取文本；扫描件 OCR 改用 pdf2image + pytesseract"优于罗列四个库
- **必须**：**偏过程而非结果**——教 agent"如何处理一类问题"，而非"某个具体实例要产出什么"；方法要能泛化，细节可以具体

## 5. 指令模式

可复用的指令结构技巧，按需选用，不要求全用。

### 5.1 Gotchas 章节（最高价值内容）

- **应该**：用 Gotchas 章节收录**环境专属事实**——违反合理假设的具体纠正，不是"恰当处理错误"这类通用建议
- **必须**：Gotchas 放 `SKILL.md` 里（agent 在遇到情况前读到）；独立文件只在你能告诉 agent 何时加载时才用——非显而易见的问题 agent 可能认不出触发时机
- **必须**：agent 犯错你纠正后，把纠正加进 Gotchas——这是迭代改进 skill 最直接的方式之一

### 5.2 输出格式模板

- **必须**：需要特定输出格式时提供**模板**，比散文描述可靠（agent 对具体结构模式匹配好）
- **应该**：短模板内联 `SKILL.md`；长模板或仅特定情况用的模板存 `assets/` 并引用

### 5.3 Checklist（多步工作流）

- **应该**：显式 checklist 帮 agent 跟踪进度、避免跳步——尤其步骤有依赖或校验门时

### 5.4 验证循环

- **必须**：指令 agent 交付前自检——做工作 → 跑验证器（脚本/参考 checklist/自检）→ 修 → 重验至通过
- **应该**：参考文档也可当"验证器"——指示 agent 交付前对照参考核对自己的工作

### 5.5 Plan-Validate-Execute（批处理/破坏性操作）

- **应该**：批处理或破坏性操作用三阶段：生成结构化中间计划 → 对照真值校验 → 校验通过才执行
- **必须**：关键在中间的校验脚本——它检查计划（如 `field_values.json`）对照真值（`form_fields.json`），错误信息给足 agent 自纠信息

### 5.6 捆绑可复用脚本

- **必须**：迭代时比较各用例执行记录，发现 agent 每次独立重造同一逻辑（建图表、解析某格式、验证输出）→ 写一个已测脚本进 `scripts/`（见 `04` 章）
