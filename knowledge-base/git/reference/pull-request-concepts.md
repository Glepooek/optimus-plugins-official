# Pull Request 概念：平台名称差异、作用、使用时机

## 1. Pull Request 是否为 GitHub 特有

**不是 GitHub 特有，但「Pull Request」这个叫法是 GitHub 的。**

同一套机制在不同平台有不同名字：

| 平台 | 叫法 |
|---|---|
| GitHub | Pull Request (PR) |
| GitLab | Merge Request (MR) |
| Bitbucket | Pull Request |
| Gitee / 码云 | Pull Request |

底层都是 Git 的**分支合并请求**，本质一样。只是 GitHub 把「Pull Request」这个词推广开了，所以大家习惯性简称 PR。

## 2. Pull Request 的具体作用

一句话：**发起合并请求，并在这个过程中完成代码评审和自动化检查，最后决定是否合入主分支。**

它解决的不只是「把代码合起来」，而是把「合代码」变成一个**可审查、可讨论、可拦截坏代码**的流程。核心作用分三块：

- **代码评审**：别人可以看你的改动，逐行评论、提建议、要求修改。多人协作时这是最重要的质量关卡。
- **自动化检查**：PR 可以触发 CI/CD（跑测试、lint、构建），验证改动没问题才允许合并。
- **作为合并关卡**：可以配置规则，比如「必须通过 CI」「必须至少 1 人批准」才能合并，防止未经验证的代码进主分支。

之所以叫「Pull」，语义上是你请求仓库维护者**拉取你的改动**进主分支。虽然实际是「推上去」，但历史沿用了这个说法。

## 3. 在什么情况下使用

凡是**需要把代码变更合入受保护分支，且需要别人参与确认**的场景都该用 PR：

- **团队协作的分支开发流程**：改完一个 feature 分支，希望通过 review 再进 main / develop。这是最常见用法。
- **开源项目贡献**：你是别人的仓库，没有写权限，或想保持正式流程——fork 一份 → 改 → 提交 PR 给上游，这是开源协作的标准姿势。
- **改动比较重要/有风险**：涉及公共 API、数据库变更、重构等，想走正式评审通道。
- **需要 CI 兜底**：改完直接提交怕翻车，想让它先过一遍测试再合并。

反过来，**什么时候不用 PR**：自己的个人项目没人看代码、自己直接 `git push` 到自己的分支；或者紧急修复且团队允许直接推。但即便在这些场景，很多团队也会养成「所有改动走 PR」的习惯，因为它天然留痕（谁改的、改了啥、为什么改）。
