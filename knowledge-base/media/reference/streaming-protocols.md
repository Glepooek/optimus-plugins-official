# 流媒体传输与分发：HLS、M3U8、RTMP、RTSP 与相关协议

## 1. 流媒体传输 vs 文件格式

一个核心区分：**文件**是静态的、完整的媒体；**流**是边传边播的媒体。

- 文件视角（本知识库其余文件）：容器、编码、分辨率、码率——描述"一段媒体长什么样"
- 流媒体视角（本文件）：怎么把媒体拆分成小块、经网络送到观众端、播放器如何拼起来——描述"媒体怎么到达"

流媒体协议通常由两类组件构成：

- **清单 / 索引**：描述媒体有哪些部分、怎么拼接（如 M3U8）
- **传输通道**：实际搬运媒体数据的机制（HTTP 分片、TCP 流、RTP 包）

## 2. 逐个概念

### 2.1 M3U8 —— HLS 的播放清单

M3U8 是 M3U 播放列表的 UTF-8 变体，一个**纯文本清单文件**，内容是分片文件的 URL 与元数据标签（`#EXTM3U`、`#EXTINF`、`#EXT-X-STREAM-INF` 等）。它本身不包含媒体数据，只是"分片索引"。

播放器拿到 `.m3u8` 后，按清单逐个下载分片并连续播放。扩展名 `.m3u8` 常见于网页/移动端 HLS 流的地址。

### 2.2 HLS —— 基于 HTTP 的分片流媒体协议

Apple 提出的协议，把媒体切成**2~10 秒的小分片**（传统为 TS，现代也可为 fMP4），通过 M3U8 清单索引，走**普通 HTTP/HTTPS** 传输。

- 优点：HTTP 广泛兼容（能过 CDN、防火墙、NAT）、天然支持点播与直播、自动码率切换（多档清单）
- 缺点：分片缓冲带来**秒级延迟**（直播场景比 RTMP/WebRTC 高）
- 地位：目前网络视频分发的**事实标准**——YouTube、Netflix、主流视频站的网页/App 端大量使用

### 2.3 RTMP —— TCP 长连接的直播推流协议

Adobe 为 Flash 直播设计的实时消息协议，基于 **TCP 长连接**维持稳定低延迟的流。Flash 已淘汰，但 RTMP 仍是直播**推流（ingest）**环节的通行方式：推流端（如 OBS）用 `rtmp://` 地址把画面推到平台收流服务器，平台再转 HLS 等分发。

- 优点：低延迟、推流稳定成熟、工具链普及
- 缺点：依赖 TCP 长连接，不适配大规模分发/CDN；需专业流媒体服务器（Nginx-RTMP、SRS 等）收流
- 现状：**推流用 RTMP，分发用 HLS**，是直播生态最常见的组合

### 2.4 RTSP —— 会话控制协议（配合 RTP 传输媒体）

RTSP 是**控制协议**：负责会话的建立、播放、暂停、快进等**控制信令**，媒体数据本身通常由 **RTP**（Real-time Transport Protocol）承载、经 UDP/TCP 传输。`rtsp://` 地址常见于 IP 摄像机、监控系统、VoIP。

- 与 HLS/RTMP 的区别：RTSP 本身不传媒体，只做"控制"，媒体走 RTP；多用于**实时监控/音视频对讲**场景
- 播放器需同时支持 RTSP 控制信令 + RTP 媒体接收，通用浏览器不原生支持

### 2.5 DASH —— HLS 的开放竞争对手

DASH（Dynamic Adaptive Streaming over HTTP）是**基于 HTTP 的自适应流媒体协议**，思路与 HLS 相同（切分片 + 清单 + 码率自适应），但由 MPEG 标准化、与厂商无关：

- 清单用 **MPD**（Media Presentation Description，XML）而非 M3U8；分片常用 fMP4
- 浏览器原生支持有限，通常经 MSE（Media Source Extensions）播放
- 用于 YouTube（实际是 DASH 变体）、Netflix 等大型流媒体

### 2.6 WebRTC —— 超低延迟的实时通信协议

WebRTC 是面向**实时音视频通信**的开放协议栈（P2P + 协商控制），主打**毫秒级延迟**：

- 用于视频会议、互动直播、屏幕共享、在线教育等需即时互动的场景
- 与 HLS/RTMP 的"一对多广播"不同，WebRTC 强于"点对点实时互动"，大规模直播需配 SFU 中转
- 浏览器/移动端原生支持，延迟远低于 HLS（秒级 → 百毫秒级）

## 3. 对比总表

| 术语 | 类型 | 承载 | 延迟 | 主要用途 | 现状 |
|---|---|---|---|---|---|
| M3U8 | 清单文件 | HTTP（HTTPS） | — | HLS 的分片索引 | 广泛 |
| HLS | 流媒体传输协议 | HTTP 分片 | 秒级 | 网页/App 点播与直播分发 | 分发事实标准 |
| RTMP | 流媒体传输协议 | TCP 长连接 | 低 | 直播推流（OBS → 平台） | 推流环节仍用 |
| RTSP | 会话控制协议 | 控制信令 + RTP 媒体 | 低 | IP 摄像头、监控、VoIP | 监控事实标准 |
| DASH | 流媒体传输协议 | HTTP 分片（MPD 清单） | 秒级 | 大型流媒体分发（YouTube/Netflix） | 与 HLS 竞争 |
| WebRTC | 实时通信协议栈 | UDP P2P / SFU 中转 | 毫秒级 | 视频会议、互动直播 | 实时互动主流 |

## 4. 直播生态的典型分工

```
推流（源端上传）           分发（观众拉流）
      │                        │
 RTMP ──→ 平台收流服务器 ──→ HLS/DASH ──→ 观众（网页/App）
 (OBS)    （转码/切片）       (CDN)      │
                                          └─ WebRTC：互动/低延迟直播
      RTSP：监控/对讲（控制+实时，独立生态）
```

- **推流**：把信号从源端送到平台，常用 RTMP
- **分发**：平台把流切成片、经 CDN 送给大量观众，常用 HLS/DASH
- **互动 / 超低延迟**：会议、连麦、互动直播，用 WebRTC
- **监控 / 对讲**：控制信令 + 实时媒体，用 RTSP/RTP

## 5. 常见误区

- **"M3U8 是视频格式"**：M3U8 是清单文本，不是媒体格式；真正的媒体在清单列出的分片里，分片内部仍是普通 TS/fMP4 容器（容器概念见 `video-container-formats.md`）
- **"RTMP 已淘汰"**：Flash 淘汰了，但 RTMP 作为推流协议在直播生产链路里仍普遍存在
- **"RTSP 是一种传输协议"**：RTSP 是控制协议，媒体走 RTP；直接类比是"遥控器"，不是"水管"
- **"HLS 和 DASH 完全不同"**：两者思路同源（切分片 + 清单 + 自适应），差别在标准化组织、清单格式（M3U8 vs MPD）与厂商绑定

## 6. 与 ffprobe 的关系

- ffprobe 能解析网络流地址（`ffprobe "https://example.com/stream.m3u8"`），但解析的是**清单背后的媒体流**，输出的编码/参数仍是文件视角的字段（见 `ffprobe-field-map.md`）
- 对 RTSP 可用 `ffprobe "rtsp://..."` 探测；对纯 RTMP 地址，ffprobe 支持有限
- 流是**实时**的：分析网络流时只能看到当前正在传输的部分，看不到"完整文件"——这与分析静态文件不同
