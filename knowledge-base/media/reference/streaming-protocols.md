# 流媒体传输与分发协议：HLS、RTMP、RTSP、DASH 与 WebRTC

## 1. 从一个问题讲起：视频为什么不直接下载完再播？

一段视频动辄几百 MB 甚至几 GB。如果必须"整个下载完才能看"，你点开一个视频要干等几分钟到几小时。流媒体要解决的就是：**让视频能边下载边播放**。解决方式有三层递进：

1. **渐进式下载（伪流式）**：服务器从头开始发文件，播放器收到一点播一点。早期网页视频常用。局限：想跳到还没下载到的位置没法立即播、直播没法用、网络差会卡。
2. **真流式（切分片 + 清单）**：把整段媒体切成 2~10 秒的小块（叫**分片**），再写一个纯文本**清单**列出所有分片。播放器先读清单，再按顺序把分片一个个拉下来播。HLS、DASH 就是这个思路。
3. **实时传输（直播）**：主播端一边采集一边送，观众端一边收一边播，追求低延迟。RTMP、RTSP、WebRTC 属于这类（RTMP/WebRTC 也常用于把"生产"和"分发"接起来）。

**一个类比**：整段视频像一整只烤鸡。渐进式下载是"烤好整只再端上来，客人得等"；真流式是"边烤边切、按菜单（清单）一份份上"，客人从第一份起就能吃，后厨（服务器）还在继续烤后面的；直播则是"一直烤一直上"，观众永远吃最新出锅的。

## 2. 流媒体协议的两大组成部分

不管哪个协议，基本都由两部分组成：

- **清单 / 索引**：描述"有哪些分片、按什么顺序拼"（如 HLS 的 M3U8、DASH 的 MPD）
- **传输通道**：实际搬运媒体数据的机制（HTTP 分片、TCP 长连接、RTP 包）

这就像**菜单 + 上菜服务**：清单是菜单，传输通道是把菜端到你桌上的服务。

## 3. 逐个协议

每个协议先给一句"人话总结"，再展开细节。

### 3.1 HLS（含 M3U8）—— 分发的事实标准

> **一句话**：把视频切成小块 + 写清单，观众按清单挨个下载小块来播。今天网页/App 上看视频，绝大多数是它。

HLS 不是一个文件，而是一整套"**分片 + 清单 + 传输**"方案：

- **分片（Segments）**：媒体切成 2~10 秒的小块，传统用 TS，现代可用 fMP4。分片才是真正装音视频数据的部分
- **两级清单（M3U8）**：HLS 的"目录"，分两层——
  - 媒体播放清单：某一档清晰度下的分片列表
  - 主播放清单：多档清晰度各自的媒体清单地址
- **码率自适应（ABR）**：主清单提供多档清晰度，播放器按你实时网速自动升/降档。**网好自动变高清，网差自动变流畅**，画面不中断——这就是你看视频时清晰度"自己变"的原因
- **加密与 DRM**：分片可加密（AES-128），密钥地址用 `#EXT-X-KEY` 标注；`SAMPLE-AES` 配合 Widevine / FairPlay 等商业 DRM 做版权保护
- **直播 vs 点播**：点播清单末尾有 `#EXT-X-ENDLIST`（表示播完就结束）；直播没有，清单滑动更新、不断追加新分片

一个 M3U8（媒体播放清单）片段：

```
#EXTM3U
#EXT-X-VERSION:3
#EXTINF:10.000,
seg1.ts
#EXTINF:10.000,
seg2.ts
#EXT-X-ENDLIST
```

**播放器放一个 HLS 视频的过程**（4 步）：

1. 拿到地址（如 `https://cdn.example.com/vod/index.m3u8`）→ 先读主清单，看有哪些清晰度
2. 按当前网速挑一档，读对应的媒体清单
3. 按清单顺序把分片一个个下载下来，边缓冲边播放
4. 网速变化时切到更高/更低清晰度，画面不断

**M3U8 在 HLS 中的位置**：M3U8 只是 HLS 的**清单文件**，描述"有哪些分片、怎么拼"，本身不含媒体数据。它依附于 HLS，不与其他协议平级——把 M3U8 和 HLS 并列，就像把"菜单"和"整家餐厅"并列。看到 `.m3u8` 地址，你拿到的是清单，真正的视频在清单列出的分片里。

- 优点：走普通 HTTP（能过 CDN、防火墙、NAT），天然支持点播与直播，自带码率自适应
- 缺点：分片缓冲带来**秒级延迟**（直播场景比 RTMP/WebRTC 高）
- 地位：网络视频分发**事实标准**——YouTube、Netflix、主流视频站的网页/App 端大量使用

### 3.2 RTMP —— 直播推流的老将

> **一句话**：一条一直开着的"专线"，画面实时往上传。主播开播、把画面推给平台时用。

Adobe 为 Flash 直播设计的实时消息协议，基于 **TCP 长连接**。Flash 已淘汰，但 RTMP 仍是直播**推流（ingest）**环节的通行方式：主播用 OBS 之类的软件，把 `rtmp://` 地址填进去，画面就推到平台收流服务器；平台再把流转成 HLS 分发给观众。

典型地址：`rtmp://push.live.com/app/streamkey`（`streamkey` 是推流密钥，相当于"开播凭证"）。

- 优点：低延迟、推流稳定成熟、工具链普及
- 缺点：依赖 TCP 长连接，不适配大规模分发/CDN；需专业流媒体服务器（Nginx-RTMP、SRS 等）收流
- 现状：**推流用 RTMP，分发用 HLS**，是直播生态最常见的组合。加密变体 **RTMPS** 也存在（推流走 TLS）

### 3.3 RTSP —— 监控摄像头的"遥控器"

> **一句话**：负责"开始播、暂停、快进"这些命令的遥控器；画面本身走 RTP 另一条路送。监控摄像头、对讲机用它。

RTSP 是**控制协议**：只管**控制信令**（会话建立、播放、暂停等）。媒体数据本身通常由 **RTP** 承载，经 UDP/TCP 传输。典型地址：`rtsp://192.168.1.100:554/stream`（IP 摄像头常见地址，`554` 是 RTSP 默认端口）。

- 与 HLS/RTMP 的区别：RTSP 自己不传媒体，只做"控制"；媒体走 RTP。类比是"遥控器"（下指令）和"水管"（送水）的关系
- 播放器需同时支持 RTSP 控制 + RTP 媒体接收，通用浏览器不原生支持，多用于**监控/对讲**等专用场景

### 3.4 DASH —— HLS 的开放对手

> **一句话**：和 HLS 思路一模一样（切块 + 清单 + 自适应），但由国际标准组织 MPEG 定义、与任何厂商无关。YouTube、Netflix 这类巨头用它。

- 清单用 **MPD**（XML 格式）而不是 M3U8——MPD 在 DASH 中的角色 = M3U8 在 HLS 中的角色；分片常用 fMP4
- 浏览器原生支持有限，通常经 **MSE** 接口播放
- 现状：与 HLS 竞争，两者都是主流，同一份内容往往同时提供 HLS 和 DASH 两种

### 3.5 WebRTC —— 低延迟的实时通信协议

> **一句话**：像"打电话"一样的实时音视频，延迟最低。视频会议、连麦、在线课堂用它。

WebRTC 是面向**实时音视频通信**的开放协议栈（P2P + 协商控制），主打**毫秒级延迟**：

- 用于视频会议、互动直播、屏幕共享、在线教育等需要即时互动的场景
- 与 HLS/RTMP 的"一对多广播"不同，WebRTC 强于"点对点实时互动"；大规模直播需要配 **SFU** 中转服务器
- 浏览器/移动端原生支持，延迟远低于 HLS（秒级 → 百毫秒级）

## 4. 对比总表

| 术语 | 类型 | 承载 | 延迟 | 主要用途 | 现状 |
|---|---|---|---|---|---|
| HLS | 流媒体传输协议 | HTTP 分片（含 M3U8 清单） | 秒级 | 网页/App 点播与直播分发 | 分发事实标准 |
| RTMP | 流媒体传输协议 | TCP 长连接 | 低 | 直播推流（OBS → 平台） | 推流环节仍用 |
| RTSP | 会话控制协议 | 控制信令 + RTP 媒体 | 低 | IP 摄像头、监控、VoIP | 监控事实标准 |
| DASH | 流媒体传输协议 | HTTP 分片（MPD 清单） | 秒级 | 大型流媒体分发（YouTube/Netflix） | 与 HLS 竞争 |
| WebRTC | 实时通信协议栈 | UDP P2P / SFU 中转 | 毫秒级 | 视频会议、互动直播 | 实时互动主流 |

## 5. 直播生态的典型分工

```
推流（源端上传）           分发（观众拉流）
      │                        │
 RTMP ──→ 平台收流服务器 ──→ HLS/DASH ──→ 观众（网页/App）
 (OBS)    （转码/切片）       (CDN)        │
                                          └─ WebRTC：互动/低延迟直播
      RTSP：监控/对讲（控制+实时，独立生态）
```

- **推流**：把信号从源端送到平台，常用 RTMP
- **分发**：平台把流切成片、经 CDN 送给大量观众，常用 HLS/DASH
- **互动 / 超低延迟**：会议、连麦、互动直播，用 WebRTC
- **监控 / 对讲**：控制信令 + 实时媒体，用 RTSP/RTP

> **CDN（内容分发网络）**：把同一份内容复制到全球各地的服务器，观众就近取用。分片格式尤其适合 CDN——每片是独立小文件，能被任意服务器缓存。

## 6. 常见误区

- **"M3U8 是视频格式"**：M3U8 只是 HLS 的清单文本，不是媒体格式；真正的媒体在清单列出的分片里，分片内部仍是普通 TS/fMP4 容器（容器概念见 `video-container-formats.md`）
- **"HLS 就等于一个 m3u8 文件"**：HLS 是完整方案（分片 + 两级清单 + 自适应 + 加密），m3u8 只是其中的清单文件
- **"只有 `.m3u8` 结尾才是 HLS"**：扩展名是惯例不是铁律——地址可能带参数（`index.m3u8?token=xxx`）或经过跳转，判断协议靠内容而非后缀
- **"RTMP 已淘汰"**：Flash 淘汰了，但 RTMP 作为推流协议在直播生产链路里仍普遍存在
- **"RTSP 是一种传输协议"**：RTSP 是控制协议，媒体走 RTP；直接类比是"遥控器"，不是"水管"
- **"HLS 和 DASH 完全不同"**：两者思路同源（切分片 + 清单 + 自适应），差别在标准化组织、清单格式（M3U8 vs MPD）与厂商绑定

## 7. 术语速查

| 术语 | 一句话解释 |
|---|---|
| CDN | 内容分发网络：把内容复制到各地服务器，观众就近取用，快且省带宽 |
| TS | 一种老牌视频封装格式（`.ts`），HLS 传统分片用它；详见 `video-container-formats.md` |
| fMP4 | 分段式 MP4，一种支持边下边播的 MP4 变体，现代 HLS/DASH 分片常用 |
| TCP | 可靠传输：像挂号信，保证送达且顺序正确，但慢一点；RTMP 依赖它 |
| UDP | 尽力传输：像平邮，可能丢件但快；实时音视频常用 |
| RTP | 实时传输协议：承载音视频数据的"快递车"，通常走 UDP，配合 RTSP 使用 |
| DRM | 数字版权管理：加密内容、限制拷贝与播放，如 Widevine / FairPlay / PlayReady |
| P2P | 点对点：观众之间互传，WebRTC 用它 |
| SFU | 服务器转发单元：多人会议/直播时的中转服务器，WebRTC 大规模场景用它 |
| MSE | 浏览器播放流媒体的接口，DASH 及部分 HLS 靠它把分片注入播放器 |
| ABR | 码率自适应：播放器按网速自动切换清晰度 |

## 8. 与 ffprobe 的关系

- ffprobe 能解析网络流地址（`ffprobe "https://example.com/stream.m3u8"`），但解析的是**清单背后的媒体流**，输出的编码/参数仍是文件视角的字段（见 `ffprobe-field-map.md`）
- 对 RTSP 可用 `ffprobe "rtsp://..."` 探测；对纯 RTMP 地址，ffprobe 支持有限
- 流是**实时**的：分析网络流时只能看到当前正在传输的部分，看不到"完整文件"——这与分析静态文件不同
