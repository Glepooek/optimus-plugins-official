# 08 · 模块与部署边界

> 更新历史：2026-08-29 创建。

本篇回答「什么时候该拆」——拆构建单元、拆模块、拆独立部署单元。三者是不同量级的决策，成本相差一到两个数量级。

C# 侧的项目引用机制见 `knowledge-base/csharp/rules/01-project-structure.md § 4. 解决方案布局`，可见性与项目类型约定见同文件 `§ 7. 项目类型约定`。

## 1. 三种边界的区分

| 边界类型 | 强制手段 | 违反的后果 | 引入成本 |
|---|---|---|---|
| 目录/命名空间边界 | 约定 + review | 无技术阻止，靠人守 | 极低 |
| 构建单元边界 | 构建系统 | 编译失败 | 低 |
| 部署单元边界 | 进程/网络隔离 | 调用不通 | 高 |

- **必须**：明确当前讨论的是哪一种边界。「拆模块」在三种含义下的成本完全不同
- **应该**：从最弱的边界开始，仅在约定被反复违反时升级为构建单元边界
- **禁止**：用部署边界解决代码组织问题。进程隔离的代价是网络调用、分布式故障与运维复杂度，这些成本换来的仅是「无法互相引用」，而构建单元边界能以极低成本达到同样效果

## 2. 拆构建单元的判据

**满足任一考虑拆分：**

1. 需要用构建系统强制依赖方向（约定已被违反过）
2. 该部分有独立的复用需求（被两个以上上层单元使用）
3. 该部分的构建产物需独立分发
4. 编译时间已成为开发瓶颈，且拆分能带来增量编译收益

- **禁止**：按技术层机械拆分构建单元。层次数不等于构建单元数——不需要强制的层次边界用目录即可
- **禁止**：为「看起来模块化」而拆出大量小构建单元。每个构建单元都有构建开销与依赖管理成本
- **应该**：拆分后的依赖图是有向无环的且层次不深；出现「需要循环引用」说明拆的位置不对
- **必须**：拆分前确认拆出的部分有清晰的对外契约；契约不清的拆分会导致大量成员被迫公开

## 3. 循环依赖的架构级处置

循环依赖是拆分位置错误的信号，不是需要「想办法绕过」的技术问题。

出现循环时按顺序考虑：

1. **合并**：两部分确实无法分离 → 它们本就是一个模块，合并是正确答案
2. **提取**：双方共同依赖的部分 → 提取为第三个模块，双方都依赖它
3. **倒置**：一个方向是「通知/回调」性质 → 由被依赖方定义抽象，依赖方实现（依赖倒置）
4. **事件**：双向通知需求 → 改为经由事件解耦，双方都不直接依赖对方

- **禁止**：用反射、服务定位器或延迟解析绕过循环依赖。循环仍然存在，只是从编译期移到了运行期
- **禁止**：为打破循环而把一方的接口复制到另一方；两份契约需同步维护
- **必须**：处置方式记入架构决策记录，尤其是选择「合并」时——后续维护者可能重新尝试拆分

## 4. 内部可见性

- **必须**：模块的公开面只包含外部实际需要的部分；实现细节保持模块内可见
- **禁止**：为方便测试而公开实现细节。测试应通过公开契约验证行为；必须访问内部时使用语言提供的受限可见性机制，不改为完全公开
- **应该**：公开面的大小是模块划分质量的指标——公开面接近模块全部成员时，说明这个边界没有隔离任何东西
- **应该**：定期审视公开面，移除已无外部调用者的公开成员

## 5. 模块化单体

在单体与分布式之间，模块化单体是一个常被跳过的中间态。

- **应该**：需要模块边界但不需要独立部署时选模块化单体——用构建单元边界强制模块隔离，单进程部署
- **必须**：模块化单体的模块间通信经由显式契约，不直接访问对方内部
- **应该**：模块间通信刻意使用「跨进程也能成立」的形态（消息、明确的请求响应契约），为后续可能的拆分保留选项
- **禁止**：把模块化单体当成「注定要拆成微服务」的临时状态。多数系统在模块化单体上就是终态，这不是妥协

## 6. 拆分独立部署单元的门槛

**全部满足才考虑拆分：**

1. 存在**独立伸缩**需求——某部分的负载特征与其余部分显著不同
2. 存在**独立部署**需求——该部分的发布频率与其余部分显著不同，且合并发布已造成实际阻塞
3. 存在**独立技术栈**需求，或**独立故障隔离**需求（该部分故障不应影响其余部分）
4. 团队有能力承担分布式系统的运维成本（部署编排、分布式追踪、跨服务故障排查）

- **禁止**：以「团队各自开发互不干扰」为理由拆分部署单元。这是代码边界问题，模块化单体已能解决，代价低两个数量级
- **禁止**：以「技术先进」「便于扩展」为理由拆分。拆分后引入的分布式一致性、网络故障处理与运维复杂度是永久成本
- **必须**：拆分前确认边界稳定。边界在拆分后调整的成本远高于拆分前——跨服务的边界调整需要数据迁移与双向兼容
- **应该**：拆分从最独立的部分开始，而非从最核心的部分开始。核心部分的边界最可能需要调整
- **应该**：拆分的收益在拆分后可度量（部署频率、故障隔离效果）；无法度量的收益多半不存在

## 7. 边界稳定性

- **必须**：新系统在边界未稳定前不拆部署单元。业务理解不足时划出的边界几乎必然需要调整
- **应该**：先在单体内用构建单元边界试验模块划分，边界稳定数月后再评估是否需要部署隔离
- **应该**：边界的稳定性由改动记录判断——某边界频繁需要「两边一起改」，说明它不是真边界
