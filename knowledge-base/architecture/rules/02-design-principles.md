# 02 · 设计原则

> 更新历史：2026-08-29 创建。

本篇给出与架构决策直接相关的设计原则及其可执行检查项，语言无关。C# 侧的落地形态（类型选择、review 表述）见 `knowledge-base/csharp/rules/03-design-principles.md § 1. SOLID 原则落地`。

## 1. SOLID 原则的可执行检查项

原则本身是共识，难点在于「怎么判断违反了」。下表把每条原则转成可检验的问句：

| 原则 | 可执行检查项 |
|---|---|
| 单一职责 SRP | 一个模块一个变更理由；名称能概括全部职责，概括不了就该拆 |
| 开闭 OCP | 新增行为通过扩展点接入，不修改已稳定的既有代码 |
| 里氏替换 LSP | 派生类型可替换基类型而不改变调用方预期；覆盖时不弱化前置条件、不强化后置条件 |
| 接口隔离 ISP | 契约小而内聚；调用方只依赖它实际使用的成员 |
| 依赖倒置 DIP | 高层不依赖低层实现，双方依赖抽象；抽象归属高层 |

- **必须**：一个模块承担两个以上明显无关的职责时拆分
- **必须**：公开契约不暴露调用方不需要的成员
- **必须**：跨层依赖一律面向抽象，见 `rules/01-layering.md § 3. 跨层契约`
- **禁止**：单一模块混杂数据、业务行为与基础设施访问三类关注点

**SRP 的常见误读**：「单一职责」不是「一个模块只做一件事」，而是「一个模块只有一个变更理由」。按前者理解会把系统切成大量只有一个方法的模块，反而增加协作成本。判断标准是**变更的来源**：两段代码总是因同一个外部原因一起改，它们属同一职责。

## 2. 组合优于继承

- **必须**：复用优先考虑组合与委托，而非继承
- **禁止**：为「复用几个方法」而继承不相关的基类型
- **禁止**：深度继承链——超过两层须在 review 中说明理由
- **应该**：明确标记不打算被继承的类型，向读者明示设计意图

继承传递的是**整个上下文**（状态 + 行为 + 契约），组合传递的只是被显式声明的那部分。继承的代价在基类型演进时才显现——那时改动面已不可控。

## 3. 抽象的引入门槛

抽象不是免费的：每个抽象都要求读者多跳一层才能看到实际行为。

- **必须**：引入抽象时能说出它隔离的是什么**已经发生或明确将发生**的变化
- **禁止**：为「以后可能要换」而引入抽象——预期中的变化多数不会发生，抽象的成本却立即产生
- **禁止**：只有一个实现且无第二个实现的具体计划时，为该实现引入抽象层
- **应该**：抽象的成员按调用方需要定义，不按实现方的能力清单定义
- **可以**：为可测试性引入抽象——这是「已经发生的变化」（测试是第二个调用场景），属正当理由

**唯一实现的例外判断**：可测试性、跨进程边界、第三方依赖隔离三种情形下，即使只有一个生产实现，抽象也是正当的。除此之外的单实现抽象应当拆掉。

## 4. 显式优于隐式

- **必须**：模块的依赖关系可从其构造契约读出，不隐藏在全局状态或运行期查找中
- **禁止**：通过全局可变状态在模块间传递数据——调用顺序成为隐含契约，无法从代码读出
- **禁止**：靠约定（命名规则、目录位置）建立的隐式关联作为架构约束的唯一保障；约定应有工具校验兜底
- **应该**：副作用发生的位置在契约中可见（名称、返回类型或文档），不让调用方靠试验发现

## 5. 原则冲突时的取舍

多条原则同时适用且互相冲突是常态，不是例外。取舍顺序：

1. **先看变更成本**：哪种做法在最可能发生的变更下改动面更小
2. **再看可读性**：两种做法变更成本接近时，选新读者能更快理解的那个
3. **最后看原则的字面**：原则是经验的压缩，不是判决书。原则与实际成本冲突时，成本优先，并把理由记入架构决策记录

- **禁止**：以「符合某原则」作为唯一理由引入复杂度，而不说明它降低了什么具体成本
- **必须**：因原则冲突而偏离常规做法时，在架构决策记录中写明冲突双方与取舍依据
