# 05 · 整洁架构

> 更新历史：2026-08-29 创建。

整洁架构与六边形架构（`rules/04-hexagonal.md`）主张高度重叠，本篇只写整洁架构**特有**的部分：同心圆的层次划分、依赖规则的精确表述、以及跨层数据传递的方向约束。二者共有的「核心不感知外部」「端口归核心」等约束不在此重复。

是否引入见 `rules/06-style-selection.md § 4. 引入六边形/整洁架构的门槛`。

## 1. 同心圆层次

整洁架构比六边形多做了一件事：把「核心」进一步分成两层。

| 圈层 | 内容 | 变更频率 |
|---|---|---|
| 实体（最内） | 业务规则本身，不随应用形态变化 | 最低 |
| 用例 | 编排实体完成一个业务操作 | 低 |
| 接口适配 | 控制器、展示器、网关实现 | 中 |
| 基础设施（最外） | 框架、数据库、外部服务、UI | 最高 |

- **必须**：实体层只含跨用例通用的业务规则；只服务单个用例的规则属用例层
- **必须**：用例层可依赖实体层，实体层不得依赖用例层
- **禁止**：把所有业务规则都放实体层——只被一个用例使用的规则放在那里会让实体层随该用例的需求变动
- **应该**：实体层与用例层能否分开是判断该不该用整洁架构的信号；分不开说明用四层是过度设计，两层（核心 + 外部）已足够

## 2. 依赖规则

依赖规则是整洁架构唯一的硬性规则，表述比「依赖向内」更精确：

> **源码依赖只能指向内层。内层的任何名称都不得出现在外层的声明中。**

- **必须**：跨圈层的源码依赖一律向内，无例外
- **必须**：内层的类型、函数、常量名不出现在外层的公开契约中
- **禁止**：内层通过任何形式感知外层——包括「外层注册回调、内层调用」这类看似反向的写法，若回调签名由外层定义则依赖方向已被打破
- **应该**：依赖规则用架构测试断言，见 `rules/01-layering.md § 6. 分层约束的可执行性`

**「内层名称不出现在外层声明中」的实际含义**：外层可以*使用*内层的类型，但外层的公开 API 签名里不应暴露内层类型——否则内层类型的变更会传播给外层的调用方。

## 3. 依赖倒置跨越边界

内层需要调用外层能力时，依赖规则如何满足：

- **必须**：内层定义抽象，外层实现该抽象——抽象归内层，实现归外层
- **必须**：运行期的调用方向（内层调用外层实现）与源码依赖方向（外层依赖内层抽象）相反，这是正常的
- **禁止**：为了「让内层调用外层」而在内层引用外层，即使只引用一个接口

## 4. 跨层数据传递

这是整洁架构约束最严的部分，也是最常被简化掉的部分。

- **必须**：跨圈层传递的数据结构是**简单数据结构**，不含行为、不含框架标注
- **必须**：数据结构的定义归**内层**——内层定义它需要什么形状的数据，外层负责填充
- **禁止**：把实体对象直接传到接口适配层或基础设施层
- **禁止**：把外层的数据结构（请求对象、数据库行、UI 模型）传入用例层
- **应该**：每次跨越圈层都做一次转换。转换代码看起来重复，但它是层次独立演进的代价——省掉它等于把两层焊在一起

**允许的简化（须显式记录）**：层次少、数据结构简单、且团队规模小到不存在独立演进需求时，可共用同一数据结构。此时必须在架构决策记录中写明这是有意取舍，以及什么信号出现时要拆开（如两层的字段需求开始分叉）。

## 5. 与六边形架构的选择

二者不是竞争关系，是同一思想的两种表述粒度：

| 维度 | 六边形 | 整洁架构 |
|---|---|---|
| 核心内部划分 | 不划分 | 划分实体层与用例层 |
| 强调重点 | 端口的对称性（驱动/被驱动） | 依赖规则与跨层数据转换 |
| 适用信号 | 外部集成方式多样、需要多适配器 | 业务规则本身复杂、需与应用形态分离 |

- **应该**：两者选一，不要同时套用两套术语——术语混用会让「端口」「网关」「边界接口」指同一事物却各有三个名字
- **禁止**：把两套结构叠加成六层或八层；层次数量增加的成本是真实的，见 `rules/01-layering.md § 1. 分层模型的选择与统一`
