# 10 · 横切关注点的层次归属

> 更新历史：2026-08-29 创建。

日志、缓存、事务、校验、授权这些关注点跨越所有层次，因此「放哪一层」不会自然得出答案，必须显式决定。本篇给出归属判据与承载机制的选择。

各关注点的具体实现要求见对应领域：日志与脱敏、缓存上限与过期、数据访问事务、输入校验等的落地约束见 `knowledge-base/csharp/`（`rules/11-observability.md`、`rules/07-performance.md`、`rules/09-data-access.md`、`rules/14-security.md`）。

## 1. 归属判断的通用判据

对每个横切关注点问三个问题：

1. **它是业务规则还是技术手段？** 业务规则（「金额超过阈值需二次审批」）属核心层；技术手段（「重试三次」）属外层
2. **核心层的正确性是否依赖它？** 依赖 → 必须在核心层可见；不依赖 → 应对核心层透明
3. **换掉它的实现，核心层是否需要改动？** 需要 → 归属划分错误

- **必须**：每个横切关注点的归属层次是显式决定的，并记入架构决策记录
- **禁止**：同一关注点在多个层次各自实现一部分而无明确分工。这让「这里到底管不管」无法回答
- **应该**：对核心层透明的关注点用装饰或拦截承载（见 § 3），不侵入核心层代码

## 2. 各关注点的归属

| 关注点 | 归属 | 判据 |
|---|---|---|
| 日志 | 分两类：**技术日志**（调用耗时、外部请求）属外层；**业务事件记录**（审批通过、状态迁移）属核心层 | 业务事件是领域事实，技术日志是运行观测 |
| 缓存 | 应用层与基础设施层之间，对核心层透明 | 缓存是性能手段，核心层的正确性不应依赖是否命中缓存 |
| 事务 | 边界在**应用层**（一个用例一个事务）；核心层不感知事务 | 事务边界对应业务操作的原子性，由用例定义 |
| 输入格式校验 | 最外层（适配器/接口层） | 格式非法的输入不应进入核心层 |
| 业务规则校验 | 核心层 | 它就是业务规则，不是横切关注点 |
| 认证 | 最外层 | 「你是谁」是接入问题 |
| 授权 | 分两类：**接入级授权**（能否调用该操作）属外层；**数据级授权**（能否操作这一条）属核心层 | 数据级授权依赖业务状态，无法在外层判定 |
| 重试与超时 | 基础设施层（紧邻外部依赖处） | 是外部依赖不可靠性的应对，核心层不应感知 |
| 并发控制 | 乐观并发的**冲突判定**属核心层；锁与重试机制属外层 | 「什么算冲突」是业务规则 |

- **必须**：领域层不感知缓存、不感知事务、不感知重试
- **必须**：数据级授权在核心层判定；只在外层做授权检查的系统必然可被绕过
- **禁止**：把业务规则校验放在外层「以便早失败」。校验会随规则变化，放在外层会让规则分散在所有入口
- **禁止**：事务边界跨多个用例，或一个用例内开启多个事务而无补偿设计

## 3. 装饰与拦截的选择

对核心层透明的关注点有三种承载机制，成本与可见性不同：

| 机制 | 作用范围 | 可见性 | 适用 |
|---|---|---|---|
| 管道/中间件 | 整个入站路径 | 高——顺序显式声明 | 与接入方式绑定的关注点（认证、请求日志） |
| 装饰器 | 单个契约 | 高——装饰关系在装配处可见 | 少量特定契约需要该能力 |
| 拦截器/动态代理 | 按规则批量匹配 | 低——哪些被拦截需查配置 | 大量契约需要同一能力 |

- **应该**：按上表顺序优先——可见性高的机制优先，仅在数量使其不可行时降级
- **必须**：拦截规则的匹配范围明确可查；「所有以某后缀结尾的类型都被拦截」这类规则须在架构决策记录中写明
- **禁止**：多种机制叠加在同一关注点上。同时用中间件和拦截器做日志会得到重复记录，且排查时无法确定来源
- **禁止**：装饰或拦截改变被包装契约的语义（吞掉异常、改变返回值含义）。它们应当只增加行为，不改变契约
- **应该**：装饰链的顺序显式声明，不依赖注册顺序等隐式约定——顺序影响行为（缓存在重试内侧还是外侧结果不同）

## 4. 关注点之间的顺序

多个横切关注点作用于同一路径时，顺序影响正确性：

- **必须**：认证在授权之前
- **必须**：格式校验在业务处理之前
- **应该**：缓存在重试之外侧——命中缓存时不应触发重试逻辑
- **应该**：事务在缓存之内侧——事务未提交的数据不应进入缓存
- **必须**：顺序约束在装配处可读；靠「恰好这样注册了」维持的顺序会在重构时静默改变

## 5. 常见误用

- **禁止**：为「统一处理」把不相关的关注点合并到同一个拦截点。它会成为所有请求的必经之路，且承担多个变更理由
- **禁止**：横切关注点内含业务分支（「如果是某类订单则跳过缓存」）。业务判断属核心层，此处应改为由核心层决定是否可缓存
- **禁止**：把「所有方法都记日志」当成可观测性方案。全量日志的信噪比使其在排查时无用，且带来实际开销
- **应该**：横切关注点的失败处理策略显式定义——日志写入失败不应导致业务失败，而授权检查失败必须导致业务失败。二者不能用同一套错误处理
