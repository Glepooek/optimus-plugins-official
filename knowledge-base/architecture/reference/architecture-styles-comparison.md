# 架构风格横向对比

> 更新历史：2026-08-29 创建。

本文是 `rules/06-style-selection.md` 的配套参考，给出四种风格的对比与取舍理由。规范条款在 `rules/`，本文只提供判断所需的背景，不含 MUST/SHOULD/MAY 语气。

## 1. 四种风格解决的问题

每种风格都是对某个具体痛点的回应。理解它解决什么问题，比记住它的结构图更重要。

| 风格 | 回应的痛点 | 核心机制 |
|---|---|---|
| 简单分层 | 代码互相调用无序，改一处不知影响哪里 | 规定依赖方向，禁止反向与越层 |
| 六边形 | 业务逻辑与外部技术纠缠，无法在没有数据库的情况下测试 | 所有外部交互抽象为端口，实现为适配器 |
| 整洁架构 | 业务规则随应用形态（Web/批处理/CLI）变化而被牵动 | 把业务规则与用例编排分成两层，跨层强制数据转换 |
| DDD | 复杂业务规则散落各处，术语在不同团队含义不同 | 战略上划分限界上下文，战术上把规则集中到领域对象 |

**关键观察**：四者不是从低到高的进化阶梯。六边形与整洁架构解决的是**同一类**问题（隔离外部技术），DDD 解决的是**另一类**问题（业务复杂度）。一个系统可以只需要六边形而完全不需要 DDD，反之也成立。

## 2. 各自的代价

代价部分在推广材料中通常被省略，但它是选型的一半依据。

### 简单分层

- 跨层调用需逐层转发，简单操作也要穿过多层
- 层次划分标准不清时会出现「这个类该放哪层」的持续争议
- 依赖方向的强制需要工具支持（构建单元隔离或架构测试），否则靠人守

### 六边形

- 每个外部依赖至少增加一个抽象加一个实现
- 端口契约设计错误的代价高——契约按外部系统能力而非核心需要设计时，外部模型会经由端口渗入核心
- 团队需要理解「驱动端口」与「被驱动端口」的区别，术语学习成本真实存在

### 整洁架构

- 跨层数据转换代码量可观，且看起来是纯重复劳动
- 实体层与用例层的界线在实践中经常模糊——「这条规则是跨用例的还是单用例的」需要判断
- 严格执行「内层名称不出现在外层声明中」会导致大量转换类型，团队常在此妥协，妥协后收益随之减少

### DDD

- 成本在四者中最高：术语体系 + 建模投入 + 与领域专家的持续对话
- 战术模式（聚合、值对象）在业务规则薄的场景下会退化为空壳，此时全部成本已付出而收益为零
- 需要团队中有人真正理解，否则会得到「用了 DDD 词汇的三层架构」
- 聚合边界划错的代价高：聚合过大导致并发阻塞，聚合过小导致一致性无法保证

## 3. 什么情况下不该用

这一节比「什么情况下该用」更有价值，因为默认倾向总是「用上更规范」。

| 风格 | 不该用的情形 |
|---|---|
| 任何风格 | 代码规模小且不增长、生命周期短暂、纯数据搬运无业务规则、团队一到两人无交接 |
| 简单分层 | 单文件脚本、一次性迁移程序——分层的转发成本大于收益 |
| 六边形 | 单一接入方式 + 单一数据源 + 无替换计划。端口成为「多一层接口」 |
| 整洁架构 | 业务规则与用例编排分不开时。分不开说明四层是过度设计，两层已足够 |
| DDD 战术模式 | CRUD 应用、业务规则一次实现后长期稳定、无领域专家可对话 |
| DDD 战略设计 | 极少不适用——识别限界上下文与核心子域对任何规模都有价值，成本远低于战术模式 |

## 4. 组合形态

实践中很少只用一种。常见的有效组合：

| 组合 | 形态 | 适用 |
|---|---|---|
| 六边形 + DDD 战术 | 核心内用聚合与值对象，外部交互走端口 | 业务复杂且外部集成多样 |
| 整洁 + CQRS | 写侧走完整四层，读侧从接口适配层直达存储 | 读写负载与形状差异大 |
| DDD 战略 + 简单分层 | 划分限界上下文，每个上下文内部用简单分层 | 系统有多个业务能力，但每个能力内部规则不复杂 |
| 垂直切片 + 六边形 | 按功能切片，切片内部遵守端口约束 | 功能多、各功能间共性低 |

**无效组合**：六边形 + 整洁架构同时套用两套术语。二者主张重叠，同时使用会让「端口」「网关」「边界接口」指同一事物却各有三个名字。

## 5. 选型的常见误区

| 误区 | 实际情况 |
|---|---|
| 「先按最完整的做，以后不够用麻烦」 | 架构可增量引入，过度设计难以后减。已建成的层次很少有人主动拆掉 |
| 「大厂都在用，跟着做没错」 | 大厂的约束条件（团队规模、系统规模、变更频率）与多数团队不同。同样的结构在不同约束下成本收益完全不同 |
| 「用了框架就等于用了这个架构」 | 框架提供的是脚手架，依赖方向与边界仍需人守。有框架但依赖方向乱的系统很常见 |
| 「重构成某风格是技术债偿还」 | 只有当前结构确实在造成具体成本（改动面大、测试困难）时才是。否则重构本身是新增成本 |
| 「层次越多越解耦」 | 层次增加的是间接度，不是解耦度。解耦由依赖方向与契约质量决定，与层数无关 |

## 6. 决策记录该写什么

选型结论本身价值有限，有价值的是判断过程。一份有用的架构决策记录包含：

1. **当前的具体痛点**——不是「代码不够规范」，而是「改一个字段要动 7 个文件」
2. **被考虑过的选项**，含被排除的，以及排除理由
3. **选定方案的已知代价**——将来重新评估时，这一条是最重要的输入
4. **引入时的假设**——「会有第二个接入方」「规则会持续演进」。假设是否成立决定了收益是否兑现
5. **重新评估的触发条件**——什么信号出现时该重新考虑这个决策

第 4 与第 5 项最常被省略，也最有价值：`rules/06-style-selection.md § 7. 风格的演进与退出` 要求定期复核收益是否兑现，没有记录下当初的假设就无法复核。
