# .NET / C# 生态的架构决策记录

> 更新历史：2026-08-29 创建。

本文记录 .NET/C# 项目中反复出现的具体架构决策，以及各选项的实际代价。是 `rules/07-cqrs-and-slices.md`、`rules/08-module-boundaries.md`、`rules/09-composition-root.md`、`rules/10-cross-cutting.md` 的配套参考。

本文是 `reference/`，允许点名具体库与类型；`rules/` 保持语言无关。规范条款在 `rules/`，本文只提供判断背景，不含 MUST/SHOULD/MAY 语气。

## 1. 单体 vs 微服务的实际门槛

.NET 生态推广微服务的材料多，但门槛的讨论少。实际的成本构成：

| 成本项 | 单体 | 微服务 |
|---|---|---|
| 部署编排 | 一个产物 | 容器编排、服务发现、配置分发 |
| 跨服务调用 | 方法调用 | HTTP/gRPC/消息，需处理超时、重试、熔断 |
| 数据一致性 | 数据库事务 | 最终一致性、补偿事务或 Saga |
| 故障排查 | 单进程堆栈 | 分布式追踪，跨服务关联请求 |
| 本地开发 | 直接运行 | 需启动多个服务或用 mock 替代 |
| 集成测试 | 进程内 | 需要编排多服务环境 |

**中间态：模块化单体。** .NET 里的落地形态是多个类库项目 + 单个可执行项目，用 `ProjectReference` 的方向强制模块隔离，`InternalsVisibleTo` 控制受限可见性。这个形态获得了模块边界的全部收益（构建期强制、依赖方向可查），而不承担上表任何一项分布式成本。

**判断信号**：需要独立伸缩或独立部署频率时才拆服务；只是「团队各自开发」用模块化单体即可，见 `rules/08-module-boundaries.md § 6. 拆分独立部署单元的门槛`。

## 2. MediatR 类中介者库的收益与代价

`MediatR` 在 .NET 的 CQRS/垂直切片实践中几乎成为默认选择，但它解决的问题需要辨明。

**它实际提供的：**

1. 请求到处理器的分发（按类型匹配）
2. 管道行为（`IPipelineBehavior<,>`）——横切关注点的统一接入点
3. 进程内通知发布

**常被误认为的收益：**

- 「解耦调用方与处理方」——若两者在同一构建单元内，这种解耦不产生实际收益。调用方仍需知道请求类型，只是不知道处理器类型
- 「便于测试」——直接注入处理器接口同样可测，且更直接

**真实代价：**

- 调用关系无法用 IDE 的「转到定义」追踪；从 `Send(new XxxCommand())` 跳不到处理器
- 异常堆栈增加多层框架帧
- 新人需先理解分发机制才能读懂任一处业务代码
- 请求类与处理器类的数量翻倍（每个操作两个类型）

**判断依据**：管道行为是它的主要价值。若项目有三个以上横切关注点需要统一接入（验证、日志、事务、缓存），管道机制的收益能抵消间接层成本；若只有一两个，直接用装饰器更简单且可见性更高。见 `rules/07-cqrs-and-slices.md § 3. 中介者与命令分发`。

## 3. Repository 在 EF Core 之上是否仍必要

这是 .NET 里争议最久的架构问题之一，两侧都有站得住的理由。

**「不需要」一侧的论据：**

- `DbSet<T>` 本身就是 Repository 模式的实现，`DbContext` 本身就是 Unit of Work
- 在 EF Core 之上再包一层 Repository 通常会限制 `IQueryable` 的能力（无法按需 `Include`、无法组合查询条件），最终演化为大量 `GetByXxxWithYyy` 方法
- EF Core 已有 `InMemory` 与 SQLite 内存模式可用于测试

**「需要」一侧的论据：**

- 领域层不应引用 `Microsoft.EntityFrameworkCore`——这是依赖方向问题，与 EF Core 是否已实现 Repository 无关
- `IQueryable` 泄漏到应用层意味着查询能力泄漏，调用方可写出任意查询，性能问题的位置不可控
- 更换 ORM 或引入读侧独立存储时，无抽象层则改动面覆盖全部调用点

**实践中的折中形态：**

| 形态 | 做法 | 适用 |
|---|---|---|
| 无 Repository | 应用层直接用 `DbContext` | 简单分层、无 DDD、领域层不独立 |
| 聚合级 Repository | 只为聚合根提供 Repository，方法返回完整聚合 | DDD 项目——此时 Repository 是领域概念不是数据访问抽象 |
| 读写分离 | 写侧走聚合级 Repository，读侧直接用 `DbContext`/`Dapper` 查投影 | CQRS 二级分离，见 `rules/07-cqrs-and-slices.md § 2. 读写模型分离的判据` |

**关键区分**：DDD 里的 Repository 是**领域概念**（「聚合的集合」），不是「数据访问的抽象层」。按前者理解，它的方法按聚合的业务查询需要定义（`FindPendingApprovals()`），不按数据操作定义（`GetAll()` + `Where()`）；此时它不会退化成 `IQueryable` 的包装。

## 4. AutoMapper 类映射工具的取舍

整洁架构要求跨层数据转换（见 `rules/05-clean-architecture.md § 4. 跨层数据传递`），转换代码量可观，映射工具因此流行。

**收益：** 减少样板代码量。

**代价：**

- 映射错误从编译期移到运行期。手写赋值时字段改名会编译失败，约定映射时会静默产生 `null` 或默认值
- 映射配置成为隐式契约，`IDE` 找不到「这个字段的值从哪来」
- 复杂映射的配置代码往往比手写赋值更长且更难读
- 源生成式映射工具（`Mapperly` 等）在编译期生成代码，规避了运行期风险，是较新的替代方向

**判断依据**：跨层转换的字段是**机械对应**（同名同类型）时，映射工具的收益成立；存在计算、条件或结构变化时，手写更清晰。混合使用（简单映射用工具、复杂映射手写）是合理的，但须在同一项目内保持一致的判断标准。

## 5. 模块化单体在 .NET 的落地形态

`rules/08-module-boundaries.md § 5. 模块化单体` 的具体形态：

**项目结构：** 每个模块一个或多个类库项目，一个可执行宿主项目。

**边界强制手段：**

| 手段 | 作用 |
|---|---|
| `ProjectReference` 方向 | 构建期强制依赖方向，反向引用编译失败 |
| `internal` + `InternalsVisibleTo` | 模块内部类型不对其他模块可见，测试项目例外 |
| 每模块一个注册扩展方法 | 模块自带装配片段，由宿主汇聚，见 `rules/09-composition-root.md § 2. 注册的组织方式` |
| 架构测试（`NetArchTest` / `ArchUnitNET`） | 断言模块间引用规则，覆盖 `ProjectReference` 管不到的命名空间级约束 |

**模块间通信：** 进程内使用显式契约接口或进程内事件。刻意使用「跨进程也能成立」的形态（不传递可变对象引用、不依赖共享内存状态），为后续可能的拆分保留选项。

**常见偏差：** 建了多个项目但所有项目互相引用，或所有类型都是 `public`。此时项目边界不隔离任何东西，只增加了构建开销。

## 6. 横切关注点在 ASP.NET Core 的承载机制对照

`rules/10-cross-cutting.md § 3. 装饰与拦截的选择` 的三种机制在 .NET 的具体形态：

| 机制 | .NET 形态 | 可见性 |
|---|---|---|
| 管道/中间件 | `IMiddleware` / `app.Use...`；MVC 的 `IActionFilter` | 高——`Program.cs` 中顺序显式 |
| 装饰器 | 手写装饰类 + `Scrutor` 的 `Decorate<,>` 注册 | 高——装配处可见 |
| 拦截器 | `Castle.DynamicProxy`；`MediatR` 的 `IPipelineBehavior<,>` | 低——匹配规则需查配置 |

**顺序陷阱：** 中间件顺序即注册顺序，缓存与重试、事务与缓存的相对位置影响正确性（见 `rules/10-cross-cutting.md § 4. 关注点之间的顺序`）。`MediatR` 的 `IPipelineBehavior` 执行顺序由注册顺序决定，且与中间件顺序无关——两套机制同时使用时，完整执行顺序需要人工推演，这是不建议叠加使用的具体原因。

## 7. 依赖装配的启动期校验

`rules/09-composition-root.md § 5. 启动期校验` 在 .NET 的可用手段：

- `ServiceProviderOptions.ValidateOnBuild = true`——启动时校验所有注册的服务可被构造，缺失依赖立即失败
- `ServiceProviderOptions.ValidateScopes = true`——检出 `Singleton` 持有 `Scoped` 这类生命周期违规（这是 .NET DI 最常见的装配缺陷）
- 两项默认在 Development 环境开启，生产环境默认关闭。生产关闭的理由是启动耗时，但装配错误在生产环境的代价更高，值得重新评估这个默认值
- `IOptions<T>` 的 `ValidateOnStart()`——配置校验在启动期而非首次读取时执行

**为什么值得显式开启**：`Singleton` 持有 `Scoped` 的缺陷症状是「某个请求的数据出现在另一个请求里」，属最难排查的一类问题，而 `ValidateScopes` 能在启动期直接检出。
