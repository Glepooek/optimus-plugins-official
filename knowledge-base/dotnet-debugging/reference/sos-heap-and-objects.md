# SOS 命令：堆与对象

> 本篇覆盖「内存为什么涨、涨的是什么、谁持有它」三类问题的取证命令。

预防侧的编码规范——如何正确实现 `IDisposable`、事件订阅为何要解绑、LOH 该如何规避——见 `knowledge-base/csharp/rules/06-memory-resource.md`。本篇讲的是**那些规范被违反之后，在堆里长什么样**。

命令名前的 `!` 是 WinDbg 的扩展命令前缀。在 `dotnet-dump analyze` 中可省略。

## 1. !dumpheap

### 用途与前置条件
按类型统计或逐对象列出托管堆内容。内存持续增长时的**第一条命令**——它给出"涨的是什么类型、涨了多少"的全景，后续用 `!gcroot` 深入某个可疑类型找持有者。任何类型的 dump 都支持。

### 语法与关键开关
```
!dumpheap -stat              # 按类型聚合统计，不逐对象列出
!dumpheap -type <类型名片段>  # 按类型名子串筛选
!dumpheap -mt <MT地址>        # 按方法表地址筛选（比 -type 精确，避免子串误匹配）
!dumpheap -min <字节数>       # 只显示不小于该大小的对象
!dumpheap -max <字节数>       # 只显示不大于该大小的对象
!dumpheap -short              # 只输出对象地址，便于喂给后续命令批量处理
```

`-mt` 与 `-type` 常配合使用：先 `-stat` 找到可疑类型的 MT 地址，再用 `-mt` 精确筛出该类型的全部实例地址。`-min 85000` 可直接筛出进入 LOH 的对象（阈值见 `reference/clr-runtime-anatomy.md § 2. 大对象堆（LOH）与固定对象堆（POH）`）。

### 输出逐列语义

`!dumpheap -stat` 的输出列（不加 `-stat` 时逐对象列出，无 `Count`/`TotalSize` 聚合列，改为每行一个对象地址）：

| 列 | 含义 | 异常信号 |
|---|---|---|
| `MT` | 该类型的方法表地址 | 可喂给 `-mt` 精确筛选该类型全部实例 |
| `Count` | 该类型在堆上的实例数 | **数量异常增长是泄漏的第一信号**（见下方判据） |
| `TotalSize` | 该类型全部实例的浅层总字节数（不含子对象/字符串等引用字段的大小） | 单一类型占比过高需结合 `Count` 判断是"个体大"还是"数量多" |
| `Class Name` | .NET 类型全名 | —— |

**经验性知识（出自书籍知识体系，无官方文档佐证）**：排查泄漏时，**按 `Count` 排序看泄漏、按 `TotalSize` 排序看绝对量**——数量异常比体积异常更能指向泄漏，因为泄漏的典型形态是同类对象无限累积（如未退订的事件处理器、无界缓存），单个对象体积通常不变而是数量线性或阶梯式上涨；`TotalSize` 排序能看出当前内存主要花在哪个类型上，但体积大不等于在泄漏（也可能是合法的大缓存或大对象一次性分配）。

### 判据：能证实 / 排除什么
- 同一进程间隔一段时间两次 `-stat`，某类型 `Count` 持续上涨而其余类型基本不变 → **证实**该类型是泄漏嫌疑对象，转 `!dumpheap -mt <该类型MT>` 取实例地址，再对可疑实例执行 `§ 4. !gcroot` 找持有者
- `Count` 平稳但 `TotalSize` 异常高 → **排除**"数量堆积型"泄漏，转查是否存在少数超大对象（`-min 85000` 筛查 LOH 分配）
- 输出末尾出现 `Free` 类型且 `TotalSize` 占比高 → 表示已回收但未归还操作系统的堆碎片空间，**不是**泄漏信号，指向堆碎片化而非对象持有

## 2. !dumpobj

### 用途与前置条件
展开单个对象地址的字段：方法表、`EEClass`、大小与每个字段的类型/偏移/值。定位到可疑类型后的**第二步**——`!dumpheap` 给出全景与地址，`!dumpobj` 深入某个具体实例看它内部持有什么引用。任何类型的 dump 都支持。

### 语法与关键开关
```
!dumpobj <对象地址>
!dumpobj -nofields <对象地址>    # 不展开字段，只显示对象头信息（大字符串等场景用于降噪）
```

对象地址来自 `!dumpheap`（逐对象列出模式或 `-short` 输出）或 `§ 5. !dso`。字段类型为 `CLASS`（引用类型）的字段值本身是另一个对象地址，可对其再次执行 `!dumpobj` 逐层下钻；字段类型为 `VT`（值类型，即结构体内联字段）时不能直接 `!dumpobj`，需用 `!dumpvc`。

### 输出逐列语义

| 列 | 含义 | 异常信号 |
|---|---|---|
| `Name` | 对象的 .NET 类型全名 | —— |
| `MethodTable` | 该类型的方法表地址 | 可喂给 `!dumpheap -mt` 查看同类型全部实例 |
| `EEClass` | 类型的运行时元数据结构地址 | —— |
| `Size` | 对象浅层大小（字节） | 与 `!dumpheap -stat` 的 `TotalSize` 对应但是单实例值 |
| `Fields` 表：`MT` / `Offset` / `Type` / `VT` / `Attr` / `Value` / `Name` | 逐字段的方法表、偏移、类型、是否值类型、实例/静态属性、当前值、字段名 | `VT=1` 表示值类型内联字段，`Value` 列不是地址不能直接 `!dumpobj`；`Attr=static` 的字段不随实例变化，是潜在的静态根来源 |

### 判据：能证实 / 排除什么
- 某字段 `Attr` 为 `static` 且 `Type` 为集合类型（如 `List`、`Dictionary`） → **证实**该类型存在静态持有的集合，是无界缓存泄漏的直接证据，转查 `knowledge-base/csharp/rules/06-memory-resource.md § 5. 静态引用`
- 逐层展开 `CLASS` 字段最终追到一个已知的长命对象（如单例服务、`static` 容器） → **证实**当前对象的持有链终点，可作为 `!gcroot` 结果的交叉验证
- 字段 `Value` 显示为 `0x00000000`（空引用） → **排除**该字段是持有原因，无需继续下钻此分支

## 3. !objsize

### 用途与前置条件
计算指定对象及其可达引用图（子对象、字段引用的对象等）的总大小（保留大小），而非 `!dumpobj`/`!dumpheap` 给出的浅层大小。用于判断"这个对象真正占了多少内存"——一个看似很小的对象若持有一棵庞大的子图（如一个 `List<byte[]>` 字段），浅层大小无法反映其真实内存代价。仅 Windows 平台支持。

### 语法与关键开关
```
!objsize <对象地址>              # 计算单个对象的保留大小
!objsize -stat -aggregate         # 配合 !dumpheap -stat 使用，展示仍被根引用的类型明细
```

不带参数执行时，命令会对当前所有可从托管线程栈可达的对象与全部 GC 句柄逐一求和，代价较高，仅在小范围诊断时使用；带具体地址执行是常规用法。

### 输出逐列语义

`!objsize <地址>` 的输出是单行结果，不是表格：

```
sizeof(<地址>) = <字节数> (<十六进制字节数>) bytes (<类型全名>)
```

| 字段 | 含义 | 异常信号 |
|---|---|---|
| `sizeof(...)` 数值 | 该对象加上其整个可达引用图的总字节数 | 远大于 `!dumpobj` 报的 `Size`（浅层大小）说明该对象持有庞大子图 |
| 括号内类型名 | 被计算对象的 .NET 类型全名 | —— |

### 判据：能证实 / 排除什么
- `!objsize` 结果远大于 `!dumpobj` 的 `Size` 字段 → **证实**该对象通过引用持有一棵大的子图，真实内存代价在子图而非对象本身，需要展开子图找具体是哪个字段占大头
- 多个根对象的 `!objsize` 结果相加远超 `!dumpheap -stat` 报出的堆总大小 → **排除**"各根互不相交"的假设——多个根共享了同一段字符串驻留（intern）或子图，直接相加发生了重复计数，不能作为总内存的可靠依据

## 4. !gcroot

### 用途与前置条件
从指定对象地址反向追溯，找出是谁（哪条引用链）让该对象保持存活——托管堆本身、句柄表、线程栈与终结队列全部纳入搜索范围。这是内存泄漏定位的**核心命令**：`!dumpheap` 找到可疑类型、`!dumpobj` 看清对象内部字段之后，`!gcroot` 回答"为什么这个该被回收的对象还活着"。

### 语法与关键开关
```
!gcroot <对象地址>
!gcroot -nostacks <对象地址>   # 跳过线程栈扫描，只搜句柄表与堆可达对象
!gcroot -all <对象地址>         # 显示全部根路径而非去重后的唯一根
```

线程栈是保守式扫描——命令无法区分栈上某个位置是"仍在使用的局部变量"还是"上一次调用遗留、尚未被覆盖的陈旧字节"，因此栈根存在**假阳性**，官方文档明确说明这一点须靠 `!clrstack`/`u` 反汇编确认该栈槽是否仍被使用。`-nostacks` 是排除这类噪声的直接手段：怀疑某条根是栈假阳性时，加此开关重新运行，若报告的根路径消失即证实是假阳性。

### 输出逐列语义

`!gcroot` 的输出是根路径链，不是表格，形如：

```
<根来源> -> <对象类型1> -> <对象类型2> -> ... -> <目标对象>
Found N unique roots.
```

| 根来源标记 | 含义 | 异常信号 |
|---|---|---|
| `HandleTable: <地址> (pinned handle)` | 该对象被一个固定句柄根住 | 常见形态：静态字段实际存储于运行时内部的固定对象数组，根路径末端会先经过一个 `pinned handle`，再指向该数组，才到达真正持有它的静态字段所在类型 |
| `HandleTable: <地址> (strong handle)` | 该对象被一个强句柄根住 | 强句柄不会自动释放，除非显式 `Free` 或 AppDomain 卸载 |
| `Scan Thread N OSTHread <ID> ESP:<地址>:Root:...` | 该对象被某线程栈上的一个局部变量/参数引用 | **可能是假阳性**，需配合 `!clrstack`/`u` 确认该栈槽是否仍在用；也可直接用 `-nostacks` 重跑排除 |
| `Found N unique roots.` | 去重后的根路径总数 | `0` 表示无根路径，见下方判据 |

### 判据：能证实 / 排除什么

| 根路径末端形态 | 指向的根因 | 对应规范 |
|---|---|---|
| 静态字段（`static var`） | 静态集合无限增长、静态缓存无淘汰 | `knowledge-base/csharp/rules/06-memory-resource.md § 5. 静态引用` |
| 事件的 `_invocationList` | 事件订阅未解绑，发布者存活导致订阅者无法回收 | `knowledge-base/csharp/rules/06-memory-resource.md § 4. 事件与委托泄漏` |
| `Pinned handle` | 固定对象未释放，常见于原生互操作缓冲区 | `reference/clr-runtime-anatomy.md § 7. 句柄表` |
| 无根路径（输出为空） | **排除**托管泄漏，转查非托管内存或句柄泄漏（`§ 6. !gchandles`） | —— |

## 5. !eeheap

### 用途与前置条件
报告运行时内部数据结构占用的进程内存，分 `-gc`（垃圾回收堆结构）与 `-loader`（加载器堆）两部分。`!dumpheap -stat` 只统计对象本身占用，`!eeheap -gc` 能看到堆段的提交/保留边界，用于判断"内存涨在托管对象上还是涨在堆结构本身（如段膨胀、加载器堆）"。

### 语法与关键开关
```
!eeheap -gc        # 显示各代（gen0/1/2）、LOH、POH 的段范围与大小
!eeheap -loader     # 显示各 AppDomain / 程序集的加载器堆用量
```

`-gc` 与 `-loader` 可分别单独执行，也可都不加（等价于两者都显示）。判断"内存主要在托管堆还是别处"时，先跑 `-gc` 排除托管堆是否已经占满预期内存量。

### 输出逐列语义

`-gc` 部分按 GC 堆（工作站 GC 通常 1 个，服务器 GC 每核 1 个）列出分代段表：

| 列/字段 | 含义 | 异常信号 |
|---|---|---|
| `generation 0/1/2 starts at` | 各代在托管堆中的起始地址 | —— |
| 段表 `begin` / `allocated` / `size` | 每个堆段的起始地址、已分配到的位置、段总大小 | `allocated` 接近 `size` 且段数持续增多 → 该代持续扩张 |
| `Large object heap` 段 / `Pinned object heap` 段 | LOH / POH 各自的段范围与大小，语义见 `reference/clr-runtime-anatomy.md § 2. 大对象堆（LOH）与固定对象堆（POH）` | LOH 段数增多但 `!dumpheap -stat` 中大对象计数未同比增长 → 碎片化而非真实增长 |
| `GC Heap Size` 总计 | 全部堆段大小之和 | 可与 `!dumpheap -stat` 的 `TotalSize` 总和交叉核对，量级应接近 |

`-loader` 部分按 AppDomain/程序集列出加载器堆大小，无固定列名，核心是一个总字节数。

### 判据：能证实 / 排除什么
- `GC Heap Size` 总计与进程实际内存占用（如任务管理器读数）量级接近 → **证实**内存主要花在托管堆，问题定位应集中在 `!dumpheap`/`!gcroot`；若差距悬殊则**排除**托管堆是主因，转查非托管内存（句柄、原生分配）
- `-loader` 输出中某程序集对应的加载器堆持续增长 → **证实**该程序集被反复动态加载而未卸载（常见于反射生成程序集、插件热加载场景），加载器堆本身不受常规 GC 回收管理

## 6. !gchandles

### 用途与前置条件
按类型（Strong / Pinned / Weak / RefCount 等）统计进程当前的 GC 句柄数量。托管对象泄漏用 `!gcroot` 能追到根，但**句柄本身**的泄漏（代码持有一个强句柄却忘记 `Free`）不会在托管堆对象计数里直接体现——`!gchandles` 是发现这类问题的入口。仅 Windows 平台支持。

### 语法与关键开关
```
!gchandles
!gchandles -perdomain    # 按 AppDomain 分组统计
```

句柄类型语义见 `reference/clr-runtime-anatomy.md § 7. 句柄表`。怀疑具体是哪个句柄泄漏时，配套命令 `!gchandleleaks` 会扫描全部内存寻找指向该强/固定句柄的引用，帮助定位是哪段代码持有它（本篇不收录该命令的完整用法，仅提示存在）。

### 输出逐列语义

```
Handles:
    Strong Handles:       <N>
    Pinned Handles:        <N>
    Ref Count Handles:     <N>
    Weak Long Handles:      <N>
    Weak Short Handles:     <N>
    SizedRef Handles:       <N>
```

| 字段 | 含义 | 异常信号 |
|---|---|---|
| `Strong Handles` | 强句柄数，持续存活直至显式释放 | 数量持续增长且无对应释放路径 → **证实**强句柄泄漏，常见于 COM 互操作场景创建后未 `GCHandle.Free()` |
| `Pinned Handles` | 固定句柄数，阻止 GC 移动其指向对象 | 数量过多 → 堆压缩效率下降，表现为碎片增多（与 `!eeheap -gc` 的 LOH/POH 碎片征象呼应） |
| `Ref Count Handles` | 引用计数句柄，计数归零后退化为弱句柄，多用于 COM 互操作 | 计数长期不归零 → COM 端未按预期释放引用 |
| `Weak Long Handles` / `Weak Short Handles` | 弱句柄，不阻止对象回收 | 通常无需关注，用于跟踪对象而非阻止回收 |
| `SizedRef Handles` | 带大小提示的句柄，用于 GC 决策 | 通常无需关注 |

### 判据：能证实 / 排除什么
- `Strong Handles` 与 `Pinned Handles` 计数随时间单调增长，而 `!dumpheap -stat` 中对应类型的托管对象计数保持稳定 → **证实**问题是句柄泄漏而非托管对象泄漏——对象本身可能已经没有其他托管引用，仅靠这个未释放的句柄维持存活，`!gcroot` 会显示根路径终止于 `(strong handle)` 或 `(pinned handle)`
- 全部句柄计数长期稳定，但进程内存仍在增长 → **排除**句柄泄漏，转查非托管代码自身的分配（`malloc`/`new` 未配对释放），已超出 SOS 命令的取证范围，需要原生内存分析工具
