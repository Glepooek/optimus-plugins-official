# CLR 运行时可观测结构

> 本篇解释在 dump 或运行中进程里**能观察到什么**，以及各结构的语义。它是读懂 `sos-*` 系列命令输出的术语基础——命令输出的每一列都对应本篇的某个结构。

本篇不含命令，只含结构。命令见 `reference/sos-threads-and-stacks.md`、`reference/sos-heap-and-objects.md`、`reference/sos-locks-and-async.md`。

预防侧的编码规范（如何避免泄漏、如何正确实现 IDisposable）见 `knowledge-base/csharp/rules/06-memory-resource.md`。

## 1. 托管堆分代结构

**用途**：CLR 的垃圾回收器基于「大多数对象活得很短」的假设分代管理托管堆。堆分为 gen0、gen1、gen2 三代，新对象总是分配在 gen0；一次 gen0 回收后仍存活的对象晋升到 gen1，gen1 回收后仍存活的晋升到 gen2。分代的意义在于让高频的小范围回收（gen0）代价低，而全堆扫描（gen2）只在必要时发生。gen0/gen1 合称「短暂代」，各自的分配预算（budget）会随存活率动态调整。

.NET Framework 与早期 .NET Core 用**段（segment）**组织堆内存，每个段是一段连续虚拟内存，gen0/gen1/gen2 各自使用不同段。.NET 5+ 引入**区域（region）**布局，堆被划分为固定大小的小块，同一代的对象可以分散在多个 region 中，不再要求同代对象物理连续——这一变化降低了大堆场景下的虚拟内存碎片。

**在 dump 中的可观测形态**：`!eeheap -gc` 输出按段/区域列出每一代的起止地址与大小；`!dumpheap -stat` 按类型聚合统计整个托管堆（跨代）的对象计数与总大小。可以通过 `!gcroot` 定位一个对象为何仍存活（哪条根引用链持有它），进而判断它本应在哪一代被回收却未被回收。

**异常时的征象**：gen0/gen1 大小持续增长且回收后未回落，指向短命对象被意外持有（如被静态字段或长命对象的字段引用）而晋升到 gen2，逃过了本该高频发生的短暂代回收；gen2 大小单调增长且伴随进程整体内存增长，指向真正的托管内存泄漏——需要配合 `!gcroot` 找到持有链的根。

## 2. 大对象堆（LOH）与固定对象堆（POH）

**用途**：单个对象大小达到 85000 字节阈值时，CLR 不将其分配在常规的 gen0/gen1/gen2 段中，而是分配到**大对象堆（Large Object Heap，LOH）**。LOH 在逻辑上归属 gen2（随 gen2 回收一并扫描），但物理上是独立的段。这样设计的原因是大对象复制（compact）代价高——移动一个几十 KB 甚至几 MB 的对象比移动一个几十字节的对象昂贵得多，因此 LOH 默认**不做压缩整理**，只做「标记-清除」不做「标记-清除-压缩」。

**固定对象堆（Pinned Object Heap，POH）**是 .NET 5 引入的独立堆区域，专门承载被 `GCHandleType.Pinned` 或 `fixed` 语句固定的对象。固定对象在物理内存中的地址不能被 GC 移动（常见于与非托管代码互操作、传递缓冲区指针的场景）。在 POH 出现之前，固定对象散落在常规堆中，每个固定对象都会阻止其所在的整个内存区域被压缩；POH 把这类对象集中隔离，避免它们拖累常规堆的压缩效率。

**在 dump 中的可观测形态**：`!eeheap -gc` 输出中 LOH 与 POH 分别列为独立的段范围；`!dumpheap -stat` 中占用超阈值的类型可在 `!dumpheap -min 85000` 中单独筛出。LOH 因不压缩而产生的碎片可通过比较「LOH 总提交内存」与「LOH 内实际存活对象总大小」观察到——两者差值大即碎片严重，即使 `GC.Collect()` 回收了大量对象，LOH 段占用的虚拟内存也不会随之缩小。

**异常时的征象**：LOH 段数量或总大小持续增长但对象计数并未同比增长，指向大对象分配后长期存活或碎片化严重，导致新分配无法复用已释放的空洞、只能开辟新段；进程出现 `OutOfMemoryException` 但常规堆（gen0-2）总量看起来并不大时，往往是 LOH 碎片导致找不到足够大的连续空闲块——这是「堆没满但分不出连续空间」的典型形态。POH 对象数量异常增长通常指向非托管互操作场景中固定的缓冲区未按预期释放。

## 3. 同步块表

**用途**：每个托管对象在其对象头中预留了一段用于并发控制与身份标识的元数据空间（32 位进程 4 字节、64 位进程 8 字节）。这段对象头**不直接存放**锁状态的完整数据结构——出于内存效率考虑，绝大多数对象从未被加锁、从未被调用 `GetHashCode`，如果每个对象都预分配一个完整的同步块，开销无法接受。CLR 采用两级机制：

- **瘦锁（thin lock）**：对象头直接存储线程 ID 与递归计数。当调用 `Monitor.Enter`（`lock` 语句的底层实现）且当前没有其他线程持有该对象的锁时，直接把持有者线程的 ID 写入对象头，这是无竞争路径下开销最小的加锁方式。
- **同步块（sync block）膨胀**：当发生下列情况之一时，瘦锁不足以表达所需状态，对象头改为存一个索引，指向 CLR 维护的**同步块表**（SyncBlockTable）中的一个条目：
  - 发生锁竞争（另一个线程尝试获取已被持有的锁，需要等待队列）
  - 调用了 `Object.GetHashCode()`（默认哈希码需要一个稳定的存储位置，不能像瘦锁那样被随时覆盖）
  - 需要 `Wait`/`Pulse`（`Monitor.Wait`/`Monitor.PulseAll`，依赖同步块记录的等待线程集合）

膨胀后的同步块条目记录：当前持有锁的线程、递归进入计数、等待获取锁的线程队列、等待 `Pulse` 通知的线程队列。膨胀是单向的——同步块一旦分配，即使锁被释放也不会退化回瘦锁，只会被标记为可回收复用。

> **经验性知识**：对象头的字节布局细节（瘦锁在无竞争时直接存 ThreadId、膨胀阈值的具体触发条件组合）出自《Advanced .NET Debugging》一类书籍对 CLR 内部实现的记录，微软官方诊断文档未逐字节公开该布局，随 CLR 版本演进可能有出入，此处按其描述的行为模式呈现，不代表逐字节精确到当前所有运行时版本。

**在 dump 中的可观测形态**：`!syncblk` 列出进程中所有已膨胀的同步块，每行包含索引号、对应对象地址、持有线程的 OS 线程 ID、递归计数、等待队列中的线程数。`!dumpobj` 查看单个对象时会显示其 `SyncBlock` 字段是否指向了某个索引（瘦锁状态下该字段为空或显示线程 ID 直存形式）。判断死锁的核心数据来源正是 `!syncblk`：若线程 A 持有的同步块正是线程 B 在等待队列中的目标，同时线程 B 持有的另一同步块又是线程 A 在等待的目标，即构成循环等待。

**异常时的征象**：`!syncblk` 输出条目数持续增长，指向大量对象曾发生锁竞争或被调用 `GetHashCode` 后未被回收（常见于把自定义对象当 `Dictionary`/`HashSet` 的 key 且该对象生命周期很长）；出现多线程互相等待对方持有的同步块，即为死锁，`!syncblk` 的持有线程列与等待线程列可直接连成等待图。

## 4. 终结队列

**用途**：实现了终结器（`~ClassName()`）的对象在构造完成时，CLR 会把它的引用登记进**终结队列（Finalization Queue）**——这是一份 GC 内部维护的强引用列表，独立于对象是否还有其他可达路径。终结队列的存在使得「对象没有终结器」与「对象有终结器」在回收流程上分道扬镳：

- 无终结器的对象一旦不可达，本次 GC 直接回收。
- 有终结器的对象即使不可达，本次 GC 也**不会**立即回收，而是把它从终结队列移到 **F-Reachable 队列（Finalizer Reachable Queue）**，并暂时把它标记为存活（因为终结队列本身持有对它的引用，等同于一次「复活」）。真正的内存回收要等到**下一次**该对象所在代发生 GC、且此时它的终结器已经跑完、对象再次变得不可达时才会发生。

F-Reachable 队列由一个专门的**终结器线程（Finalizer Thread）**单线程串行消费：该线程逐个取出 F-Reachable 队列中的对象，调用其 `Finalize` 方法。这个线程是进程内唯一负责执行终结器代码的线程。

**在 dump 中的可观测形态**：`!finalizequeue` 列出当前终结队列与 F-Reachable 队列中按类型分组的对象计数与地址，可以直接看出「有多少个 XxxClient 对象正等待终结」。`!threads` 可以定位到 Finalizer 线程（标记为 `Finalizer` 或类似标注），若该线程当前调用栈卡在某个终结器方法内部（例如卡在一次同步的非托管资源释放调用中），说明终结器执行本身被阻塞。

**异常时的征象**：终结队列本身正常增长通常无害（对象终结前的正常等待），但若 F-Reachable 队列条目数持续增长且不回落，指向终结器线程执行速度跟不上对象产生速度——由于终结器线程是单线程串行执行，任何一个终结器方法内的阻塞调用（如同步等待网络释放）都会拖慢队列中所有后续对象的终结。这在应用层表现为「对象已不可达但内存/句柄迟迟不回收」，且这类对象至少经历两轮 GC 才能真正释放（先复活一次，再等下一轮）——这解释了为何持有非托管资源却依赖终结器兜底的对象，回收总是比预期慢一拍。

## 5. 线程池内部结构

**用途**：.NET 线程池维护一组工作线程，用于执行排入队列的工作项（`ThreadPool.QueueUserWorkItem`、`Task.Run`、异步 I/O 完成后的续体等）。工作项的排队结构分两级：

- **全局队列（Global Queue）**：没有明确关联到某个线程的工作项进入这里，任意空闲工作线程都可能取走它。
- **本地队列（Local Queue）**：每个工作线程维护一个自己的本地队列（work-stealing queue），线程优先处理自己本地队列里的任务（局部性更好、无需跨线程同步），本地队列为空时才去全局队列或**窃取（steal）**其他线程本地队列尾部的任务。

线程池的线程数量不是固定的，而是由**爬坡算法（Hill Climbing）**动态调节：算法持续观察吞吐量随线程数变化的趋势，逐步试探性增减线程数以逼近吞吐量最优点。这一算法的关键约束是**线程注入速率有上限**——线程池不会在检测到任务积压后立即创建大量新线程，而是每隔一小段时间（默认约 500 毫秒量级）才评估是否新增一个线程。这个限速设计是为了避免瞬时任务尖峰导致线程数暴涨、上下文切换开销反噬吞吐量。

**在 dump 中的可观测形态**：`!threadpool` 输出当前工作线程数、空闲线程数、CPU 利用率、全局队列中排队的工作项数量。`!dumpqueue` 或 `!threadpool` 的队列长度字段可以看到全局队列积压情况；结合多次采样的时间序列可以看出线程数增长的斜率是否符合爬坡算法的限速特征。

**异常时的征象**：线程池饥饿（thread pool starvation）在 dump 中的典型形态是：全局队列中排队的工作项数量远超当前线程数，且线程数增长明显滞后于队列积压——因为受限于注入速率上限，线程池不能瞬间补足缺口。这在应用层表现为**请求延迟呈阶梯式上升**而非线性劣化：每隔一个注入周期线程数增加一点、处理能力才提升一点，与线性增长的负载曲线不同步，造成延迟曲线出现台阶状拐点，而不是随负载平滑上升。

饥饿的**成因**（如何避免耗尽线程池：全链路异步、避免同步阻塞等待）见 `knowledge-base/csharp/rules/04-async-programming.md § 1. 全链路异步`；`knowledge-base/csharp/rules/04-async-programming.md § 2. 反模式表`；本篇只负责饥饿发生后**如何从 dump 中识别**它。

## 6. GC 模式

**用途**：CLR 的垃圾回收器沿两个正交维度提供可配置模式：

- **工作站 GC（Workstation GC）vs 服务器 GC（Server GC）**：工作站 GC 只维护一个堆、一个 GC 线程，回收时该线程与应用线程交替执行（或短暂暂停应用线程），适合客户端类应用（GC 线程抢占 CPU 会影响 UI 响应）。服务器 GC 为每个逻辑 CPU 核心维护一个独立的堆和专属 GC 线程，回收时多个 GC 线程并行工作，牺牲部分内存开销（多堆意味着多份分配预算）换取更高吞吐，适合多核服务端进程。
- **并发/后台 GC（Concurrent/Background GC）开关**：默认开启。后台 GC 允许 gen2 的标记阶段与应用线程并发执行，只在必须暂停的短暂阶段（如最终标记）才挂起应用线程，从而缩短一次完整 gen2 回收对应用造成的暂停时间。关闭后台 GC 会让 gen2 回收变为完全阻塞式（stop-the-world），暂停时间显著变长。

两个维度可以组合：工作站+并发、工作站+非并发、服务器+后台、服务器+非并发（服务器 GC 场景下也有独立的后台 GC 开关）。

**在 dump 中的可观测形态**：`!eeheap -gc` 输出的堆数量直接反映当前模式——工作站 GC 只有 1 个堆，服务器 GC 有多个堆（数量通常等于逻辑核心数）。`!threads` 中可见的 GC 相关线程数量与命名模式（如 `BGC`）也能佐证是否启用了后台 GC。运行时配置本身（`gcServer`/`gcConcurrent` 设置项）在托管代码里可通过 `System.GC.Server`（部分版本暴露）或读取生效的 `runtimeconfig.json`/环境变量间接确认，但从 dump 现场最直接的证据仍是堆数量。

**异常时的征象**：服务器进程若观察到只有 1 个堆（应为服务器 GC 却实际是工作站 GC），说明配置未生效，GC 吞吐可能成为多核场景下的瓶颈；工作站 GC 进程若观察到 GC 暂停时间异常长且没有并发标记的迹象，可能是后台 GC 被显式关闭或运行环境不支持并发（如某些资源受限的容器环境）。GC 模式与实际负载不匹配是「CPU 利用率正常但吞吐上不去」或「间歇性长暂停」这两类问题的常见候选根因之一。

## 7. 句柄表

**用途**：**GC 句柄（GC Handle）**是 CLR 提供的一种机制，让托管对象可以被托管堆回收算法之外的实体（通常是非托管代码，或需要跳过常规可达性规则的托管代码）持有引用。所有 GC 句柄集中记录在**句柄表（Handle Table）**中，按用途分为四类：

| 句柄类型 | 语义 |
|---|---|
| 强句柄（Strong Handle，`GCHandleType.Normal`） | 等同于一条强引用，只要句柄存在，对象就不会被回收，即使对象在托管代码中已无任何其他引用 |
| 弱句柄（Weak Handle，`GCHandleType.Weak`/`WeakTrackResurrection`） | 不阻止对象回收，对象被回收后句柄失效（取值为 null），用于「能访问就访问、不能访问就重建」的场景 |
| 固定句柄（Pinned Handle，`GCHandleType.Pinned`） | 既是强引用又固定对象地址，使其在整个句柄存活期间不会被 GC 移动，用于把托管缓冲区地址传给非托管 API |
| 句柄用于 COM 互操作场景的 RCW/CCW 引用计数 | 运行时可调用包装（RCW）与 COM 可调用包装（CCW）内部依赖句柄维持托管对象与非托管 COM 对象之间的双向引用关系 |

句柄表条目数与常规对象数是两套独立的计数体系——一个对象可以同时被多个句柄引用，句柄本身占用的是句柄表的槽位，不是托管堆的对象空间。

**在 dump 中的可观测形态**：`!gchandles` 列出句柄总数、按类型分组的计数（Strong/Weak/Pinned/其他），以及占用最多句柄的类型统计。`!gcroot` 对某个对象的可达性分析中，若根路径显示为 `HANDLE` 类型的根，说明该对象是通过某个 GC 句柄保活的，而非常规的栈/静态字段引用链。

**异常时的征象**：句柄总数随时间持续单调增长且不回落，是「非托管资源泄漏」的典型指标——常见于 COM 互操作场景中 RCW 未被正确释放（未调用 `Marshal.ReleaseComObject` 或未走完整的 `using`/`Dispose` 流程），或托管代码显式分配了 `GCHandle`（尤其是 `Pinned` 类型）却遗漏 `GCHandle.Free()`。Pinned 句柄数量异常增长还会连带表现为常规堆碎片化加剧（因为被固定的对象阻止其所在区域被压缩，参见第 2 节 POH 的引入动机）。Windows 上句柄数增长到系统上限还会触发进程级别的资源耗尽错误，与托管内存是否充足无关。
