# dump 类型与取证能力

> 选错 dump 类型是排查中最贵的返工——拿到一个 Triage dump 却要查内存泄漏，只能重抓，而故障现场可能已经消失。本篇给出四种类型的取证能力边界。

抓取命令见 `reference/dump-capture.md`；dump 文件的合规处置见 `rules/01-dump-handling.md`。

## 1. 四种类型的能力对照

四种类型名（`Mini`、`Heap`、`Triage`、`Full`）不是同一个命令的统一取值——四个产出接口各自暴露的取值范围不同，但 `Triage` 并非只有一两条产出途径：`dotnet-dump collect --type Triage`、`procdump -mt`、`createdump -t`、`DOTNET_DbgMiniDumpType=3` 四条路径均可产出（开关表分别见 `reference/dump-capture.md § 1. procdump（Windows，全运行时）`、`§ 2. dotnet-dump collect（.NET Core 3.0+，跨平台）`、`§ 3. createdump（.NET Core 3.0+，Linux 优先）`、`§ 5. DOTNET_DbgEnableMiniDump（.NET Core 3.0+，崩溃自动抓取）`）。

**易错点**：微软官方 `dotnet-dump` 参考页在 `--type` 选项处存在文档自身的签名与正文不一致——选项签名写作 `<Full|Heap|Mini>`、概述句也称"共三种类型"，但紧随其后的取值列表实际逐项列出了第四项 `Triage`。照签名或概述句直接下结论会误以为该命令不支持 `Triage`；`dotnet-dump collect` 的源码（`Dumper.cs` 的 `DumpTypeOption` 枚举与 `Collect` 内两处 switch）也确认 `Triage` 是受支持且无平台门控的取值，需以取值列表逐项核对为准，不能只看签名。四个类型名描述的是同一套抽象语义，只是各工具/接口暴露的取值范围不同。

| 类型 | 保留 | 剥离 | 能答 | 不能答 | 体积量级 |
|---|---|---|---|---|---|
| `Mini` | 模块列表、线程列表、异常信息、全部线程栈 | 托管堆对象数据、句柄信息 | 崩溃在哪行、线程调用栈长什么样 | 任何涉及堆对象内容的问题（对象字段值、集合元素、字符串内容） | 数十 KB 到数 MB |
| `Heap` | 上述 + 全部内存（除映射的模块镜像外）+ 句柄信息 | 模块镜像本身 | 内存泄漏、对象数量与大小异常、句柄泄漏、`!gcroot` 持有链追溯 | 需要模块镜像才能完成的分析（如某些反汇编场景） | 数十 MB 到数百 MB |
| `Triage` | 模块列表、线程列表、异常信息、全部线程栈，且已尝试脱敏（路径、密码等个人信息） | 堆对象数据、句柄信息，脱敏尝试覆盖的敏感字段 | 崩溃位置、线程状态——在需要对外传递 dump（如提交给第三方支持）又要求最小化敏感信息暴露时的折中选择 | 对象内容、泄漏归属；脱敏为「尽力而为」不保证完全 | 与 `Mini` 同量级 |
| `Full` | 进程的全部内存（含模块镜像） | 无 | 以上全部问题 | —— | 等同进程实际占用的虚拟内存 |

`Mini` 与 `Triage` 的核心差异不在保留的数据范围，而在是否尝试剥离个人信息（PII）——两者能回答的问题范围相同，`Triage` 只是在传递给外部前多做一道脱敏。

**`MiniPlus`（`procdump -mp`）对 .NET 进程无效。** procdump 另有一种 `MiniPlus` 类型，保留全部私有内存与可读写的镜像/映射内存，排除超过 512 MB 的最大私有内存区域，官方描述其"细节接近 Full 但体积只有 10%–75%"。但官方同时明确注明：**CLR 进程因调试限制一律按 `-ma`（Full）转储**。因此对 .NET 应用而言，`-mp` 不会带来任何体积收益，实际拿到的就是 Full dump——选它等于选 `-ma`，但会让人误以为产出的是精简版本。需要控制体积时应改用 `Heap` 或 `Triage`，而非 `MiniPlus`。

用托管堆分代术语具体化「保留」与「剥离」：`Heap` dump 保留的「全部内存」包含 gen0/gen1/gen2 三代对象、LOH、POH 的完整数据（结构见 `reference/clr-runtime-anatomy.md § 1. 托管堆分代结构`），因此 `!dumpheap -stat`、`!gcroot` 等按代分析的命令在 `Heap` dump 上都能正常工作；`Mini`/`Triage` 剥离的正是这部分堆对象数据——三代对象、LOH、POH 里的实际内容全部不在 dump 中，只保留了对象所在的调用栈引用了它们的事实（如果有），而非对象本身的字段值。这也是「查内存泄漏必须用 `Heap` 或 `Full`」这条判据在结构层面的来源：`gcroot` 追溯持有链需要遍历托管堆里对象之间的引用关系，`Mini`/`Triage` 根本不含这部分数据可供遍历。

## 2. 位数必须匹配

抓取 dump 的位数由被抓取进程的位数决定：64 位进程产出 64 位 dump，32 位进程（含运行在 WOW64 子系统下的 32 位进程）产出 32 位 dump。加载 dump 分析时，调试器（WinDbg、`dotnet-dump analyze` 等）的位数必须与 dump 的位数一致——用 64 位调试器加载 32 位进程的 dump，或反之，会得到无法解析的托管栈：符号无法正确匹配、`!dumpheap`/`!clrstack` 等命令报错或给出损坏的输出，而非明确的"位数不匹配"提示，容易被误判为 dump 本身损坏或符号缺失。

`procdump` 默认在 64 位 Windows 上为 32 位目标进程抓 32 位 dump；如果目标实际以 64 位运行却错误使用了 32 位版本的 procdump，同样会导致位数不匹配（见 `reference/dump-capture.md § 1. procdump（Windows，全运行时）` 的 `-64` 开关说明）。

## 3. dump 是单时点快照

dump 记录的是抓取那一瞬间进程内存与线程状态的完整快照，不包含任何历史信息。因此它能回答"此刻堆里有多少个某类对象""此刻哪些线程在等待哪个锁"，但无法回答"这类对象是什么时候开始增长的""增长速率有多快""这个死锁是哪一步开始形成的"——这类问题本质上需要跨时间点的采样对比（如多次抓取后比较 `!dumpheap -stat` 的差值，或使用 trace 类工具持续采样），而非单份 dump 能提供的信息。

一期知识库不含专门的时间线采样工具链（如 `dotnet-trace` 的计数器持续采集），仅在 `reference/dump-capture.md § 1. procdump（Windows，全运行时）` 中以连续抓取多份 dump 作为一期内可行的替代手段；完整的时间线分析方法留待二期路标。

遇到"间歇性抖动""偶发几秒钟的延迟尖峰"这类问题时，`reference/debugging-decision-tree.md` 的「间歇抖动」分支会先说明：dump 只能捕获抓取瞬间的状态，如果抖动窗口极短且抓取时机没能覆盖到发生瞬间，dump 里看到的会是正常状态，此时需要转向持续采样类工具而非单次抓取 dump。
