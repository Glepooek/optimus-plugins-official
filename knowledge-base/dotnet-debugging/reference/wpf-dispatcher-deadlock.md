# WPF Dispatcher 死锁归因

> **适用范围**：WPF 桌面应用，**仅 Windows**。覆盖 .NET Framework 4.x 与 .NET 6+ 两条 WPF 技术栈。非 WPF 应用的挂起排查见 `reference/debugging-decision-tree.md § 1. 进程挂起`。

本篇不引入新命令，全部复用一期已交付的 SOS 命令，增量是「同一份输出在 WPF 场景下怎么读」。预防性的线程与 Dispatcher 编码规范属另一领域，见 `knowledge-base/wpf/rules/09-threading.md § 5. 死锁防护`。那里讲怎么不写出死锁，本篇讲已经死锁了怎么认出来。

## 1. 从 !threads 认出 UI 线程

### 识别依据

UI 线程的判定依据不是线程编号。`0` 号线程通常是主线程，但主线程未必是 UI 线程——托管宿主场景（如 WPF 控件被托管进另一进程）或 `Main` 方法里另起一个 STA 线程创建窗口的场景下，UI 线程可能是任意编号；多 UI 线程应用（多窗口分属不同线程）中，每个线程各有独立的 `Dispatcher`，同一个进程可能有不止一条"UI 线程"。

两个判定条件须**同时**成立：

- `reference/sos-threads-and-stacks.md § 1. !threads` 输出中该线程的 `APT` 列为 **STA**（WPF 依赖 COM 单元模型，UI 线程必须是单线程单元）；
- `reference/sos-threads-and-stacks.md § 2. !clrstack` 显示该线程栈底可见 Dispatcher 的消息循环帧（经验性知识：常见形态是 `Dispatcher.Run`/`Dispatcher.PushFrame` 附近的帧，具体是否能看到内部帧因运行时版本与内联情况而异，不作为唯一判据）。

单独满足其中一个条件不足以下结论：STA 但没有消息循环帧的线程可能是普通 COM 互操作线程；有类似帧但非 STA 的情况在实践中未观察到，但仍建议两条件都查，避免单一信号误判。

### 操作步骤

1. 执行 `!threads`，列出全部托管线程，记下每条线程的 `APT` 列；
2. 对 `APT` 为 STA 的线程逐个 `setthread` 切换后执行 `!clrstack`（或对全部线程执行 `!clrstack -all` 一次性查看）；
3. 栈底出现 Dispatcher 消息循环帧的 STA 线程即为一条 UI 线程——注意可能不止一条。

### 判据与下一步

- **证实**：某线程 `APT` 为 STA 且 `!clrstack` 栈底可见 Dispatcher 消息循环帧 → 该线程是 UI 线程，后续按 `§ 2. UI 线程栈的三类等待形态` 判断它是否被阻塞。
- **排除**：全部线程都没有消息循环帧 → 有三种可能：该 dump 抓取时所有 UI 线程恰好已退出（例如窗口已关闭但进程未退出）；这根本不是一个 WPF 应用（可能是 Console/Service 类无界面挂起）；或者消息循环帧因内联或符号缺失而不可见（见 `reference/symbols-and-tool-matching.md § 4. 缺符号时的降级读法`）。第三种情况须先补齐符号或换用元数据可见的托管栈重新核对，避免在符号不全的 dump 上误判成"这不是 WPF 应用"；前两种转 `reference/debugging-decision-tree.md § 1. 进程挂起` 走通用的、不依赖 UI 线程假设的排查路径。

## 2. UI 线程栈的三类等待形态

### 识别依据

确认某线程是 UI 线程（`§ 1`）之后，若它当前无响应，第一步是看它的栈顶停在什么形态上。UI 线程被阻塞时，栈顶只会呈现以下三类之一，三者的下一步取证命令与修复方向完全不同：

| 栈顶形态 | 含义 | 下一步 |
|---|---|---|
| `Monitor.Enter` / `Monitor.ReliableEnter` | 等 Monitor 锁 | `§ 4. 定位持锁方与互等闭环` |
| `Task.Wait` / `Task.Result` / `WaitHandle.WaitOne` | 同步等待异步结果 | `reference/sos-locks-and-async.md § 2. !dumpasync`（.NET 6+ 限定，Framework 下按该篇降级读法） |
| `CoWaitForMultipleHandles` 等 COM 编组帧 | 等待一次 COM 调用返回 | 超出 SOS 托管取证范围，需转原生栈分析（如 `!dumpstack` 结合非托管符号） |

第二行是 WPF 里最常见、最容易被写出的一类——UI 线程 `await` 时用 `.Result`/`.Wait()` 同步等待自身抛出的异步任务，属于编码层面本可避免的反模式，预防规范见 `knowledge-base/wpf/rules/09-threading.md § 5. 死锁防护`；本篇讲的是它已经发生之后，dump 里长什么样。

第三行是本篇的能力边界：COM 编组等待发生在非托管侧，SOS 的托管栈追踪到 `CoWaitForMultipleHandles` 之类的帧后无法再深入解析等待的是哪个具体 COM 调用，也无法判断对端为什么不返回——继续排查需要非托管调试手段，不写"如何解决"是因为已超出本篇范围，硬凑判据反而误导读者在 SOS 里空转。

### 操作步骤

1. 对 `§ 1` 认出的 UI 线程执行 `!clrstack`；
2. 按上表比对栈顶帧，确定属于哪一类等待形态；
3. 按对应"下一步"列跳转到相应命令或范围声明。

### 判据与下一步

- **证实**：栈顶命中上表任一行 → 该 UI 线程确实处于阻塞等待，按对应行的"下一步"继续；
- **排除**：栈顶既不是等待原语也不是上表三类之一，而是普通业务方法帧 → 该线程并非被阻塞，转 `§ 3. Dispatcher 队列积压 vs 真死锁` 判断是否属于"长任务占用 UI 线程"的另一种成因。

## 3. Dispatcher 队列积压 vs 真死锁

### 识别依据

界面无响应有两种成因，外在表现相同，处置方向相反：

- **UI 线程在跑长任务**：某个事件处理器或命令在 UI 线程上做了耗时同步操作（大量数据绑定刷新、同步 IO、密集计算），Dispatcher 消息队列因此排队积压，界面表现为卡顿或彻底无响应，但线程本身没有被谁阻塞——它一直在忙，只是忙的不是"响应消息"；
- **UI 线程被阻塞**：`§ 2` 列出的三类等待形态之一，线程压根没有在执行任何业务代码，而是挂起等待一个永远等不到（或很久才等到）的信号。

区分依据是**栈顶形态**，不是无响应时长。"界面卡超过 30 秒就是死锁"是错误判据——长任务同样能卡任意久（例如同步处理一个几十万行的 CSV），而某些死锁在极端情况下也可能在几秒内因超时机制自行解开。时长只是征象，不是判据。

### 操作步骤

1. 对 UI 线程执行 `!clrstack`；
2. 栈顶为业务方法帧（不是 `§ 2` 表中任一等待原语）→ 长任务占用；栈顶为等待原语 → 转 `§ 2` 已给出的对应下一步；
3. 怀疑长任务时，配合 `reference/sos-threads-and-stacks.md § 5. !dso` 看栈上持有哪些对象，辅助判断具体在处理什么（例如栈上能看到一个巨大的 `List<T>` 或 `DataTable` 实例，佐证是在处理大数据集）。

### 判据与下一步

- **证实**长任务：栈上有业务方法帧（非等待原语），且这些帧对应的方法确实在做数据处理/IO/计算 → 修复方向是把这部分工作挪到后台线程（`Task.Run` + `IProgress<T>` 回 UI），预防规范见 `knowledge-base/wpf/rules/09-threading.md § 3. 后台任务与 UI 更新模式`；
- **证实**阻塞：栈顶是 `§ 2` 表中的等待原语之一 → 走 `§ 2` 对应分支，最终指向打破等待环（`§ 4`）；
- **排除**：UI 线程栈看起来正常（既不在跑长任务也没有等待帧，栈很浅或处于消息循环本身）→ 无响应另有成因，可能是渲染线程（WPF 的合成/渲染在独立的 Composition 线程，UI 线程正常不代表画面在刷新）问题，或消息泵本身被某个非托管钩子占用——这两种都超出本篇（本篇只覆盖 UI 线程自身阻塞或过载）的范围，需要专门的渲染或消息钩子排查手段。

## 4. 定位持锁方与互等闭环

### 识别依据

`§ 2` 中判定 UI 线程停在 `Monitor.Enter`/`Monitor.ReliableEnter` 帧后，只能得出"它在等一把锁"，尚不能证实死锁——必须找到持有该锁的线程，并确认这条持锁线程反过来是否也在等待、且等待对象最终回到 UI 线程本身，形成闭环，才构成死锁证据。单看 UI 线程这一侧永远只能得出"在等"，看不到环就不能下死锁的结论。

### 操作步骤

完整闭环四步：

1. 执行 `reference/sos-locks-and-async.md § 1. !syncblk`，找到 UI 线程正在等待的那把锁对应的同步块，读取其 `Owning Thread Info` 一列——该列给出的 OS 线程 ID（十六进制）与 SOS 线程索引，分别对应 `!threads` 输出的 `OSID` 列与 `ID` 列；
2. 用其中的 SOS 线程索引回 `!threads` 输出定位到对应的托管线程；
3. 对该线程 `setthread` 切换后执行 `!clrstack`，看它当前在等什么；
4. 若它等的锁又被 UI 线程持有（或者链条继续传递、最终又绕回 UI 线程），环闭合，构成死锁证据。

排查同步块表本身是否膨胀（条目数持续增长）须加 `-all` 参数——默认输出只反映当前被持有的同步块，是 `-all` 输出的子集；此细节 `reference/sos-locks-and-async.md § 1. !syncblk` 已述，此处不重复。

### 判据与下一步

- **证实**：沿持锁方向追踪下去，等待关系最终成环（UI 线程等锁 A，持有锁 A 的线程等锁 B，……,持有最后一把锁的线程反过来等待 UI 线程持有的资源）→ 死锁证据闭环完整，修复方向是打破环上任一等待边，常见做法是改用异步调度避免 UI 线程持锁等待后台，见 `knowledge-base/wpf/rules/09-threading.md § 5. 死锁防护`；
- **排除**：追到的持锁方线程栈顶不是等待原语，而是正常业务帧（它在忙，只是恰好慢）→ 不是死锁，而是锁竞争（热点锁），转 `§ 3. Dispatcher 队列积压 vs 真死锁` 的长任务分支判断具体耗时原因。
